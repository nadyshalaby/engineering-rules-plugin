# 16.12 [route] Authoring a new skill

Use this when the user wants a **new reusable skill** — a documented, repeatable procedure
that will be invoked by name later, not a one-off script.

## Four steps, in order, and the file is written last

```
1. Clarify   (1-3 questions)
2. Draft     (in working memory, never on disk)
3. Validate  (7 checks, blocking)
4. Write     (one write, only after step 3 passes)
```

**Step 1. Clarify.** Ask one to three questions, batched, from this bank. Drop any the
user's prompt already answered:

- **Purpose.** What does the skill do, in one sentence? *Required.*
- **Triggers.** Which user prompts should reach it? Three to six phrases. *Required.*
- **Artifact.** What does it write, print, or produce? *Required.*
- **Kept and skipped steps.** Only when the skill is a variant of an existing procedure.

**Step 2. Draft in memory.** Required sections, in this order:

1. `# <name> (<one-line title>)`
2. `## When to invoke`
3. `## How it works`
4. `## What this skill does NOT do`
5. `## Anti-rationalizations` — a table, at least four rows
6. `## One-line summary`

Extra sections are welcome between those. The four anchors appear in that order.

**Step 3. Validate.** Every check is a yes or no. Any `no` sends you back to step 2.

1. **Name.** Matches `^[a-z0-9-]{1,64}$`. Kebab-case, no leading or doubled dash.
2. **Triggers.** At least three distinct phrases a prompt can be matched against.
3. **Sections.** The four anchors present, in order.
4. **Embedded checklists carry their own verification.** Any procedure the skill embeds
   has a numbered method, a yes/no verification list, and a stated output shape. A method
   with no verification is a suggestion.
5. **Output caps are explicit.** Where the skill caps a report's length, it says `≤N words`.
   Never "keep it short".
6. **No soft language in the body.** Zero occurrences of: *if reasonable, consider, maybe,
   try to, usually, as appropriate, where possible, generally, often.* The one exception is
   inside an anti-rationalizations row or a labelled bad-example block, where the soft
   phrasing is the thing being rejected.
7. **Size and paths.** The file is at or under 500 lines, and every cross-reference is a
   repo-rooted path or a section reference — never an absolute path into someone's home
   directory, so the skill travels with the repository.

Output step 3 as a seven-row table of yes/no with one line of evidence each.

**Step 4. Write.** One write. No partial drafts on disk — a half-written skill gets
committed and then invoked. After writing, confirm the structure and the line count.

## What this does NOT do

- **It does not edit an existing skill.** That is an ordinary change and goes through the
  normal phases, where it gets a plan and a review.
- **It does not delete a skill.** That is a deliberate removal, done by hand.
- **It does not author supporting files.** Reference files and assets are a separate task.

## Anti-rationalizations

| Thought | Reality |
|---|---|
| "I'll skip the validation this once." | The checklist is the deliverable. Skipping it ships a skill that fails on first use, which is a re-do, not a shortcut. |
| "The user asked for a quick skill, so the checks are optional." | The checks are never optional. They are cheap insurance the user would regret losing. |
| "I'll write the file first and validate after." | A half-written skill on disk gets committed and routed to. Validate in memory, write once. |
| "Seven checks is a lot, four is enough." | Each check exists because its absence produced a specific failure. Removing one reopens it. |
| "The skill is small, the structure is overkill." | The structure is what makes it findable and invocable later. A small skill nobody can trigger is a file. |
