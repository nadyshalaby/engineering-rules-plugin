# 16.9 [route] Exploring one feature, entry point to leaves

## Explore a feature (one verified execution path, published as a browsable page)

> ## ⚑ Locked contract, read this BEFORE anything else
>
> 1. **Code is the only source of truth.** A README, a docblock, a comment, a work-doc, a
>    chat memory or an earlier page is intent at best and never a fact on the page. Every
>    sentence the page shows is derived from lines the page also shows, and every cited line
>    is checked against the working tree by `verify-trace.sh` before the page is built (1.5).
> 2. **One entry point, walked to its leaves.** A leaf is an external call, a query handed to
>    a driver, a filesystem or network syscall, a queue put, a pure mapper with no outgoing
>    call, or a type. Stopping at "the service" is the failure this route exists to ban.
> 3. **Every hop is a verified frame with a verified call site.** The parent line that calls
>    it is cited by file, line and a literal substring of that line; the verifier checks the
>    frame, the call site and that the call site sits inside the parent's excerpt.
> 4. **Unresolved is shown, never guessed.** A handler map, a DI token, a runtime flag, a
>    tenant branch, `handlers[type](payload)`: the hop is `unresolved`, its `reason` says why
>    the code alone does not decide, and its `candidates` name every frame that could be
>    next. The page draws it dashed. The user picks; the route does not.
> 5. **Nothing is written into the explored repository.** Trace, excerpts and page live under
>    the scratch directory (16.10, "Where the files live") and the page is published through
>    the artifact tool. No folder in the repo, no server, no `.gitignore` edit.
> 6. **One feature per page, 40 hops at most.** A bigger feature is chapters (16.10, "Size
>    caps"), each a complete page, cross-linked through `related`, the user picking the first.
> 7. **The page is the deliverable; the chat carries the handoff** (step 8): the link, the
>    verification line, the unresolved hops, the questions and the decisions checklist.
>
> ### Refused: redo the trace when any of these holds
>
> - `verify-trace.sh` exits 1. The fix is re-reading the cited file and correcting the trace,
>   never editing `evidence` until the check passes.
> - A hop's `why`, a shape, a branch outcome or a decision states something no excerpt shows.
> - A leaf was not reached and `unreached` does not say so.
> - A hop the runtime decides is marked `verified`.
> - The page was built from a trace the verifier refused, or published from a file
>   `build-page.sh` did not write.

The deliverable is a page the user opens to digest one feature in minutes: three columns,
the call stack on the left, diff-style excerpts with line numbers in the middle, and a flow
rail on the right (overview, a clickable sequence diagram, pseudocode steps, branches, the
failure path, shapes, decisions, a quiz), every view keyed to one selected hop. Two files
carry the detail:

- **16.10**, the trace data schema: what `trace.json` holds, what `excerpts.json` holds,
  and the checks the verifier runs, listed in 16.10.
- **16.11**, the trace rubric: how each field is derived from the code, the ambiguity table,
  the accelerators and the yes/no gate that stands between the trace and the page.

Read both from disk before step 3 on the first run in a session. The always-on law binds
throughout: every question goes through the wizard tool, every claim carries fresh evidence,
and the explored repository is never edited.

## Definitions for this route

| Term | Meaning |
|---|---|
| **Hop** | One frame on the path: a function, handler, middleware, schema or type the path reaches, cited by file, line and evidence, with the call site that reached it. |
| **Leaf** | A hop with no outgoing call on the path: `kind` `io`, `external` or `type`, or a `call` whose excerpt calls nothing further. |
| **The artifact tool** | The runtime's page publisher, `Artifact` on Claude Code. Where the runtime has none, the page stays a local file and its path is the handoff. |
| **The scripts** | `verify-trace.sh` and `build-page.sh` under `skills/explore-feature/scripts/` in this plugin, with the template under `skills/explore-feature/assets/`. |
| **The scratch folder** | `<scratch>/explore-<slug>/`, 16.10. |

## When to invoke

This route is picked by its sub-command, `/engineering-rules:explore-feature <entry point>`
(4.4), or by the classifier (4.1) when the user names an entry point and wants to see how
it runs end to end: *"walk me through what happens when this route fires"*, *"trace
`POST /orders` to the database"*, *"explain how the migration runner works"*, *"explore the
send-estimate feature"*.

**Do not invoke** for a lookup one grep answers (*"where is X defined"*, *"who calls Y"*):
that is a read-only ask, and a page is the wrong size for it. A PR is a diff, not an entry
point; *"walk me through this PR"* routes to Phase 5 (12.1) or triage (16.2).

## Where the scripts are, resolved before anything else

The scripts ship with this plugin at `skills/explore-feature/scripts/`. Resolve the absolute
path from the base-directory line of whichever skill loaded:

- Loaded by the sub-command: that base directory is `skills/explore-feature`, and the
  scripts are at `<base>/scripts/`.
- Loaded by the main skill: that base directory is `skills/engineering-rules`, and the
  scripts are at `<base>/../explore-feature/scripts/`.

```bash
SCRIPTS=<resolved>/scripts
test -x "$SCRIPTS/verify-trace.sh" && test -x "$SCRIPTS/build-page.sh" && command -v jq >/dev/null && echo ready
```

Print `ready`, or stop and say which of the two files or `jq` is missing. Nothing else in
this route runs until that line printed.

## Workflow shape

```
1 confirm the entry → 2 read the conventions from the code → 3 walk to the leaves
→ 4 author trace.json → 5 verify → 6 gate on the rubric, build the page → 7 publish
→ 8 chat handoff. A re-run on the same entry starts again at 1 and republishes to the same link.
```

### Step 1. Confirm the entry point; ambiguity stops the walk

Parse the request for exactly one entry and resolve it to one file and one line. When any
row of the ambiguity table in 16.11 (section 1) applies, stop and ask through the wizard
tool which path to explore, the candidates as the options. Never pick one silently.

When the entry is settled, print two lines:

```
Exploring: src/orders/orders.routes.ts:7 for POST /orders
slug: post-orders
```

The slug follows 16.10 ("Slug convention"). It names the scratch folder and the page file.

### Step 2. Read the conventions from the code, not from the docs

Spend the first minutes on the tree around the entry: the framework's signature, how
dependencies are wired, the error model, the layer vocabulary, where tests live. Read a
`README`, `CLAUDE.md` or `ARCHITECTURE.md` only as a map of where to look; nothing from
them reaches the page unless the code shows it. The rules are in 16.11, section 0.

### Step 3. Walk depth-first to the leaves

For every hop, in this order, from the file itself:

1. Open the file. Read the frame. Record `file`, `symbol`, `line` and `evidence`, the
   evidence copied from the line, never retyped.
2. Record the `call` site in the parent's excerpt the same way.
3. Decide `range` (the lines this path runs, with enough context to read, at most 200) and
   `invoked` (16.11, section 3, the hardest field).
4. Record `kind`, `why`, `returns`, `throws`, `status`; on `unresolved`, the `reason` and
   the `candidates`.
5. For every outgoing call on the invoked lines that is not a leaf, recurse. For every type,
   schema or DTO named in the signature on the path, add a `type` hop.

**Accelerators are hints, never evidence.** `graft`, `rg`, `fd`, `ast-grep` and the like,
when installed, shorten the search for the next frame; every hop is still read from its
file, and a citation that came from a tool's output without the file being opened is a
citation typed from memory (16.11, section 10).

**The cap is 40 hops.** Reaching it is not a reason to trim: it is the signal to split into
chapters (16.10, "Size caps") and to ask the user, through the wizard tool, which chapter to
build first. A 3-hop page for a feature that reaches a database is shallow, and shallow is
refused by the contract above.

### Step 4. Author `trace.json`

Write `<scratch>/explore-<slug>/trace.json` to the shape in 16.10, `version: 2`, `root` an
absolute path, every hop in walk order with `h0` first. Fill the flow rail from the code
alone: `pseudocode` (1 to 12 steps, each naming its hops), `branches` (listed, never
expanded), `failure` (one path a reader most needs to know), `shapes` (typed pseudocode),
`decisions` (what the code decided and what the alternative would have cost), `questions`
(3 to 5), `unreached` (everything on the path you did not open, by name) and `related`
(the other chapters, when there are any). The derivation rules for each are in 16.11.

### Step 5. Verify

```bash
bash "$SCRIPTS/verify-trace.sh" "<scratch>/explore-<slug>/trace.json"
```

Exit 1 prints one line per problem, `hop <id>: …` or `trace: …`, and writes nothing. Fix
each by re-reading the cited file, run again, and paste the passing run's last line
(`verified N hops across M files; wrote …/excerpts.json`) into the chat. That line, fresh,
is the evidence the page rests on. The checks are listed in 16.10. A passing run that also
prints `note: no hop carries invoked` is a finding, not a pass to build on: go back to step
3 and decide `invoked` wherever the code decides which lines run (16.11, section 3).

### Step 6. Gate on the rubric, then build

Print the yes/no gate from 16.11 (section 11), filled in. Any `no` goes back to step 3 or
4. Then:

```bash
bash "$SCRIPTS/build-page.sh" "<dir>/trace.json" "<dir>/excerpts.json" "<dir>/page.html"
```

The builder inlines the template, embeds both JSON files, and refuses an excerpts file that
does not cover every hop or whose excerpt lines carry a hardcoded secret, judged by the law
scout's own patterns (9.5) with the value redacted: the page is published, so a secret in an
excerpt is fixed at its source, never shipped. Its output line (`wrote …/page.html (N
bytes)`) is pasted too.

### Step 7. Publish

Publish `page.html` through the artifact tool: `favicon` `🧭` on the first publish of an
entry, a one-sentence `description` naming the entry and the repository, and the `url` of
the earlier page when the same entry was explored before in any conversation (find it with
the tool's list action, or ask the user for the link). The template already carries the
page's design; nothing is restyled per run. Where the artifact tool is not available, print
the absolute path of `page.html`; it opens in any browser as a file.

### Step 8. Chat handoff

Print, in this order and nothing else before it:

```
Explored: POST /orders → <link or path>
Verified: 8 hops across 8 files, . @ 3f2a9c1, 2026-09-13T10:41:07Z, 0 cited files with uncommitted changes
Unresolved: h7 notify, 2 candidates named on the page
Not covered: src/platform/email/resend.client.ts, the provider client and its retry policy
```

Then the **questions** (3 to 5, the same ones the page's quiz carries, so the user can
answer in their head and check on the page), and the **decisions checklist** in three
buckets, one short line per item, each ending with the hop it rests on, and `(none on this
path)` for an empty bucket:

```
Safe to change:
  - The 201 envelope shape in the controller (h2)
Load-bearing:
  - The insert runs before the stock check; moving it changes what a backorder leaves behind (h4, h5)
Chesterton's fence (don't touch until you ask):
  - notify matches handler keys by prefix; a third registration changes who gets the event (h7)
```

A line in either list that rests on no hop is cut: the point of the page is that every
claim has a line behind it, and the handoff keeps that promise.

## Re-runs

A second exploration of the same entry starts again at step 1 and walks the tree as it is
now. Nothing from the earlier trace is merged, because the earlier trace described an
earlier tree. The new page is published to the earlier link (`url`), so the user's bookmark
stays good, and the verification line in the handoff says which commit the new page
describes.

## Anti-rationalizations

| Tempting shortcut | Why it breaks the deliverable |
|---|---|
| "The README explains this flow, I'll paraphrase it onto the page." | The README is what somebody believed when they wrote it. The page shows lines; a sentence no line supports is the one the user will act on and be wrong about. Derive it from the excerpt or leave it off. |
| "Stopping at the service is fine, everybody knows what the repository does." | The user asked to digest the feature, and the feature ends where the row is written, the email leaves the process or the event is enqueued. The contract bans the stop, and `unreached` exists for the leaf you could not open. |
| "The DI token obviously resolves to Postgres, I'll mark it verified." | Obvious is not a citation. The hop is `unresolved` with the candidates named, and the page draws it dashed so the reader knows the code did not decide it. |
| "I'll publish now and run the verifier after." | The verifier is what makes the page trustworthy. A page built before it ran carries citations nobody checked; the order in this route is not negotiable. |
| "The evidence string is off by a character, I'll fix the string." | The check failed because the line was typed from memory. Re-read the line and copy it; a string edited to pass proves the check was defeated, not passed. |
| "40 hops is too many for one page, I'll trim to the interesting ones." | Trimming hides hops; chapters keep them. The cap splits the feature, it never shortens the path. |
| "graft says the callee is `insertOrder`, that is the citation." | The tool said where to look. Open the file, read the frame, copy the line; the verifier will refuse the citation otherwise, and it should. |
| "The user asked to walk through this PR, close enough." | A PR is a diff, not an entry point. Phase 5 (12.1) or triage (16.2). |

## What this route does NOT do

- It does not edit the explored repository, and it writes nothing inside it.
- It does not review or refactor. `decisions` and the checklist name what the code decided
  and what a change would touch, each with a hop behind it; they propose no fix.
- It does not follow a call into another process. A queue put, an HTTP call and a job
  enqueue are leaves; the downstream side is another exploration rooted there.
- It does not build an index of every endpoint. One feature per page.
- It does not merge an earlier page's notes into a new one; a re-run is a fresh walk.
- It does not generate tests, types or documentation.

## One-line summary

**`/engineering-rules:explore-feature <entry>`** → confirm one entry (ask on ambiguity) →
read the conventions from the code → walk depth-first to the leaves, types included,
`unresolved` where the runtime decides → `trace.json` (16.10) → `verify-trace.sh` refuses
any citation the tree disagrees with → the rubric gate (16.11) → `build-page.sh` → one
browsable page published through the artifact tool → the chat handoff with the
verification line, the questions and the decisions checklist.
