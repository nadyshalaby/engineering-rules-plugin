# 16.11 [rubric] The trace rubric

## How every field of a trace is derived from the code, and the gate before the page

The page renders whatever the trace says. A polished page over a sloppy trace is worse than
no page, because it looks trustworthy. This rubric is how each field is derived, from the
code and from nothing else, and it ends with the yes/no gate that stands between the trace
and `build-page.sh`.

---

### 0. Sources: the code, and where a document is allowed to point

- **The code is the only source of truth.** Every value in `trace.json` is read from a
  file under `root` in this session. What the page says about a hop is what its excerpt
  shows; what it says about a shape is what the type declaration shows.
- **Documents are a map, never a fact.** A `README`, `ARCHITECTURE.md`, `CLAUDE.md` or a
  docblock says where to look and what the author intended. Read them to find the entry
  and the conventions; then open the files they point at. A sentence whose only support is
  a document does not go on the page.
- **`author_says` is the one place a comment's claim appears**, labelled as a comment, and
  only when the excerpt agrees with it. A comment the code contradicts is not repeated on the
  page; it goes into `decisions` as "the comment at line N says X, the code does Y", which is
  a fact about the code.
- **Conventions come from the tree**: the framework's own layer words (a Hono app has routes,
  controllers, services, middleware; a Rails app has controllers, models, concerns), how
  dependencies are wired (constructor injection, a decorator, a factory, a module-scope
  singleton), the error model (throw, `Result`, tuples, null-for-missing), where tests live.
  Write the detected convention in one line before the walk, so the `layer` of every file
  and the `why` of every hop use the repository's vocabulary.

---

### 1. Confirm the entry point. Never guess.

Resolve the request to one frame. When any row applies, stop and ask through the wizard
tool, the candidates as the options:

| Ambiguity | Example | Ask |
|---|---|---|
| Several matching definitions | two `createOrder` functions in different modules | which file |
| Conditional registration | a route mounted only under `if (env.FEATURE_X)` | flag on, off, or both pages |
| Tenant or role fork at the entry | the same handler dispatching on `c.var.tenant.plan` | which tenant or role |
| DI token with several providers | `@Inject(USER_REPO)` bound to two classes | which binding |
| Dynamic dispatch at the entry | `handlers[type](payload)` | which `type` |
| A method name and no owner | *"trace `send`"* | which class or module |

After the answer, print `Exploring: <file>:<line> for <label>` and the slug (16.9, step 1).

---

### 2. Walk depth-first, one hop at a time

For every frame on the path, in this order, from the file:

1. **`file`, `symbol`, `line`, `evidence`.** Open the file. `line` is the frame's
   declaration line. `evidence` is a substring of that exact line, copied, not retyped: the
   verifier compares it byte for byte, and a typo here is how it catches a citation made
   from memory. Prefer a substring that survives a reformat of the rest of the line, `export
   async function placeOrder` over the whole signature.
2. **`call`.** The line in the parent's excerpt that reaches this frame, cited the same way.
   It must sit inside the parent's `range`; widen the parent's range before citing a call
   outside it.
3. **`range`.** The lines this path runs plus the context a reader needs, at most 200. The
   frame line and every child's call line must be inside it. Narrow a long function to the
   arm this path takes; the whole function is one click away in the editor.
4. **`invoked`.** Section 3 below. Omit it when the code does not decide which lines run.
5. **`kind`.** `entry` for `h0`; `middleware` for a guard or filter on the way to the
   handler; `dispatch` for a frame that picks the next frame at runtime; `io` for a query,
   a file or a socket handed to a driver; `external` for a call that leaves the process; `type`
   for a schema, DTO, interface or class referenced on the path; `call` for everything else.
6. **`why`.** One sentence, in the domain's words, that the excerpt supports: what this hop
   does on this path and the one thing about it a reader must not miss. Not a restatement of
   the code ("calls insertOrder") and not a guess about intent.
7. **`returns`** and **`throws`.** From the `return` statements on the invoked lines and the
   `throw` statements on the path, plus the errors a callee on the path is cited as throwing.
   `throws[].when` is the condition from the code, `order.backordered`, not "on failure".
8. **`status`.** Section 4 below.
9. **`title`.** At most 60 characters, a verb phrase a reader can scan in the stack:
   "placeOrder inserts the row, then emails and notifies".

**Recurse into every non-leaf call on the invoked lines**, in the same file or another, in
the same class or another. A decorator or middleware that runs on this path is a hop. Add a
`type` hop for every schema, DTO, interface or class named in a signature on the path, with
`invoked: []` and the declaration as its excerpt; a type is referenced, not run, and the page
shows it undimmed.

---

### 3. `invoked`, the hardest field

The page washes the invoked lines and dims the rest, and that contrast is the page's primary
signal about what ran. Getting it wrong is worse than leaving it out.

The floor is mechanical, and `verify-trace.sh` refuses a trace under it: `line` is in
`invoked`, because the line a hop is entered at runs; every child hop's `call.line` is in it,
because a call on this path runs; no blank or comment-only line is, because nothing runs
there. Above the floor the field is judgment, and these steps are the judgment:

1. Start from `range`; assume every line runs.
2. Walk the body top to bottom. For every conditional:
   - `if (a) { A } else { B }`: when the code decides which arm this path takes, the other
     arm leaves `invoked`. When a runtime value decides (an env flag, a row's column, a
     tenant setting), stop: the hop keeps no `invoked`, and the fork goes into `branches`
     with `taken` reflecting what the entry's trigger implies, or the hop becomes
     `unresolved` when the next frame depends on it.
   - `switch`: only the matching case and its fall-through.
   - `try { A } catch { B }`: on the path the trigger describes, `B` runs only when `A`
     throws; the catch arm leaves `invoked` and the throw goes into `failure` or `branches`.
   - `a && b`, `a || b`, `a ?? b`: when the left side decides, the right side may not run;
     count cautiously and keep the line when in doubt.
   - An early `return` or `throw` on line N: nothing after N runs.
3. Every `invoked` line is inside `range`; the verifier refuses one that is not.

**The failure mode:** every line marked invoked because "the function ran". A 30-line `else`
arm that did not fire then looks like it did, and the reader trusts it.

---

### 4. `status`: verified or unresolved, and what unresolved must carry

A hop is **`verified`** when the code alone decides that this frame is the next one: a
direct call, an import that resolves to one file, a middleware listed by name.

A hop is **`unresolved`** when the runtime decides: a handler looked up in a map, a DI token
with more than one binding, a strategy chosen by a config value, a tenant-specific override,
a plugin registered at boot, a method resolved through an interface with several
implementations. Then:

- `reason` says, in one sentence, what decides and why the code does not: "handlers is
  filled at boot and matched by prefix; two keys prefix order.placed".
- `candidates` names every frame that could be next, each a full citation the verifier
  checks. A candidate you could not find is named in `unreached` instead.
- The walk continues into no candidate. An unresolved hop is a leaf on this page; the user
  picks a candidate, and that is a new exploration rooted there.

Marking a runtime-decided hop `verified` because the answer is "obvious" is the one error
the page cannot recover from: it draws a solid arrow where the code has none.

---

### 5. `branches`: listed by name, never expanded

One entry per fork the path meets, in the hop where it sits:

```json
{ "at": "h4", "name": "backordered", "trigger": "order.backordered", "taken": false,
  "outcome": "OutOfStock is thrown after the row was already inserted" }
```

- `name`: what the fork means, "backordered", "admin override", "cache hit"; not the code.
- `trigger`: the condition from the code, one line.
- `taken`: whether this path takes it, from the entry's trigger and the code.
- `outcome`: what the arm does, read from its lines, in one line; the arm is not walked.

The page lists every branch in one tab so the reader sees the roads not taken without the
path turning into a call graph.

---

### 6. `failure`: the one failure path a reader most needs

Pick one: the first refusal a bad input meets (validation, auth), or the throw in the
deepest hop that leaves state behind. `steps` are the lines the failure runs through, in
order, each read from the code: where it is thrown, who catches it, what the caller sees,
what was already written. `hops` names the frames the steps touch.

---

### 7. `shapes`: typed pseudocode from the declarations

At the hop where a shape is declared or transformed: `{ sku: string, quantity: number }`,
`Order | null`, `{ data: Order, error: null, meta: {} }`. From the type, the schema or the
`returning` clause, never paraphrased. When a layer narrows a shape (a row becomes a DTO),
record both, at their hops, so the reader can see the field that was dropped.

---

### 8. `decisions`: what the code decided, and the cost of the alternative

One entry per decision the path embodies that a reader could reverse by mistake: the order
of two operations, a check before or after a write, a retry or its absence, a cache read on
the path, a value copied instead of referenced. `text` is the decision as the code shows it;
`alternative` is what the other way would cost, in one line; `hops` cites where. A decision
with no hop is a review comment, and this route does not make review comments.

---

### 9. `questions`: three to five, answerable only from the path

Each names a layer boundary, a side effect, a branch not taken or a shape transition the
path shows, and `a` answers it from the hops it cites:

> - Where does `user.id` come from by the time `placeOrder` reads it? (h1, h2)
> - What has already been written when `OutOfStock` is thrown? (h4, h5)
> - Why is the last hop unresolved? (h7)

The page hides the answers behind a click; the chat prints the questions so the user can
answer in their head first.

---

### 10. Accelerators: hints, gated, never evidence

Run a tool only after `command -v <tool>` says it is on PATH; say which ran. Typical:

| Tool | Use it for | Never for |
|---|---|---|
| `graft callers <symbol> --direction out -d 2 --json` | the candidate callees of a frame, in one call | a citation: the file is still opened and the line copied |
| `graft skeleton <file>` | the symbol list and ranges of a file, to pick `range` | `invoked`, which needs the body read |
| `rg -n '<symbol>\(' <root>` | every call site of a symbol, to find the parent line | proof that only one exists: read the hits |
| `fd <name>` | locating a file the import path does not spell out | deciding between two matches: that is the ambiguity table |
| `ast-grep` | a structural search where a regex would over-match | anything the two above already settled |

A tool's output tells the walk where to read next. Every hop on the page is read from its
file; the verifier makes a citation that skipped the file fail, and that is the design.

---

### 11. The gate, printed before `build-page.sh` runs

Every row is `yes` or `no` with one line of evidence. Any `no` sends the walk back to the
hop it names; nothing is built over a `no`. Row 13 is answered again at the rebuild with a
capture (16.9, step 6b), and `no capture` is its third answer, with the reason the handoff
carries.

```
Trace gate for <slug>
1. verify-trace.sh passed on this exact trace.json, output line pasted above?          yes / no
2. Every leaf on the path is a hop, or is named in `unreached`?                         yes / no
3. Every hop the runtime decides is `unresolved`, with reason and candidates?           yes / no
4. Every `why`, `outcome`, `shape`, `decision` and `answer` is supported by an excerpt?  yes / no
5. No sentence on the page comes from a document, a comment or memory alone?            yes / no
6. Every type named in a signature on the path is a `type` hop?                         yes / no
7. `invoked` is given only where the code decides which lines run?                      yes / no
8. `branches` lists every fork the path meets, none expanded?                           yes / no
9. `pseudocode` has 1 to 12 steps and every step names its hops?                        yes / no
10. `questions` has 3 to 5 entries, each answerable only by following the path?         yes / no
11. Hops ≤ 40, or the feature is split into chapters linked through `related`?           yes / no
12. Nothing was written inside the explored repository?                                 yes / no
13. The capture was written by capture-run.sh and embedded by build-page.sh --capture,
    and no code-derived field quotes a value from the run?                              yes / no / no capture
```

---

### 12. After the page: the handoff

The page is the deliverable. The chat prints the handoff in 16.9, step 8: the link, the
verification line taken from `excerpts.json` (hops, files, repository and commit,
`verified_at`, the count of cited files with uncommitted changes), the `Captured:` line
taken from the runner's output (or `none` with the reason), the unresolved hops with their
candidate counts, the `unreached` list, the questions, and the decisions checklist in three
buckets with a hop behind every line.

---

### 13. Captured values: observations of one run, masked, never the contract

A capture (16.9, step 6b; 16.10, "capture.json") records what one run did: the arguments
each anchored function got, what it returned or threw, how long it took, and which way each
condition went. It is evidence about that run and about nothing else:

- **One run is one run.** An `if` that went `true` once did not go `true` always; a
  function that returned a string once has the return type its declaration gives it. The
  shape stays derived from the declaration (section 7), the `why` from the excerpt (section
  2), a branch's `taken` from the entry's trigger and the code (section 5).
- **Masked, and cut.** The sink masks secret-shaped keys, emails, phone numbers and tokens
  before a byte reaches disk, and caps depth, string length, item and key counts; the runner
  and the builder each refuse a capture that still carries a secret. A value on the page that
  reads `<masked>` or `<email>` is the mask working, not a defect in the trace.
- **Shown where it was observed, labelled as such.** The page renders the capture on the
  Runtime tab, under each excerpt and as chips on the lines, and every block says it is one
  run. No field of `trace.json` quotes a captured value, and the handoff's checklist rests
  on hops, never on a run.
- **A run that reaches no anchor is a fact about the command, not about the code.** The
  runner refuses it; pick the test that reaches the entry or fire the request, and say which
  in the handoff.

---

### Wrong → right, the four errors the verifier and the gate exist for

**Evidence typed from memory**

```json
// wrong: the line reads `export async function createOrder(c: Context) {`
{ "line": 6, "evidence": "export function createOrder" }
// right: copied from the line
{ "line": 6, "evidence": "export async function createOrder" }
```

**A runtime decision marked verified**

```json
// wrong
{ "id": "h7", "symbol": "notify", "status": "verified" }
// right
{ "id": "h7", "symbol": "notify", "status": "unresolved",
  "reason": "handlers is filled at boot and matched by prefix; two keys prefix order.placed",
  "candidates": [ { "file": "src/platform/notify/handlers.ts", "line": 4, "evidence": "order: pushToSlack" } ] }
```

**A `why` the excerpt does not show**

```json
// wrong: the README says so, the code retries nowhere on this path
{ "why": "Sends the receipt with three retries." }
// right
{ "why": "A leaf: the request leaves the process here, and nothing on this path reads the provider's answer." }
```

**Every line invoked**

```json
// wrong: lines 6 to 8 are the `if (!session)` arm this path does not take
{ "range": [4, 11], "invoked": [4, 5, 6, 7, 8, 9, 10, 11] }
// right
{ "range": [4, 11], "invoked": [4, 5, 6, 9, 10, 11] }
```
