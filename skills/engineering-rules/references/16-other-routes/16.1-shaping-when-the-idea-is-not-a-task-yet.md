# 16.1 [route] Shaping, when the idea is not a task yet

## Shaping (Socratic pre-task refinement)

Shaping is the idea-shaping front door to the workflow. It runs ONE Socratic conversation, 1 or 2 forking questions per turn, reflection before each following question, until the user signals intent to build. At that signal it writes a one-paragraph distillation and hands it to quick mode (4.2), the default route for any substantive prompt, as the in-chat Primary Goal & Guardrails anchor Phase 1 opens on. It writes a work-doc only on the one branch that has somewhere to put it, the user who asked for full mode by name.

The graduation handoff is into Phase 1 (6.1) of quick mode, or of full mode when the user asked for it by name. The always-on law binds throughout shaping: every question goes through the wizard tool, and nothing is edited.

---

### When to invoke

This route is picked (4.1) when the user's most recent prompt contains any of the following (case-insensitive substring match):

- `shaping`
- `let's discuss`
- `let's think`
- `what if`
- `explore the idea`
- `what do you think`
- `considering`
- `thinking about`

Do NOT invoke shaping when the user prompt already contains build-intent verbs (`add`, `implement`, `build`, `fix`, `refactor`, `ship`, `make this happen`), those route directly to quick mode (4.2), the default route for any substantive prompt; full mode takes them only when the user asks for it by name. A prompt can match both lists at once, and when it does the positive trigger wins: the build-verb block applies only to a prompt that carries none of the trigger phrases above, which is why `let's discuss adding rate limiting` shapes and `add rate limiting at 100 req/min per IP` does not. Shaping is strictly pre-task; it is not a discussion stage that runs after Phase 1.

---

### Workflow shape

Shaping runs an interactive Socratic loop until the user signals build intent. The loop has exactly three rules. Violating any rule is a workflow failure.

**Rule 1, 1 or 2 questions per turn. Never more.** Shaping is NOT the Phase 1 clarify round. Clarify batches questions to lock requirements; shaping asks 1 or 2 questions to surface a real fork in the user's thinking. Each question still goes through the wizard tool, like every question in this law (1.4): one call, one or two questions, the fork's branches as the options with the strongest first, and the free-text input the tool adds serving as the open answer. What makes shaping different from Phase 1 is the count and the purpose, not the delivery.

**Rule 2. Every question must surface a real fork.** A real fork is a choice where the two branches lead to different builds, different acceptance criteria, or different user experiences. Vanity questions ("what do you want to call this?", "what color theme?") are forbidden at this stage, those go to Phase 1 Clarify after graduation. If you cannot name the fork the question opens, do not ask it.

**Rule 3. Reflect before asking the following question.** Each turn begins with one sentence (≤25 words) that mirrors back what the user just said in their own framing. Then the following 1-2 questions. The reflection proves you read what they wrote and gives them a chance to correct a misread cheaply.

**Anti-loop guard.** If you have asked 3 or more questions in a row without the user offering new substantive information (their answers shrink to one-word affirmations, or they ask you for an opinion), surface the implicit graduation offer verbatim: *"Want me to write up what we have so far as a draft plan?"* If they say yes, graduate. If they decline, change tactic, propose a concrete option instead of asking another open-ended question.

**No work-doc during shaping.** Shaping runs WITHOUT a work-doc. The conversation transcript IS the state. Do NOT create `docs/work/.shaping-scratch.md`, `docs/work/.shaping-<slug>.md`, or any scratch path. Do NOT create the canonical work-doc until graduation fires AND the user has named full mode; on the default path graduation writes no work-doc at all. Lazy creation is locked.

---

### Graduation rule

Graduation fires when the user signals intent to build. The signal phrases (case-insensitive substring match against the user's most recent message) are:

- `let's build`
- `let's do this`
- `OK make this happen` (and the case variant `make this happen`)
- An explicit task-shaped ask of the form "now add `<feature>`" / "now implement `<change>`" / "now fix `<bug>`"

`ship it` is deliberately NOT a graduation signal. Phase 1's handover question (6.4, Q4) recommends the unreviewed straight-to-main option only when the user's prompt carries that literal phrase, and shaping hands off in the same turn to a flow that runs that same question, so a user who meant "start building" would be steered into a merge nobody read. Do not add it back.

On graduation, execute these three steps in order. Do not reorder. Do not skip.

**Step 1. Distill.** Write a one-paragraph distillation (≤120 words) of what the shaping clarified. The paragraph names: the user's underlying goal, the chosen approach (the surviving fork branch), the constraints surfaced during the conversation, and any explicit non-goals. The distillation is for whoever picks the work up next, and it must be self-contained enough that someone who did not see the shaping transcript can read it alone and understand the locked decisions. These four elements map straight onto the Primary Goal & Guardrails anchor (goal → North-Star Goal; approach → In-Scope; constraints → Guardrails; non-goals → Out-of-Scope).

**Step 2. Seat the distillation as quick mode's anchor.** Shaping graduates into quick mode (4.2). **Quick keeps no work-doc**, so the distillation does not reach disk: it becomes the in-chat Primary Goal & Guardrails anchor that Phase 1 opens on. Print it in the handoff turn under a `## Primary Goal & Guardrails` heading, carrying the four fields Step 1 produced, so Phase 1 inherits a filled anchor to confirm instead of restating a one-line goal from scratch (5.2).

**Say the tradeoff in that same turn rather than papering over it.** A shaped idea that lands in quick **cannot be paused and resumed across sessions**. The anchor lives in the transcript, quick's phase ledger is session-local by contract, and nothing about either survives a restart. A user who wants the shaping to outlive the session asks for full mode by name, and that is the branch below. Do not promise a work-doc on the default path, and do not write one to keep the promise.

**The full-mode branch, and only when the user named that mode.** Full mode has a work-doc to write into, so on that branch shaping writes it. Create it at `<project>/docs/work/<YYYY-MM-DD>-<slug>.md` (date is today; slug is `kebab-case`, ≤6 words, derived from the distilled goal). Use the skeleton from 7.2. Fill in frontmatter `slug`, `title`, `status: clarifying`, `type` (best-fit from `feature` | `fix` | `refactor` | `revamp` | `redesign` | `debug` | `research`), `created`, `project`. **Keep the template's `## 0. Phase ledger` block as the first section of the body, with every item open (`- [ ]`).** Whoever creates the work-doc writes the phase ledger (5.1) into it, and on this path that is shaping; Phase 1 adopts the block and Phase 2 step 1 confirms it. Do not tick an item and do not set one in progress, shaping runs no phase. Contract: 5.1. Then insert a new H2 section titled `## Shaping Provenance` placed directly below `## 0. Phase ledger` and above `## 1. Original ask`. The Shaping Provenance block contains the one-paragraph distillation from Step 1 and nothing else. Then populate the template's `## Primary Goal & Guardrails` section from that same distillation, so Phase 1 inherits a seeded anchor to confirm rather than build from scratch. **Then publish the file as a page, write the link it returns into frontmatter `page_url`, and say that link once in the handoff turn**, where the runtime can. The rule is the one this branch already runs on for section 0: whoever creates the work-doc does the thing that has to happen at its first save, and on this branch that is shaping rather than Phase 2. The user gets one link at creation and keeps it for the rest of the task, because every later ledger tick republishes the same path. Phase 2 step 1 reads `page_url` back and confirms it instead of publishing again, so the file is published once on either path and never twice on this one (7.1 step 1, 7.3). Where the runtime has no publish tool, leave `page_url` at the `null` the template ships, say so in one line with the path, and hand off anyway: no part of the handoff waits on a link.

**Step 3. Hand off.** On the default path, end the shaping turn with a single explicit handoff line: *"Shaping done, handing off to quick mode. The Primary Goal & Guardrails anchor is above; quick keeps no work-doc, so this does not survive a restart."* Then begin Phase 1 (6.1) from its step 1, opening the ledger. On the full-mode branch, first print the `## 0. Phase ledger` block in chat, all items open, so the shaped task reaches Phase 1 with a visible tracker instead of none, then end with *"Shaping done, handing off to Phase 1 (Clarify) in full mode. Work-doc created at `<path>`."* and begin 6.1. Phase 1 flips its own ledger item to in progress; shaping never does. The handoff is the terminal action of shaping.

**Never create two work-docs.** This binds the full-mode branch, the only branch that writes one. If a work-doc already exists for the same slug, append a numeric suffix (`-2`, `-3`) to the slug. Never write to two paths in one graduation.

### Anti-rationalizations

These thoughts mean STOP and apply the listed reality.

| Thought | Reality |
|---|---|
| "I'll just create the work-doc now since we have enough" | Lazy creation is locked, and on the default path there is no work-doc at all. Graduation seats the distillation as quick's in-chat anchor; a file written anyway forks state between transcript and disk. |
| "I'll just create the file, Phase 2 step 1 writes section 0 later" | On the full-mode branch the file exists before Phase 1, so Phase 2 has nothing left to create. Whoever creates the work-doc writes the ledger into it. Leave it out and the task runs with no durable tracker. |
| "This idea got big during the shaping, so it should graduate to full mode" | Size is not a routing signal and never was. Shaping graduates into quick like every other build ask, and full mode runs only when the user names it. Reading a big idea as an implied request is the auto-promotion the user ruled out. |
| "The user will want to resume this later, so I'll write a work-doc to be safe" | Then say so and let them ask for full mode. A work-doc quick never reads is a file nothing updates, and it will disagree with the tree by the second turn. |
| "The user said something vaguely build-shaped, that's a graduation signal" | Graduation signals are the explicit phrase list in the Graduation rule. Vague build-shape is not on the list. Ask one more reflecting question instead. |
| "I'll ask 8 questions in one turn to save time" | Rule 1 caps at 2 questions per turn. Batched questions kill the Socratic reflection loop. |
| "Shaping can run *after* Phase 1 if they want more discovery" | Shaping is strictly pre-task. Once Phase 1 runs, the discovery channel is the Clarify wizard. Re-entering shaping mid-flow is forbidden. |
| "I'll write a quick scratch file at `docs/work/.shaping-<slug>.md` to track ideas" | No scratch files. The transcript is the state. Scratch files violate the one-work-doc rule. |
| "The user asked me 3 questions back-to-back, I'll just answer and keep shaping" | The anti-loop guard fired. Surface the verbatim graduation offer: *"Want me to write up what we have so far as a draft plan?"* |
| "I'll ask a vanity question to keep the conversation warm" | Every question must surface a real fork. If you cannot name the fork, do not ask the question. Propose a concrete option instead. |

### One-line summary

Reflect → ask 1-2 forking questions → loop until the user signals build → distill → seat the distillation as quick's in-chat Primary Goal & Guardrails anchor, saying plainly that it will not survive a restart → hand off to Phase 1 in quick mode. Only when the user named full mode: write the work-doc with an open phase ledger (section 0) + a Shaping Provenance block + seeded anchor, print the ledger, and hand off to Phase 1 in full mode instead.
