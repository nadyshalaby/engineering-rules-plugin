# 16.5 [reference] Audit carve-outs

An auditor that flags a documented exception trains its user to ignore it. Encoding the
carve-outs IS the core feature, not an afterthought. Two kinds: **path carve-outs** (which
files a rule skips) and **semantic floors** (which constructs a judgment pass must leave
alone). Verify per project which apply by checking for the files, dirs and config; never
assume one project's layout. The law scout (9.5) and the codebase audit (16.3) both honor
this file.

## Path carve-outs

| Exempt set | Rules waived | Detect by |
|---|---|---|
| Test files (`*.test.*`, `*.spec.*`, `*_test.*`, `*_spec.*`, `test_*`, `**/tests/**`, `**/__tests__/**`, `**/test/**`, `**/spec/**`) | non-null, inline-type, bare-error, `clean.removed-comment`, `clean.debt-marker`; suppression ONLY for a `@ts-expect-error` carrying a WHY comment (1.1's sole exception), every other suppression still fires | path glob |
| Prose (`*.md`, `*.mdx`) | `clean.removed-comment`, `clean.debt-marker`, and the construct bans (`ban.suppression`, `ban.empty-catch`, `ban.bare-error`, `ban.non-null`, `clean.debug-artifact`), because a markdown file only quotes a token, in a code span or a fence; `cap.file-lines` and `sec.hardcoded-secret` still fire | path glob |
| Append-only records (`CHANGELOG.md`, `HISTORY.md`, `NEWS.md`, named exactly by the project) | `cap.file-lines` ONLY | exact basename |
| Generated (`*.gen.ts`, `*.d.ts`, `*.generated.*`, `routeTree.gen.ts`, any file whose header says `@generated` / `DO NOT EDIT`) | ALL | path glob + generated-header comment |
| Migrations (`**/migrations/**`) | ALL (off-limits to refactor) | path glob |
| Frozen or vendored dirs (`template-reference/`, anything the project's `tsconfig` or lint config excludes) | ALL | dir name; confirm in the exclude lists |
| Dependencies and build output (`node_modules`, `dist`, `.next`, `build`, `target`, …) | ALL (not walked) | dir name |
| Inline-type ban, mechanical tier | applies ONLY to `*.service.*`, `*.controller.*`, `*.routes.*`, `*.middleware.*`, `*.guard.*` (9.5 scans exactly those); the semantic tier covers every other implementation file (2.2, "How this table meets the inline-type ban") | basename glob (the rule's domain, not a waiver) |
| Focused and skipped tests (`test.focused`, `test.skipped`) | exist ONLY in test files (the first row's globs); outside them a `.only` or `.skip` is a method on something else and never fires | path glob (the rule's domain, not a waiver) |
| Debug artifacts (`clean.debug-artifact`) | `debugger` and its analogs fire on every production path; the `console.*` row fires ONLY in domain roles (`*.service.*`, `*.use-case.*`, `*.usecase.*`, `*.repository.*`, `*.validator.*`, `*.job.*`, `*.worker.*`), so a CLI entry, a script, a component or the logger module itself never trips it | basename glob (the rule's domain, not a waiver) |
| Non-null `!` (`ban.non-null`, the `!` row) | fires ONLY in files whose language reads a postfix `!` as non-null: `*.ts`, `*.tsx`, `*.mts`, `*.cts`, `*.js`, `*.jsx`, `*.mjs`, `*.cjs`, `*.vue`, `*.svelte`, `*.swift`, `*.kt`, `*.kts`, `*.cs`, `*.dart`; a Ruby bang method, a Rust `vec![` or a shell `$!` never trips it; the `!!`, `.unwrap()` and `.expect(` analogs run on every path | extension (the rule's domain, not a waiver) |

**A waiver is from a RULE, never from the SCAN.** Every row above is applied at the last
step, after the file has been walked to, opened, read and checked. The file stays counted as
scanned and every rule NOT named in its row still fires against it; only the matching finding
is dropped. A carve-out applied earlier, by keeping a path out of the scanned set, reads as
coverage in the report, and telling that apart from a real clean scan is exactly what the
coverage counters in 16.7 exist to make possible.

### Why test files waive five rules, narrow a sixth, and carry two of their own

The first three are doctrine carve-outs: a test may legitimately do the banned thing, a `!`
on a fixture, an inline type, a bare `Error`. The two hygiene markers are waived for a second
reason: a fixture asserting that a scanner detects `// TODO` has to contain `// TODO`. **The
residual, written down:** a genuine ownerless debt marker in an ordinary test file reaches
only the semantic pass. Both rules are `low` severity `cleanup`, and a false positive nobody
can rewrite away trains its reader to skim the whole report, so that is the cheaper half of
the trade.

The suppression ban is NOT waived, only narrowed, because 1.1 names exactly one allowed
suppression: a `@ts-expect-error` over deliberately invalid input, with a comment saying WHY.
A `@ts-ignore`, an `eslint-disable` or a `biome-ignore` in a test hides a real type error or
a real lint failure in the code that proves the code, and stays a finding. And two rules run
ONLY in test files: `test.focused`, because a committed `.only` silently drops the rest of the
suite, and `test.skipped`, because a disabled test with no ticket is a debt marker in test
form. Those two are the test file's own bans, not carve-outs. A test file is named by every
language's convention, the globs in the first row, so a Go `_test.go`, a Ruby `_spec.rb`, a
Python `test_*.py` and a JVM `src/test/` tree are test files too: their skip tokens fire and
their fixtures get the same waivers.

### Why prose waives the hygiene markers and the construct bans

The two markers require a comment opener, and markdown has none of them: `#` opens a heading
there, a leading `*` opens a bullet, and `//` or `/*` reach a `.md` file only inside a code
span, where the pattern is being quoted in order to define it. The construct bans are waived
for the same reason: a `.md` never executes, so an `@ts-ignore` or a `catch (e) {}` in it is
a token being taught, quoted or banned, and `SKILL.md` 1.1 itself is the canonical example.
**The residual:** a `# TODO` heading in a design doc is arguably real debt, and a README that
teaches `@ts-ignore` is arguably a documentation defect; both drop to the semantic pass. The
file cap and the secret rows are never waived for prose: a 600-line reference is still over
the cap, and a credential pasted into a README is still a credential.

### Append-only files, waived from the cap and nothing else

A changelog grows by one entry per release and shrinks for no reason at all. "Split by
responsibility", the remedy the 500-line cap exists to force, has nothing to act on. So
append-only records are waived from `cap.file-lines` and from that rule only, and the
project names them exactly, never by pattern: `*.md` would take every reference with it.

## Runtime detection, before scanning

- **Generated files**: grep the first lines of candidates for `@generated`, `eslint-disable`,
  `DO NOT EDIT`, `This file is auto-generated`. Pass matches to the scanner as extra
  generated globs.
- **Frozen and vendored dirs**: read `tsconfig.json` `exclude` and the lint ignore file;
  anything excluded from typecheck or lint is excluded from the audit too.
- **Schema files**: `**/schema.ts` and `**/*.schema.ts` are off-limits to magic-literal
  extraction (schema-builder arguments). They are not scoped-type files, so the inline-type
  ban already skips them.
- **The project's own ban list**: a documented ban-patterns file (grep-ERE, one per line),
  handed to the scanner as `ban.custom`.

## Semantic floors, the judgment pass must honor these

These are the DO-NOT-EXTRACT and DO-NOT-FLAG rules for the judgment pass (16.6). A pass that
flags one of these is producing noise. Hand this list to every relevant pass. They restate
the extraction floors in 2.1 with the audit's detection detail.

### Magic-literal extraction floors, leave these inline

- Identity values: `0`, `1`, `-1`, `''`, `true`, `false`.
- Utility-CSS and class strings.
- Schema-builder arguments: `z.literal(...)`, `z.enum([...])`, and equivalents.
- Object keys; SQL fragments; template literals containing `${…}`.
- Import specifiers; regex literals; union-type member literals.
- ORM schema defaults. **`**/schema.ts` and `**/migrations/**` are entirely off-limits.**
- Lint-ban tokens themselves (`biome-ignore`, `@ts-ignore`, …) stay literal; they ARE the
  strings the bans grep for.

### Frontend-specific floors, when the project is a typed frontend

- **Typed router paths** consumed by `createFileRoute`, `<Link to>`, `navigate`, `redirect`,
  `validateSearch` stay inline; extracting breaks route type-inference. HTTP client
  endpoint paths ARE extractable.
- **The hot-reload carve-out, narrowed.** A component that declares its own inline
  `const FormSchema = z.object({…})` may keep that schema's inferred value type and the
  field-prop interfaces referencing it in-file, because relocating ONLY the type trips
  `react-refresh/only-export-components`. The clean resolution that satisfies the
  one-construct rule is to relocate BOTH the runtime schema and its inferred type to
  dedicated files, so the component exports no runtime value. The inline carve-out applies
  ONLY when a project deliberately keeps the runtime schema in-file for locality; otherwise
  an inline component schema IS a finding (`scope.one-construct`). Every other type still
  leaves the implementation file.
- `routeTree.gen.ts` and its equivalents are generated: never hand-edit, never flag.

### Bare-error nuance

`ban.bare-error` is "in DOMAIN code" (`SKILL.md` Definitions). The scanner flags every
`throw new Error(`, every `throw Error(`, every thrown literal and every `reject(new Error(`
because it cannot tell domain from a script, a CLI or a test. In the judgment pass and in
remediation, confirm the file is domain code before treating it as a real violation; a
one-off script throwing `Error` is a weak finding. The `console.*` half of
`clean.debug-artifact` carries the same nuance, which is why 9.5 scans it only in the domain
roles named in the table above.

## When a project deliberately relaxes a rule

Stricter wins (`SKILL.md` Precedence), so a project may TIGHTEN but not relax a ban. If a
maintainer states an explicit, coherent exception ("we allow `console.error` in the frontend
logger"), record it as a **waiver** in the report rather than silently dropping the finding.
A waiver is auditable; a silent skip is not. A waiver on a Critical finding (a secret, an
auth bypass) is not a waiver; it is a finding the user has chosen to ship, and the report
says so in those words.
