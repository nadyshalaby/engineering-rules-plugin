# 12.7 [check] Quality, layering, plan and scope

**The floor. Two lenses over one read, and it is never sliced** — it applies to every touched
file and re-judges every scout row, so no part of the change is safe to withhold from it.

## Lens one: quality, layering and placement

1. **The hard caps (1.1)**, on every touched file: function length, parameter count, nesting depth,
   file length.
2. **The zero-tolerance bans**: lint, type or coverage suppressions, non-null assertions in
   production code, empty catches in every form, bare error throws and thrown literals in
   domain code, inline types of two or more properties in a scoped module, focused or
   unticketed skipped tests, debug artifacts.
3. **The file-organization law (2.2)**: is every new file in the right place, named correctly, with
   its export matching its name? Does every import obey the direction table? Any reach-in
   past a feature's public surface, any orphan folder, any second layout?
4. **DRY, with the search shown.** Every symbol the diff added, against what already
   existed: re-run the reuse search the stage pasted (9.1) and search again yourself. A new
   function, type, constant, schema or component with an existing equivalent is a finding
   naming the target (`style.reuse`, `style.dry`); a duplication finding requires the
   reusable target to actually exist, named. The same 3+ lines twice inside the diff is a
   finding too.
5. **Leftovers, both directions (13.1, classes 1 to 5 and 9).** Every symbol the diff added
   has a caller; every symbol whose last caller, import or reference the diff removed is
   deleted with it, along with the types, constants, fixtures, flags, config keys, env vars,
   translations and doc lines that served only it; the dead code that was already in a
   touched file is gone in its own cleanup commit, whose zero-reference proof you re-run per
   symbol, or was offered under a guardrail 13.2 class 10 names; no unused import, debug
   line, commented-out block, `// removed:` marker or ownerless debt marker; no reference the
   change made stale. Each leftover is a finding citing its row (`scope.dead-code`,
   `style.structure.unused-import`, `clean.debug-artifact`, the `clean.*` rows in 16.4). A
   cleanup commit that deleted a symbol the guardrails protect is a Critical finding.
6. **The semantic tier no scan reaches**: one construct per file, controller purity, single
   responsibility, reuse and generalization, SOLID and YAGNI, the clean-code catalog's judged
   rows (3.4) for the domains the touched code has, each finding citing its
   `style.<domain>.<slug>` and its severity, and test coverage against the test-scenario
   catalog's domains — only the domains the touched code plausibly has.
7. **Re-judge every row the law scout (9.5) staged.** Confirm or dismiss each, with a reason.
8. Quote the rule sentence verbatim in every finding, and cite `file:line`.

## Lens two: plan, scope and drift

8. Every acceptance criterion, against the change: is there a hunk that actually covers it?
9. Every ticked task, against the change: is there a hunk that actually covers it?
10. Every file the change touched, against the plan: is there a task that authorized it?
11. Every answer in the clarifying Q&A: did the change do something the user ruled out?
12. The changelog entry: present, and matching what actually shipped?
13. The goal anchor (5.2): does the change still serve the Primary Goal, and did a Guardrail move?

## The completeness section, and it is mandatory

Close with `## What the review did not reach`, answering all six:

1. What did no check open?
2. What check could not have failed — passed for the wrong reason?
3. What claim was asserted but never verified?
4. What new gate has no regression test behind it?
5. What number did nobody re-measure?
6. What file in the change did no lens read?

**File what you find here as findings with severities, not as a note.** A completeness
section that lists gaps and files nothing has reported nothing.
