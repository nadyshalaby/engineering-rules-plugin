# 12.3 [check] Security and correctness

**Reproduce, do not reason.** A vulnerability you argued your way to is a vulnerability you
can argue your way out of. Find the reachable entry point, or do not file it.

## Method

1. Read the whole change once for orientation, then again for this lens alone.
2. For every changed path, ask **who can reach this, with what input, holding what
   permission** — and answer it from the code, not from what the surrounding layer is
   assumed to do.
3. Walk all ten domains against the change:

| Domain | What to look for |
|---|---|
| Authentication | Session lifecycle, token issue and expiry, refresh, logout, credential comparison. |
| Authorization | Missing route guard, object-scope errors on nested resources, mass assignment, IDOR, over-broad scopes. Any state-changing operation reachable with no ownership check on the path to it. |
| Injection | String-built SQL, shelled-out commands, path traversal, unescaped output, dynamic code evaluation. |
| Secrets and PII | Credentials in source, keys shipped to a client bundle, personal data in logs. |
| Migrations | Destructive change with no guard, non-idempotent steps, no reversible path. |
| Concurrency | Read-modify-write on security-relevant state with no lock or transaction. |
| CORS and SSRF | Permissive origins, outbound requests to an unvalidated URL. |
| Cryptography | Weak or homegrown primitives, missing salt, predictable randomness, comparison that leaks timing. |
| Supply chain | New dependency, changed lockfile, build or CI step that fetches at run time. |
| Error handling | A catch that swallows and continues, a default that fails open. |

4. **A destructive operation with no visible guard is the canonical finding.** Do not assume
   an upstream caller checks. File it, and name where the guard belongs.
5. Cite the catalog ID, the standard where one applies, and the `file:line` in the changed
   code.

## Verification

1. Did you name a concrete reachable entry point for every finding? (yes / no)
2. Did you check all ten domains, and say which had no surface in this change? (yes / no)
3. Is every finding citing a catalog ID and a `file:line`? (yes / no)
4. Did you check the code rather than assume a guard exists upstream? (yes / no)
5. Did you say what this check did not reach? (yes / no)

## Severity

- **Critical** — exploitable now, by someone who can reach the endpoint.
- **Important** — weakened posture, or exploitable behind another condition.
- **Minor** — hardening that costs little and is worth doing.
