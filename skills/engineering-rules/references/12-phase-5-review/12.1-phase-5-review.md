# 12.1 [phase] Phase 5, Review

**Both scouts over the whole diff, five checks over the change, then a challenge round, then one fix pass, then the triad. Then stop.** Runs in full in every mode. Read 12.2 before building the file list, and each check's file (12.3 to 12.7) as you open it.

## The scope

The change under review is `base..head` — everything this task added, changed or deleted,
excluding the work-doc itself. The work-doc is the ruler the change is measured against and
cannot also be part of what is measured.

Build the file list once, up front (12.2), and record which check read which path in the
coverage ledger. A path in the diff that no check opened is itself a finding.

**Before the first check opens, run both scouts** (9.4, 9.5) over the whole touched scope
with run-point id `phase-5`. Their staged rows enter the decision table (12.9); the
performance check re-judges the perf rows and the quality-and-plan check (12.7) re-judges the law
rows. Neither check may accept a scout row on the scout's word, and neither may leave one
unjudged.

**No diff is too small or too "config-only" to review.** A one-line change to config is
exactly the change that breaks startup (11.3). The only ask that skips Phase 5 is the
trivial ask, which never opened the ledger.

## The five checks, each closing before the next opens

| Check | Looks for |
|---|---|
| **Security and correctness** | Auth flows, permission boundaries, injection, secrets and PII, migration safety, race conditions, CORS and SSRF, cryptography, dependency risk, error handling that fails open. |
| **Performance** | Queries in loops, algorithmic cost on hot paths, unbounded growth, blocking I/O, render thrash, missing pagination or batching, serialization waste, bundle bloat. |
| **Design conformance** | The committed design spec: hardcoded values where a token exists, missing component states, contrast and focus regressions, the spec's own list of things it must never look like. **Runs only on a change with a UI surface, and is omitted rather than folded when there is none.** |
| **Cross-module coherence** | Every symbol that crosses a boundary, compared producer against consumer: field names, optionality, units, timezones, identifier space, ordering, error shape, and wiring completeness. **This one deliberately reads code outside the diff.** |
| **Quality, layering, plan and scope** | The code-quality doctrine (2.1) and the file-organization law (2.2); every scout row re-judged; and the change against the plan — acceptance criteria with no covering change, files touched with no authorizing task, scope the Q&A ruled out, and drift against the goal anchor (5.2). |

**Each check finishes and files its findings before the next one starts.** They are separate
passes on purpose: a concern read alongside another concern gets the leftovers of the
attention, and that is measurably worse than reading it on its own.

**The last check never gets sliced.** It applies to every touched file and re-judges every
scout row, and it closes with a completeness section — see its own section for what that
section must ask.

## Then challenge the findings

Before spending a single edit, run the finding challenge (12.8) over every finding at every
severity. Its rules are asymmetric on purpose and they are in its own section; the one that
matters most here is that **the default is to keep the finding.** Uncertainty is never a
refutation.

## Then fix, once

| Severity | Action |
|---|---|
| **Critical** | Fix now. Never deferred. |
| **Important** | Fix now. Deferred only with explicit user sign-off, recorded. |
| **Minor** | Fix too. Deferred to the retrospective only with explicit user sign-off, never by default. |

Group findings that touch the same file and fix them in one pass, in order, each fix inside
the file allowlist and obeying 9.2. Non-trivial fixes (two or more reasonable shapes) go
through one batched wizard question per finding or tight cluster before writing. After the
last fix, run the triad on the touched scope; green closes the phase. A `defer` on an
Important or Minor finding needs the user's sign-off through the wizard tool, recorded in
the decision table with the reason.

## One round, and that is the cap

**One review, one challenge, one fix pass. Then the phase ends.**

What that gives up, stated plainly: the review describes the change as it stood when it was
read, not after the fixes, so the last fixes ship unreviewed. That risk is real and this cap
prices it rather than removing it. The alternative — reviewing until nothing is found — has
no stopping condition, and every round after the first buys less than the one before. A
defect a fix introduces is fixed in the same fix sequence; anything still unresolved when
the fixes are done goes to the user as a written list, never as another round.

Then record the final table in the Sprint Review (in chat, in quick mode), tick Phase 5,
re-print the ledger, and read 13.1.
