# 12.2 [reference] Review coverage

## Review coverage, and proving it

Phase 5 has to end with a defensible answer to one question: **was every changed
file actually read by something that could judge it?** Coverage is the guarantee.
How the reading is organised is not part of the guarantee, and this section says
nothing about it.

### Every changed path is claimed

Build the list once, at the start of the phase:

```
git diff --name-only <base>..<head> -- . ':(exclude)docs/work/*'
```

Then assign each path to every check whose surface it touches. A path can belong
to several, and most belong to at least two. **A path you cannot confidently
classify goes to the quality-and-plan check (12.7)**, which is reading everything
anyway, so an unclassifiable file is never an uncovered file.

**The quality-and-plan check is never narrowed.** It applies its semantic tier to
*every* touched file and re-judges *every* law-scout row. There is no subset of
the diff it does not need. It is the floor under every other economy this phase
makes, and treating it as narrowable deletes coverage rather than saving effort.

### Reading wider than you judge

The path list bounds what you **diff**, not what you may **read**. When a finding
needs the contract around a change, the caller, the type it returns, the guard
above it, open that file even if it is not in the list, and say in the finding
why you opened it. Never widen the diff itself.

### An empty list is not a clean verdict

A check whose path list comes out empty has nothing to review. Do not run it, and
write that down with the reason. **Zero findings over zero files is not a verdict
and must never be counted as one.** The same holds for a list that is non-empty
until the exclusion removes every path in it: say so in the report.

### Why `docs/work/` is excluded

The work-doc is the ruler the diff is measured against, and it cannot also be the
thing measured. Phase 5 writes its coverage ledger and its decision table into
that file while the review is running, so a check that graded the work-doc would
be grading the record of its own grading, and every entry the phase made would
file a finding against the phase.

Nothing about the work-doc's accuracy goes unchecked by this: the
quality-and-plan check still reads it in full as an INPUT, and still flags any
file in the diff with no authorizing task entry behind it.

### The coverage ledger

One row per changed path. This is the artifact that makes "every file was
covered" checkable instead of asserted. Write it at the start of the phase and
fill the verdict column when the reports come back.

```
| path                | checks read it                        | verdict    |
|---------------------|---------------------------------------|------------|
| src/auth/session.ts | security, quality-and-plan, coherence | clean      |
| src/ui/Button.tsx   | quality-and-plan, design conformance  | 2 findings |
```

The verdict is filled **once**, and it is only ever about the bytes that were
read on this round. Nothing carries over from an earlier round, because there is
no earlier round: **one review, one challenge, one fix pass**, and then the phase
ends. That cap counts rounds, not checks, and it holds however much the fixes
changed. Its cost is stated in 12.1.

### What a silent check does not prove

A check that reports no scope line has not thereby proved it read everything. The
only proof of coverage is the ledger above, one row per changed path, filled in.
A report that says "clean" without a ledger row behind each path is an assertion,
and an assertion is what this phase exists to replace.
