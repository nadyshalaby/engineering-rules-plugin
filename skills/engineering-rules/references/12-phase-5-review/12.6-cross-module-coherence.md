# 12.6 [check] Cross-module coherence

**Walk out of the change.** This is the one check that deliberately reads code the change
never touched, because a seam is exactly what nobody looked at.

## Method

1. List every symbol the change added or altered that **crosses a boundary**: an exported
   function, a type, a response shape, an event payload, a column, a route, a config key.
2. For each one, find **every** producer and **every** consumer — including consumers that
   are not in the diff — and compare them on five axes:

| Axis | Disagreement to find |
|---|---|
| **Shape** | Field names, optionality, nullability, the set of enum members. |
| **Semantics** | Units, timezones, identifier space, ordering guarantees, range bounds, inclusive vs exclusive. |
| **Errors and lifecycle** | One side throws, the other expects `null`; one returns a result object, the other unwraps; cleanup that one side assumes and the other never does. |
| **Duplication** | Two definitions of one concept where a shared one should have been reused. |
| **Wiring** | A route defined but not registered; a handler written but not subscribed; a component built but not mounted; a column added but never read; a flag defined but never checked. |

3. **Cite `file:line` for both sides of every disagreement.** A coherence finding with one
   side cited is an assertion.
4. Wiring completeness is checked by finding the registration site, not by trusting that
   one exists.

## Verification

1. Did you list every boundary-crossing symbol the change touched? (yes / no)
2. For each, did you find consumers outside the change as well as inside? (yes / no)
3. Does every finding cite `file:line` on both sides? (yes / no)
4. Did you verify each new route, handler, component and column is actually wired and read? (yes / no)
5. Did you say what this check did not reach? (yes / no)
