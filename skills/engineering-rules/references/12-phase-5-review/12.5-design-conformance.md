# 12.5 [check] Design conformance

*Runs only on a change with a UI surface. When there is none, it is omitted and that is
recorded — never folded into another check.*

**Audit the change against the project's committed design spec, its composition plan, and
the AI-tell catalog.**

## Method

1. Open the project's design spec. If none exists, fall back to the frontend design law (15.1) and
   say that is what you are auditing against. Open the composition plan (15.22) when the change
   has a marketing surface, and the read and the dials (15.20) the surface was built under.
2. Take the design scout's Phase 5 table (15.29, run-point id `phase-5`) from the hand-over and
   re-judge every `staged` row: confirm it as a finding with its `tell.*` id and the catalog's
   default severity (15.24), move the severity one level with the reason stated, or dismiss it
   with a one-line counter-citation against the row's guard. No row is accepted on the scout's
   word, and none is left unjudged.
3. For every changed UI file, check:

| Look for | The finding |
|---|---|
| A raw color, size, radius, or shadow value where a token exists | Name the exact replacement token. |
| A type size outside the spec's scale | Name the role it should use. |
| A component missing a state the spec requires | Name the missing states: hover, focus, active, disabled, loading, error, empty. |
| Anything on the spec's own "don'ts" list, or in the direction profile's anti-tells (15.7 to 15.18) | Quote the don't. |
| Contrast below AA, or a removed focus indicator | Give the measured ratio. |
| A physical property where the spec requires a logical one | Name the logical equivalent. |
| A generic-looking font stack or gradient the spec bans | Quote the ban, with its `tell.*` id (15.24). |
| A judged tell the scout cannot see (15.24): hero overflow, the reflex hero, three equal cards, a theme flip, cards inside cards, an empty bento cell, a split header, a component with only its happy-path state | Cite the id and the catalog's fix direction. |
| A composition-plan breach on a marketing surface (15.22): a section whose layout family differs from the plan, the eyebrow budget exceeded, the zigzag cap broken, a nav on two lines at 1024 | Name the plan line it breaks. |
| Copy that fails the self-audit (15.23): a dash used as a thought break, a filler verb, a generic name, a fake number, broken grammar, a placeholder token | Quote the string and give the rewrite. |
| Imagery that is not real (15.23): a hero with no visual, a screenshot built from divs, a placeholder-service URL not listed in the update log, a hand-drawn icon path | Name the slot and the asset the update log must list. |
| Motion outside the discipline (15.25): a window scroll listener, a transition on a layout property, a claimed motion dial with nothing moving, no reduced-motion path | Cite the id; name the recipe or the removal. |
| A guardrail breach (15.26): `h-screen` or `100vh`, an arbitrary `z-index`, an import with no manifest entry, blur or grain on a scrolling layer, a multi-column layout with no under-768 collapse | Name the rule and the replacement. |
| An inherited design system bypassed (15.21): a hand-rolled component where the system ships one, a literal value beside a system token | Name the system token or component. |

4. Re-run the design pre-flight (15.30) against the reviewed diff at 375, 768 and 1440px, and in
   both modes where both ship. Every box the implementer ticked is re-ticked here from the
   evidence or turned into a finding.
5. Where reference frames of the intended design were supplied, or the page was built
   image-first (15.31), render the touched screen and compare side by side; drift from the
   reference set is a finding with the section named.
6. **Name the exact replacement token, value or fix direction for every finding.** A design
   finding with no replacement is a complaint.

## Verification

1. Did you open the project's committed spec, or say that none exists, and the composition
   plan where the change has a marketing surface? (yes / no)
2. Did you re-judge every staged design-scout row, citing its `tell.*` id? (yes / no)
3. Does every finding name its exact replacement token, value or fix direction? (yes / no)
4. Did you check every required state on every touched component? (yes / no)
5. Are the contrast numbers computed rather than estimated? (yes / no)
6. Did you re-run the pre-flight at the three widths and in both modes? (yes / no)
7. Did you say what this check did not reach? (yes / no)
