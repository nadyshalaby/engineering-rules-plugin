# 12.5 [check] Design conformance

*Runs only on a change with a UI surface. When there is none, it is omitted and that is
recorded — never folded into another check.*

**Audit the change against the project's committed design spec.**

## Method

1. Open the project's design spec. If none exists, fall back to the frontend design law (15.1) and
   say that is what you are auditing against.
2. For every changed UI file, check:

| Look for | The finding |
|---|---|
| A raw color, size, radius, or shadow value where a token exists | Name the exact replacement token. |
| A type size outside the spec's scale | Name the role it should use. |
| A component missing a state the spec requires | Name the missing states: hover, focus, active, disabled, loading, error, empty. |
| Anything on the spec's own "don'ts" list | Quote the don't. |
| Contrast below AA, or a removed focus indicator | Give the measured ratio. |
| A physical property where the spec requires a logical one | Name the logical equivalent. |
| A generic-looking font stack or gradient the spec bans | Quote the ban. |

3. Where reference frames of the intended design were supplied, render the touched screen
   and compare side by side.
4. **Name the exact replacement token for every finding.** A design finding with no
   replacement is a complaint.

## Verification

1. Did you open the project's committed spec, or say that none exists? (yes / no)
2. Does every finding name its exact replacement token or value? (yes / no)
3. Did you check every required state on every touched component? (yes / no)
4. Are the contrast numbers computed rather than estimated? (yes / no)
5. Did you say what this check did not reach? (yes / no)
