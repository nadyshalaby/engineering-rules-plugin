# 5.1 [reference] The phase ledger

**A visible, ordered checklist that forces the phases to run in order and makes a forgotten
step impossible to hide.** It is the order-enforcer for the whole task. Read this file at
task start in every mode.

## Why it exists

Prose rules like "do not skip Phase 2.5" and "archive before the summary" are soft; a model
under load drops them. The ledger turns each rule into a checkbox with an ordering law. You
cannot reach a later checkbox while an earlier one is open, so skipping a phase or forgetting
the archive step becomes visible and blocked, not silent.

## Two layers, do not confuse them

| Layer | Lives in | Scope | Survives a session? |
|---|---|---|---|
| **Sprint Backlog** | the work-doc (full mode) | task-level, one line per task | Yes, in full mode |
| **Phase ledger** | `## 0. Phase ledger` of the work-doc in full mode; the printed block in quick mode | phase-level, one line per phase | Full mode yes; quick mode no |

The Sprint Backlog tracks *what code work* is left. The phase ledger tracks *which phase*
you are in and forbids running them out of order.

## Substrate, where the ledger lives

**Primary.** The runtime's todo tracker, when it exposes one and it can hold a whole ledger.
**Fallback.** A markdown checklist printed in chat. Check at task start rather than assuming
either way, and never drop the ledger over a missing tool.

On Claude Code the tracker is the `Task` family (`TaskCreate`, `TaskList`, `TaskUpdate`,
`TaskGet`), gated on `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in the environment or a `settings.json`
`env` entry; there is no `TodoWrite`, and the tools arrive deferred, so a name absent from the
tool list may still be one tool-search away. **Where it is present it is still not a whole
ledger:** its list is flat, and a completed item is reaped from it, so a tracker asked to show
"3 of 10, Phase 4" cannot show the three that are done. Use it to drive the in-progress item
if you like; the printed block below stays the record, because printing every item every time
is the part that makes a skipped phase visible.

**Name the substrate once, at the first print, in one line:**
`Ledger substrate: printed block (no todo tracker in this session).` or
`Ledger substrate: todo tracker.` Never repeat it; a substrate does not change mid-task.

**Helper availability rides the same line, and is recorded the same once** (1.8):
`Helpers: available.` or `Helpers: unavailable, every shape runs in this session.` Probe the
runtime once at task start; the answer is a finding about this session, not a preference, and
the refusal below is checked against it. Recording `unavailable` without probing is a false
claim and 1.5 governs it.

**In full mode the durable copy is the work-doc**, on either substrate. A tick is an edit to
`## 0. Phase ledger` in `docs/work/<slug>.md` plus a chat re-print, and the file edit comes
first. A todo-tracker tick does not touch the file, so it owes the same edit the printed
block does. In the same edit, advance frontmatter `status` (and `current_task` where the
phase moves it). Where the runtime can publish a page, the republish rides that edit (7.3).

**Quick mode keeps nothing on disk, by contract.** The printed block is the record. Do not
invent a scratch ledger file for it.

## The printed block

Marks are `- [ ]` open, `- [>]` the single in-progress item, `- [x]` done. The heading
carries the position, because a bare list of ticks makes a reader count rows:

```
## 0. Phase ledger  (3 of 10, Phase 4)
- [x] 1  Phase 1. Clarify
- [x] 2  Phase 2. Plan + gate
- [x] 3  Phase 2.5. Spec review
- [>] 4  Phase 3. Implement
- [ ] 5  Phase 4. Verify
...
```

The count is completed items over total items, then the phase the `- [>]` line names. Print
every item, every time.

## The items, per mode. This is the only place they are listed.

**Full mode, ten items, in this order:**

1. Phase 1. Clarify (anchor locked, repo brief written)
2. Phase 2. Plan + gate (work-doc written, user "go" through the wizard tool)
3. Phase 2.5. Spec review (report produced, Critical and Important findings patched into the doc)
4. Phase 3. Implement (every task ticked with evidence, every stage committed, scouts run)
5. Phase 4. Verify (Evidence Ledger complete, triad green, ship-gate rows present)
6. Phase 5. Review (coverage ledger complete, decision table empty, fixes verified)
7. Phase 6a. Re-verify + land (Steps A, B, C of section 13.1)
8. Phase 6b. Cleanup sweep (Step D)
9. Phase 6c. Archive work-doc to `done/` (Step F)
10. Phase 6d. Law self-audit + update log (Step F)

**Quick mode, six items, in this order:**

1. Phase 1. Clarify (anchor locked, repo brief written, approach restated in chat)
2. Phase 3. Implement (every task ticked with evidence, scouts run)
3. Phase 4. Verify (Evidence Ledger complete, triad green, ship-gate rows present)
4. Phase 5. Review (coverage ledger complete, decision table empty, fixes verified)
5. Phase 6a. Re-verify + land + cleanup sweep (Steps A to D)
6. Phase 6b. Law self-audit + update log (Step F)

**Conditional items, inserted only when they apply, never pre-listed:**

- **Phase 3b. Debug**, inserted directly after the Implement item the moment you are stuck
  twice on one symptom (section 10.1).
- **Walkthrough offer** (Step E), inserted between the cleanup sweep and the archive item
  when the change touched an entry point (13.2). It ticks on its own before 6c opens.
- **Worktree cleanup** (Step G), inserted after the last item when the task used a
  worktree. It runs after the archive move and is ticked by the closing edit.

## The ordering law, the whole point

- **One item in progress at a time.** Never two.
- **No jumping ahead.** A later item may not open until the current item is complete.
- **No silent skip.** A phase that genuinely does not apply is ticked complete with a
  one-line reason appended, e.g. `Phase 2.5, skipped: quick mode, no written spec`. Never
  delete an item to make progress look done.
- **A phase never overlaps another.** Work inside one phase can be organised however serves
  it; the boundary is a hard edge.

## Exit artifact per phase, the anti-skip lever

A checkbox may flip to complete **only when its exit artifact exists**. No artifact, no
tick, and the ordering law blocks every later phase.

| Phase | Exit artifact that must exist before you tick it |
|---|---|
| 1 Clarify | The goal anchor (5.2), all five parts, locked and confirmed; the repo brief (6.13) with a command or `file:line` behind every line; in quick mode, the printed approach restatement (6.1, step 6) |
| 2 Plan | The work-doc exists at `docs/work/<date>-<slug>.md` at the template's shape **and** the user's explicit "go" through the wizard tool |
| 2.5 Spec review | The report, with the execution order and contended resources first; every Critical and Important finding patched into the doc; scope changes re-gated |
| 3 Implement | Every Sprint Backlog checkbox ticked with a fresh proof line; every stage's scout tables present (perf, law, and design when the stage wrote a UI file) with every row dispositioned; the application booted at the assembly stage; every stage committed |
| 3b Debug | The hypothesis chain written down; a confirmed root cause; the regression test and the fix landed, or the circuit-breaker halt surfaced to the user |
| 4 Verify | A proof row per task **and** per acceptance bullet; the three verify layers run; the three ship-gate rows present, each ✅ or `⏭ skipped` with a written reason naming what was searched; the "what this did not reach" list; on UI-bearing work, the design pre-flight (15.30) ticked with evidence |
| 5 Review | Coverage ledger with a row per touched path; all five checks filed (design conformance omitted with a recorded reason when the change has no UI surface); every finding challenged; the decision table (12.9) empty; the triad green on the touched scope after the fixes |
| 6a Re-verify + land | Verification re-run green on the pre-land state; the landing chosen (full: the four options through the wizard tool; quick: the Phase 1 handover answer) and executed |
| 6b Cleanup sweep | One evidence line per cleanup class (13.2), zero counts included; every defect found either fixed or filed as a linked Retrospective follow-up |
| 6c Archive | Frontmatter `status: done` and a fully closed ledger written by the closing edit, followed immediately by `git mv docs/work/<slug>.md docs/work/done/<slug>.md` |
| 6d Self-audit + update log | The law self-audit printed with no `no`; the five-field update log printed and, in full mode, appended to the doc under `## Update log` by the closing edit |

## The helper refusal, the second anti-skip lever

An exit artifact proves the work happened. This proves the work was carried the way 1.8 says
it must be. **A phase carrying a mandatory send (1.8) does not tick until the send was made,
or a reason is written on the item**, in this shape:

```
- [x] 4  Phase 3. Implement  helper skipped: Helpers unavailable in this session
```

The three reasons 1.8 allows are the recorded `Helpers: unavailable` line, a user waiver in
their own words, and a send that was made and came back with nothing usable. No other text
belongs after `helper skipped:`, and an item ticked with the send neither made nor reasoned is
a false tick whatever the code looks like. Where helpers are unavailable the reason is written
once per affected item and the reading happens in this session, which is why the refusal can
never deadlock a runtime that has no agent tool.

## Reflect after each step

When you complete a ledger item, do three things in order:

1. Say one line in chat: what changed, did it pass, what is next.
2. Flip the item to complete, and in full mode advance frontmatter `status`, in one edit.
3. Open the next item in that same edit, save, then re-print the block, then read the next
   phase's reference file from disk.
4. Send the block's heading line and the reflection through the notification tool
   (`SKILL.md` 1.4), one line under 200 characters. It is the only step here that reaches a
   user who has walked away from the terminal.

The reflection is the checkpoint. A tick with no reflection is an untrusted tick.

## Loop-back

When a later phase sends you back (a red in Phase 4, a Critical or Important finding in
Phase 5, a red re-verify in 6a, a task you cannot finish in Phase 3), re-open the earlier
item as `- [>]` with `reopened: <reason>` appended, leave every later item open, and run
forward again through every phase in between. Phase 3b, when it fires, is inserted as its
own item and ticked before Phase 3 re-opens. Nothing from the earlier pass carries over as
proof; every re-run produces fresh evidence. The block is re-printed at the reopen and at
every boundary after it.

## Re-print inside a phase, not only at its edges

A phase boundary is not the only place the ledger goes stale. Phase 3 runs in stages and
Phase 5 runs a review, a challenge and a fix pass; none of those is a boundary. So **re-print
the block at the end of every implementation stage and after the Phase 5 fix pass**, with a
one-line reflection naming the stage rather than the phase. The marks do not move on an
in-phase re-print, because a stage is not a phase. Never tick an item to show a stage
finished. The in-phase re-print goes out through the notification tool the same way a
boundary does (`SKILL.md` 1.4).

## Closing the ledger, the one place two rows tick together

Phase 6 ends in a fixed order, and it is the only point where two rows tick in one edit.

1. **6b closes, 6c opens.** The doc is still at its live path.
2. **Step F's work runs at that live path**: the Retrospective is written, the law self-audit
   is printed, the update log (16.13) is printed.
3. **One edit closes both rows.** Append the update log under `## Update log`, tick 6c and
   6d (and the worktree row, when there is one), and write `status: done` with the shipped
   fields. This is the last content change the doc ever receives.
4. **`git mv docs/work/<slug>.md docs/work/done/<slug>.md`** is the last mechanical step. A
   worktree removal, where one applies, runs after it.

Because the closing edit comes before the move, the doc never sits under `done/` with an
open row, and a doc carrying `status: done` outside `done/` is the one state that reveals a
session that died between the edit and the move. On resume, finish the move first.

## Pause and resume

- In full mode the ledger is durable only if you keep writing it: a resume finds the phase
  your last file edit recorded, not the phase your last chat print showed.
- On resume, read `## 0. Phase ledger` back, re-print it, restore it into the todo tracker if
  there is one, set the first open phase in progress, and read that phase's reference file.
  When the block is missing (an older doc), rebuild it once from `status` and the Sprint
  Backlog, write it into the doc as the single migration edit, and never rebuild again.
- Quick mode keeps no work-doc, so its ledger dies with the session, consistent with its
  no-resume contract.

## Anti-rationalizations

| Thought | Reality |
|---|---|
| "I'll archive right after I show the summary" | There is no "after". The same edit that ticks the summary row writes `status: done`, and the `git mv` follows it immediately. |
| "The code is done. I can skip the ledger now" | The ledger opens at task start, before any code. It is the order-enforcer, not a trophy. |
| "The printed block is right, I'll write the file at the end" | There is no end that reads chat back. Tick the work-doc and advance `status` in the same edit, then print. |
| "The work is green, so the missing fork does not matter" | The refusal is on the tick, not the code. Write the reason or make the send; there is no third move. |
| "The todo tracker already has it, so it is tracked" | The tracker is session-local and never touches the work-doc. Its tick owes the same file edit. |
| "This phase does not apply. I'll delete its item" | Do not delete. Tick it with `skipped: <reason>`. Silent deletion hides drift. |
| "These two phases are independent. I'll do them together" | Phases are sequential. How work is organised inside one phase is open; running two at once is not. |
| "Tests are green, that's Phase 4 done" | Phase 4's exit artifact includes the three ship-gate rows and the three layers. A green triad is not a booted app. |
| "I'll re-run the review to prove the fixes came out clean" | There is no second round. One review, one challenge, one fix pass, then the triad on the touched scope. |
| "Verify went red but the fix is obvious, I'll patch and carry on in Phase 4" | A red sends you back to Phase 3. Re-open it, fix there, and come forward again with fresh evidence. |
