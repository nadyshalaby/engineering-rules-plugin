# 5.2 [reference] The goal anchor

The **Primary Goal & Guardrails** anchor is the north-star every plan and implementation
decision is measured against. It is captured once in Phase 1, persisted (in the work-doc in
full mode, in chat in quick mode), and enforced by drift-checks in Phases 2.5, 4 and 5. Its
job is to convert a fuzzy ask into a fixed target so no later phase silently wanders off it.

Read this file at Phase 1 (to capture the anchor), at Phase 2.5 and Phase 5 (to enforce it).

## The anchor shape, five parts, always these five

- **North-Star Goal.** One sentence naming the single outcome the task commits to, in the
  user's own words. If you cannot state it in one sentence, Phase 1 is not done.
- **In-Scope.** The bullets of work this task WILL do. The boundary of the change.
- **Out-of-Scope / Non-Goals.** The bullets this task will explicitly NOT do. A change that
  does one of these is drift.
- **Guardrails / Invariants.** The properties the solution must never violate: a passing
  suite, a security boundary, a public API contract, a size cap, a behaviour the user named
  as untouchable. Breaking one is a Critical defect.
- **Success Signals.** The concrete, observable proofs Phase 4 will paste, one per
  acceptance criterion.

Open risks (what could make this the wrong solution) are written beside the anchor as a
separate list, not as a sixth part, so the drift checks have exactly five things to trace.

## Phase 1 capture

Phase 1's exit condition is a complete anchor. **Do not leave Phase 1 until all five are
settled:**

- [ ] North-Star Goal stated in one sentence and confirmed by the user through the wizard tool.
- [ ] In-Scope boundary enumerated.
- [ ] Out-of-Scope / Non-Goals named (ask "what should I explicitly NOT touch?").
- [ ] Guardrails / Invariants listed.
- [ ] Success Signals agreed.

**Question budget.** Around sixteen questions is the soft target for the whole clarify
round, not a ceiling and not a quota. Every question must fork a real decision: its branches
lead to different plans, code or acceptance criteria. Strip every question the ask, the code
or `CLAUDE.md` already answers. When the batch comes back and a part of the anchor is still
unpinned, ask a second, smaller batch for exactly that part. Never pad; never stop short.

## Persistence

- **Full mode.** Write the anchor into the work-doc under `## Primary Goal & Guardrails`,
  directly below `## 1. Original ask` (section 7.2).
- **Quick mode.** Keep the anchor as an in-chat block, and restate its North-Star Goal and
  its top Non-Goal in one line at the top of every phase, so drift is visible without a file.

## Enforcement, the drift-check

Work is traced back to the anchor at three points, with identical verdict wording:

- **Phase 2.5, the spec review (8.2).** Every Sprint Backlog task and every acceptance
  bullet traces to the anchor.
- **Phase 4, Layer 2 (11.2).** Every Evidence Ledger proof traces to the North-Star Goal and
  a Success Signal; a Success Signal with no proving row means the goal is not met yet.
- **Phase 5, the quality-and-plan check (12.7).** Every changed hunk traces to the anchor.

**Verdicts:**

- A task or hunk that serves no In-Scope bullet and is not required by one → **drift
  finding, Important**: justify it against the anchor or revert it.
- A task or hunk that violates a Guardrail or does something a Non-Goal excludes → **Critical**.

A clean pass means every unit of work traces to an In-Scope bullet and no unit violates a
Guardrail or a Non-Goal.
