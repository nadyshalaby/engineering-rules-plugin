# 9.3 [check] The implementation checklist

**The discipline every implementation stage holds itself to.**

## The floor, before a single line is written

- The task's acceptance criterion is in front of you, and you can state what will prove it.
- The files this task may write are known and written down.
- You have read the closest existing example of this kind of code, and you are matching its
  conventions.
- You know where every new file goes and what it is called, per section 2.2.

## Method

1. **Read every file the task touches, in full.** A targeted edit into a file you skimmed is
   how a working line gets deleted.
2. **Where the task is a bug fix, write the reproduction first** and watch it fail for the
   right reason. Everything else is tested in the testing stage with a watched mutation (9.2).
   A test you have only ever seen pass is a test of nothing.
3. **Search before you add.** For every new function, type, constant, schema or component,
   search the repo for an existing one first and keep the search; reuse or extend what
   exists. A new symbol with an existing equivalent is a finding, not a style choice (1.1).
4. **Write the minimum that meets the criterion**, with the edge cases handled: empty, one,
   many, absent, malformed, duplicate, unauthorized, and the error path.
5. **Stay inside the declared files.** A file the plan did not name is a scope change — stop
   and say so.
6. **Run the narrowest real check that can fail**, and keep its output.
7. **Sweep before you call it done**, both directions: every symbol you added has a caller;
   every symbol you orphaned is gone with what served only it; no debug line, commented-out
   block, `// removed:` marker or ownerless marker; and the dead code that was already in
   the files you touched is listed with its zero-reference proof for its own cleanup commit
   (9.1, the stage-end sweep).
8. **Re-run the project's own checks** (lint, typecheck and tests, from the repo brief's (6.13) Commands row) over the touched scope before you call the task done.
9. **Write the entry and tick the box in the same pass.**
10. **Report which tasks landed and which did not.** Stop at the first task you cannot finish,
   and keep everything already on disk.

## Verification, before you call a stage done

```
1. Every file I wrote was in this stage's declared list?           yes / no
2. Every task has a check that ran and its real output?            yes / no
3. Every new test failed first, for the reason it names?           yes / no
4. Lint, typecheck and tests pass over the touched scope?          yes / no
5. The application still boots?                                    yes / no
6. No suppression, non-null assertion, empty catch, bare throw, `.only` or debug artifact? yes / no
7. No inline type of 2+ properties in an implementation file?      yes / no
8. Every new file is where the organization law puts it, named to it? yes / no
9. No `git checkout`, `git restore` or `git stash` was run?        yes / no
10. Every commit is a stage commit, explicit paths, task branch, no attribution? yes / no
11. Every scout table for this stage is present (perf, law, and design when the stage wrote a UI file), every row dispositioned? yes / no
12. Every new symbol has a caller and a pasted reuse search; every symbol I orphaned is gone? yes / no
13. Dead code already in the files I touched listed with proof, for its own cleanup commit? yes / no
```

Any `no` sends you back to the work, not forward to the report.

## The report

What landed, what did not, what you had to change that the plan did not authorize, what you
had to leave broken and why, and every path this stage wrote.
