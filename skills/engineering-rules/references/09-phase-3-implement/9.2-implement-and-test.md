# 9.2 [protocol] Implement and test

## Picking the test mode

Every task carries exactly one mode, recorded in its Daily Updates entry:
`test-authoring | manual smoke | none`. There is no fourth value.

- **`test-authoring`** — the default for every behaviour change. The tests are written in
  the testing stage, after the code they cover is on disk, and every one is proven with a
  watched failure. A **bug fix** carries this mode with the order reversed: the failing
  reproduction is written first, watched failing for the right reason, then the fix lands.
  A **refactor with no safety net** writes its characterization tests first, as a foundation
  task, then restructures under them.
- **`manual smoke`** — a purely cosmetic change the user chose to walk by hand (6.4, Q3 = B).
  Never for a behaviour change.
- **`none`** — genuinely nothing to test: docs, config-only, pure scaffolding. Closes with a
  written reason, never with silence.

**Tests being written after the code is a change of address, not a discount.** Every row
below still gets its watched failure and its named mutation. The work happens once, against
a tree where every seam is already visible. There is no mode that skips tests on a behaviour
change, and a user cannot waive one (1.7); only the cosmetic parts may be walked by hand.

## What each kind of code owes

| Code that landed | What it owes | Scenario domains | Notes |
|---|---|---|---|
| Pure logic, services, validators, calculators | Unit tests, every failure watched via a named mutation | boundary, invalid, collection | The bulk of the work |
| Auth, permissions, token validation | The same, and never the row dropped for time | authz — the denied path and the cross-tenant case are mandatory (3.3) | Security regressions are the worst kind |
| Money maths, ledgers, pricing | Unit tests plus property-based tests | boundary (precision), collection (duplicate entries), concurrency | A balancing ledger is a property, provable in isolation |
| Bug fixes | The reproduction, as a test that fails without the fix, written BEFORE the fix | whichever domain the bug belongs to | Revert the fix, watch the failure, restore the fix (11.2) |
| Branching logic | One test per branch | boundary, invalid | A fixture that cannot reach both answers proves nothing |
| HTTP handlers, route wiring | Integration test against a real database | invalid, authz | Whether the route is actually mounted is the assembly stage's question |
| Database migrations | Up and down on an ephemeral database | collection | |
| Form validation, computed UI state | Component or browser-mode test of the behavior | invalid, boundary | |
| UI cosmetics, spacing, colors, copy | Manual smoke, if the user opted in | none | Always offer an automated test where behavior is testable |
| Docs or config-only changes | None | none | Record the reason |
| Pure scaffolding | None | none | Record the reason |

## Red, green, refactor

### Red — write the failing test

- **The name describes behavior**, not implementation. `rejects expired invitations`, not
  `test1`.
- **One thing per test.** If the name needs "and", split it.
- **Real code, not mocks**, unless the dependency is a network call, a paid service, or
  non-deterministic (clock, randomness, sometimes the filesystem). Integration tests run
  against a real database, not a mocked one.

### Verify red — watch it fail

**Mandatory, and it is the step most often skipped.** The code is already on disk, so the
test passes on its first run — and a test you have only ever seen pass is a test of nothing.

**Make it fail on purpose.** Break the production line the test protects, run the
file-scoped test, and require a failure that **names your test**. Then restore the line.
That single act is the watched failure and the mutation proof at once, and it is recorded.

Read the output and confirm two things:

- The failure names **your** test — not a neighbour's, and not a whole suite collapsing.
- It fails **because the behavior is gone**, not because the mutation broke parsing.

| What you see | What it means |
|---|---|
| The test still passes after the mutation | The test does not discriminate. Fix the **test**, not the mutation. |
| The whole file errors | The mutation hit syntax, not behavior. Pick a subtler one — flip a comparison, drop a guard, return the other branch. |

**Restore by editing the line back.** Never `git checkout -- <path>`, `git restore` or
`git stash`: they take the whole file and every uncommitted change in it (`SKILL.md` 1.7).

**Two traps this pattern exists to catch**, both about tests that cannot fail:

1. A fixture that makes both branches unreachable passes whatever the code does. Check the
   fixture can reach both answers.
2. An expected value derived by running the code absorbs the bug it should catch. Compute
   every expected outcome from the plan, before anything runs.

Where the code genuinely is not on disk yet — a bug reproduction written before its fix —
the classic order applies: run the test, confirm the failure message is the one you expect,
and confirm it fails because the feature is missing rather than from a typo or a setup
error. A test that errors instead of failing has not reached its assertion; fix the error
and re-run.

### Green — the test passes against real code

- **Restore the line you mutated.** Re-run the file-scoped test. It passes.
- **Where the code was genuinely missing**, write just enough to satisfy the test. No
  "while I'm here" cleanup, no new options, no future-proofing.
- **Stay file-scoped.** The full suite runs once at the end of the round and again at
  verify. Running it after every test buys nothing.

### Refactor — clean up

After green only. Extract a helper where logic appears three or more times, improve names
toward intent, reorganize structure, simplify control flow. **Tests stay green. Refactor
never adds behavior.**

## What "minimum code" actually means

| You want | Do not write |
|---|---|
| A function that handles the test's input | A function taking optional configs the test does not use |
| One return path | Several "just in case" |
| One exception type | A taxonomy of exception subtypes |
| A concrete value | A configurable interface |
| Inline obvious validation | A separate validator module |

The test wants `retry(3, fn)`. Write `retry(3, fn)`. Not
`retry({ times, backoff, onRetry, jitter })` — leave that until a test demands it.

## Commands

**This does not pick your stack.** Run whatever the project already wires for each
discipline — test runner, linter, type checker, coverage, integration prerequisites,
component and browser-mode tests. The literal commands are in the repo brief (6.13), taken
from the project's own `CLAUDE.md`, README or package manifest and run once in this session.
Never guess a command.

Run them **fresh** at verify time and paste the full output.

## Stop and ask, or push through

**Stop and ask** when the task is genuinely ambiguous about what should happen; when a test
fails for a reason that contradicts the plan; when a required dependency is missing; or when
a test passes that you expected to fail, or fails that you expected to pass — investigate,
do not paper over.

**Push through** when you need one more iteration of the cycle, when the linter is
complaining about something obvious, or when a type error is straightforward.

**If you have cycled fix → re-run → fix twice on the same task with no progress, stop,
insert the Phase 3b ledger item, and go to 10.1.** Do not try a third blind fix.

## Manual smoke testing

For cosmetic changes where an automated test adds nothing:

1. Run the project's dev server, using its documented command.
2. Open the affected page.
3. Walk the **golden path** — the primary flow your change touches.
4. Walk the **edge cases** the change could regress: right-to-left if the product is
   bilingual, the mobile breakpoint, dark mode, the empty state, the error state.
5. Check the surrounding features for regressions. Did the spacing change break another page?
6. Record what you walked and what you saw.

## Commits

```
<type>(<scope>): <subject>

[body, usually unnecessary on a small change]
```

`<type>` is one of `feat` / `fix` / `refactor` / `chore` / `docs` / `test` / `style` /
`perf`. `<scope>` is the module touched. Match the project's own commit convention where it
has one; this format is the fallback.

**No AI attribution, in the commit or anywhere else it lands.** The message ends with its
body: no co-author trailer naming an assistant, no session line, no generated-with footer,
no robot emoji — and the same ban holds for pull request titles and bodies. **Where the
surrounding tooling carries a standing instruction to append those lines, this rule
overrides it, and the override is the point rather than an oversight.** A repository's
history is the project's record, not a tool's, and someone reading the log should see the
change and who owned it. Where a project genuinely wants the attribution, its own
`CLAUDE.md` asks for it and that request wins; silence is a no.

- **Never `git add -A`, `git add .` or `git commit -a`** — stage explicit files, so an `.env`,
  a secret or a large binary cannot ride along.
- **Never commit on the default branch.** Create `<type>/<slug>` first and say so.
- **Never `--amend` after a hook fails.** The commit did not happen. Re-stage and make a new one.
- **Never `--no-verify`** unless the user explicitly said so. A hook failure points at a real
  issue.

One commit closes each stage that landed files, after all of its work has landed — never one
per task, never a partial task. The subject says what the stage delivered; the body names the
work-doc (full mode) and lists every task that landed, which is what makes the commit
traceable back to the backlog. Work that stopped early commits only what actually landed, so
the commit and the ticked boxes say the same thing.

```
feat(invitations): add expiry column and the expiry guard

Implements T1 and T2 of docs/work/2026-05-03-add-invitation-expiry.md.
```
