# 3.4 [catalog] Clean-code catalog

## Clean Code Violation Catalog (Canonical)

The canonical catalog of clean-code violations this law judges against: the community's shared vocabulary for code that is hard to read, hard to change or quietly wrong, given stable IDs so a finding can name the rule it breaks instead of a feeling. Read on demand by: Phase 3 (before the first line, for the domains the task's code has), the Phase 5 quality-and-plan check (12.7) and the challenge (12.8), the law scout's semantic tier (9.5), and the codebase audit's (16.3) code-style, file-scoping and testing categories (16.4).

**Canonical direction.** THIS file is canonical for the rows; `SKILL.md` 1.1 carries the always-on distillation (the ten-line clean-code floor) and 2.1 carries the doctrine that motivates them. The caps and the zero-tolerance bans are NOT here: `SKILL.md` 1.1 owns them and 16.4 maps their deterministic rules. What is here is everything a reviewer has to judge.

### How to load this file

The catalog is deliberately deep, every row carries why it hurts, how to detect it, and the fix direction, because a finding without those is not actionable. That depth costs tokens, so load by role rather than reading the whole file by reflex:

| Who | What to load |
|---|---|
| **Phase 3 implementation** | the severity model + ID scheme above, plus only the domains the task's code has. A pure data mapper needs Naming, Functions and Error handling; it needs Test hygiene at its testing stage and never Async unless it awaits something. |
| **Phase 5 quality-and-plan check (12.7)** | the whole catalog. It re-judges every law-scout row and applies the semantic tier to every touched file, so it needs every domain and every fix direction. |
| **Law scout (9.5) / the audit's semantic tier (16.6)** | nothing from here at scan time; they cite these IDs in their own rows. The three rows a grep can decide (`style.test.focused`, `style.test.skipped-no-reason`, `style.structure.debug-artifact`) are scanned by 9.5 under their 16.4 ids. |
| **Anyone else** | the always-on floor in `SKILL.md` 1.1, already in context. Come here only to cite an ID or read a fix direction. |

Domain sections: Naming · Functions · Comments · Structure & modules · Objects & data · Error handling · Boundaries & dependencies · Classes & cohesion · Async & concurrency · Test hygiene.

### Severity model

| Severity | Meaning | Classes it covers |
|---|---|---|
| **Critical (C)** | A defect ships, or a defect is hidden from the people who would catch it. | A floating promise, a mutated shared object, an argument mutated as a return channel, a hidden side effect, a log-and-continue catch, a focused test, an order-dependent suite, a sleep standing in for synchronisation. |
| **Important (I)** | The next change to this code will produce a defect, or a reader will act on a wrong belief. | A flag argument, a command that also queries, a train wreck, a stringly-typed closed set, a God module, a lost error cause, a vendor type in domain code, a test with no assertion. |
| **Minor (M)** | Readability. Costs a re-read, never a release. | Noise words, negative booleans, redundant comments, banner comments, distant declarations, a lazy class. |

Severity in the tables below is the **default**. Context moves it one level: a Minor naming defect on a public API rises; an Important object-design defect in a throwaway script falls. The semantic tier stages the default; the quality-and-plan check (12.7) sets the final severity. A row that duplicates a hard cap or a zero-tolerance ban is not here, except the three grep-decidable rows named above and the commented-code row, kept so a finding can cite a fix direction; the verdicts themselves live in 1.1.

### ID scheme

IDs are stable slugs `style.<domain>.<slug>`, the same convention as `perf.<domain>.<slug>` and `sec.<domain>.<slug>`. The audit rule catalog (16.4) keeps its coarse `style.*` rows and maps each to the rows here; a domain with no coarse row is cited straight from this file. Renaming an ID is a breaking change to every surface that cites it: extend, do not rename.

### Naming

Grounded in the naming chapter of *Clean Code* and the symbol table in 2.2.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.naming.intent | A name says what a thing is, not what it does or why it exists (`data`, `handle`, `process`, `doStuff`, `manager`) | M | Every call site loses meaning; the reader opens the body to learn what a call does | a noun-only function name; a name 2.2 refuses (`data`, `info`, `item`, `obj`, `temp`, `val`, `res`) | Verb first for functions, role-revealing nouns for values; a name that needs a comment is the wrong name |
| style.naming.disinformation | A name promises a shape or behaviour the value does not have (`userList` holding a Map, `isValid` returning a string, `getUser` that creates one) | I | Callers trust the name and skip the check; the bug is invisible at the call site | a suffix or prefix that disagrees with the declared type or the return statement | Rename to the truth, or change the behaviour to match the name |
| style.naming.noise-word | Suffixes that add no distinction: `Data`, `Info`, `Manager`, `Helper`, `Util`, `Impl`, `Object`; numbered siblings `a1`, `a2` | M | Two names differ without meaning anything different | a `Data`/`Info`/`Manager`/`Helper`/`Util`/`Impl` suffix carrying the whole meaning; siblings differing only by a digit | Name the responsibility; when two things hide under one noise word, split them |
| style.naming.encoding | Type or scope encoded in the name: Hungarian prefixes (`strName`, `arrItems`), `I` on interfaces, `_` for private where the language has privacy, `m_` members | M | Encodings rot on refactor and repeat what the type system already says | a leading `I` on an interface; `str`/`num`/`arr`/`obj`/`m_` prefixes | Plain names; the type carries the type (2.2, Symbols inside the file) |
| style.naming.negative-boolean | A boolean named in the negative (`isNotReady`, `disabled`, `hideDetails`) that call sites then negate | M | `if (!isNotReady)` is read wrong once a week | a boolean named `isNot*`/`not*`/`no*`/`dis*`/`hide*` appearing behind a `!` | Name the positive (`isReady`, `enabled`, `showDetails`) and invert once, where the negative is needed |
| style.naming.boolean-shape | A boolean with no predicate prefix (`active`, `visible`, `loading`) | M | Cannot be told from a value at the call site | a boolean-typed name without `is`/`has`/`can`/`should`/`will` | 2.2's prefix rule: `isActive`, `isVisible`, `isLoading` |
| style.naming.unpronounceable | Abbreviations and acronyms nobody can say or search (`genymdhms`, `usrCtxMgr`, `tmp2`); single letters outside a tiny scope | M | Cannot be discussed, grepped or remembered | a vowel-stripped identifier; a single-letter name living longer than a five-line scope | Whole words; single letters only for loop indices and one-line lambda parameters |
| style.naming.vocabulary-drift | One concept spelled several ways across the codebase (`fetch`/`get`/`retrieve`, `user`/`account`/`member`) | I | Search misses half the sites; readers assume a distinction that does not exist | two verbs or two nouns for one concept across files | One word per concept, repo-wide (2.2, rule 3); rename the minority |
| style.naming.pun | One word for two concepts (`add` that appends AND sums, `save` that writes AND validates) | I | An overloaded name hides a second responsibility (style.function.hidden-side-effect) | one identifier with two behaviours chosen by context or argument type | Split the names by meaning |
| style.naming.magic-literal | An un-named number or string whose meaning is not the value itself (`if (retries > 3)`, `status === 'A'`) | M | The reader guesses the meaning; two copies drift apart | a bare literal in a condition, an argument or a comparison, outside the floors in 16.5 | A named constant in the constants file (2.2); honor the extraction floors (16.5) and leave identity values inline |

### Functions

Grounded in the functions chapter of *Clean Code*, Meyer's command-query separation, and the size caps in 1.1 (which are verdicts and are not repeated here).

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.function.flag-argument | A boolean, or an enum used as a switch, that selects between two behaviours inside one function | I | The function does two things; every call site reads `render(true)` and means nothing | a boolean parameter read in an `if` at the top of the body; call sites passing `true`/`false` literals | Two functions, or an options object whose field names the behaviour; the caller says what it wants |
| style.function.mixed-abstraction | One body mixes orchestration (call three services) with byte-pushing (string slicing, index math, escaping) | I | The essential steps are buried in mechanics; the stepdown rule is broken | a high-level call beside a low-level loop or parse in the same body | Extract the low-level work into a named helper so the body reads as a list of steps |
| style.function.command-query | A function that both changes state and returns a computed answer, or a getter with a side effect | I | Callers cannot ask without acting; retries, caching and tests become unsafe | a `get*`/`is*`/`find*`/`has*` that writes; a `set*`/`save*`/`update*` returning derived data other than the changed entity | Split: the command returns nothing (or the entity it changed), the query changes nothing |
| style.function.param-mutation | A function mutates an argument (pushes into a passed array, sets fields on a passed object) as its way of producing a result | C | Action at a distance: every holder of the reference sees a change nobody asked for | `param.push(`, `param.x =`, `Object.assign(param,`, `delete param.x` on an input | Return a new value; take `readonly` inputs; mutate only what the function owns |
| style.function.output-argument | A result written into a caller-supplied out-parameter instead of returned | M | The data flows backwards; the signature lies about direction | a parameter that is only ever written to | Return the value; return an object when there are several |
| style.function.hidden-side-effect | A function does something its name does not promise (a validator that logs the user in, a check that resets a counter, a getter that writes a cache to disk) | C | The second effect is invisible at every call site and fires in every test that calls the first | I/O, global writes or state changes not implied by the name | Split the effect out and name it, or rename so the name carries it |
| style.function.unused-parameter | A parameter no path reads | M | Dead surface every caller has to fill; a signature that lies | a declared parameter with no reference in the body (the linter's unused-variables rule, arguments included) | Delete it and the arguments at every call site |
| style.function.short-circuit-default | `x = x \|\| default` used to default a parameter | M | A legitimate falsy value (`0`, `''`, `false`) is silently replaced | a `\|\|` on a parameter in the first lines of a body | A default parameter, or `??` where `null`/`undefined` is the only absence |
| style.function.type-switch | Behaviour picked by branching on `typeof`, `instanceof` or a `kind` string, repeated in more than one place | I | Every new variant edits every switch (`solid.ocp`); the type system already knows the shape | the same `typeof x ===`/`instanceof`/`switch (x.kind)` in two or more places | Polymorphism, one exhaustive handler over a discriminated union, or a strategy map keyed by the kind |
| style.function.negated-condition | `if (!isEmpty(x)) {…} else {…}` with both branches present, `!(a === b)`, or a guard written as the negation of the happy path | M | Double negatives cost a re-read and hide off-by-one logic | an `if (!` followed by an `else`; a `!(` around a comparison | Flip the condition and put the positive branch first; `a !== b` |
| style.function.boolean-return-branch | `if (cond) return true; else return false;` and `cond ? true : false` | M | Noise around a value that already exists | the patterns | `return cond` |
| style.function.dead-store | A value assigned and never read before it is reassigned or the function returns | M | Points at a missing use or a copy-paste error | an assignment followed by a reassignment with no read between | Delete the store, or use it |
| style.function.eval | `eval`, `new Function`, a string handed to `setTimeout`, `vm.runInContext` over data | C | Code from data; the security catalog owns the exploit (sec.injection.dynamic-code-eval) | the tokens | A lookup table, a parser, or a real function reference |
| style.function.callback-pyramid | Callbacks or `.then()` chains nested two or more levels deep where `async/await` is available | M | Error paths and ordering hide in the nesting | a `.then(` inside a `.then(`; a callback passed inside a callback | `async/await` with one `try/catch` at the boundary; promisify the callback API once |

### Comments

Grounded in the comments chapter of *Clean Code* and the Comments rule in 1.1: default to none, write the non-obvious WHY. The deterministic markers (`clean.debt-marker`, `clean.removed-comment`) live in 16.4 and are grepped by 9.5; this domain is what a grep cannot judge.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.comment.redundant | A comment that restates the code beside it (`// increment i`, `/** Gets the user. */` on `getUser`) | M | Noise readers learn to skip, and the one comment that matters is skipped with it | comment text whose words all appear in the next line | Delete; rename if the code needed the comment to be understood |
| style.comment.journal | Change-log and attribution comments (`// added by X on 2024-01-01`, `// fixed bug #12`, `// modified for the Y flow`) | M | Rots on the next edit; git owns the history | a date, a name, a ticket id or a task reference in a comment describing a change (2.1, Comments) | Delete; the commit message carries it |
| style.comment.banner | Section banners and position markers (`// ===== Helpers =====`, `// -----`, `} // end if`) | M | A divider inside a file is the line along which it should have been split (2.2) | runs of `=`/`-`/`*`/`#` in a comment; `// end` after a brace | Split the file at the banner, then delete the marker |
| style.comment.commented-code | A block of code kept as a comment | M | Nobody dares delete it; it drifts from the code it shadows | consecutive comment lines that parse as code (`clean.commented-code` in 16.4) | Delete; git is the reference |
| style.comment.misleading | A comment that no longer matches the code beside it | I | Readers trust the comment and skip the code; 1.5 calls this rationale drift | a comment claiming a behaviour, a value or a reason the code does not carry | Fix it or delete it; a comment's reason may no longer be the only one (1.5) |
| style.comment.mandated | Boilerplate doc blocks on every member because a rule says so (`@param x the x`, `@returns` restating the type) | M | Noise that buries the real contract | `@param <name> the <name>`; a doc block on every private member | Document only the WHY and the non-obvious contract; delete the rest |
| style.comment.nonlocal | A comment describing code somewhere else (`// see also the retry in the queue module`) | M | Breaks the moment the other place moves | a comment naming another file's internals | Put the fact where it lives; name symbols a rename tool tracks |

### Structure & modules

Grounded in the formatting chapter of *Clean Code* (vertical density, the stepdown rule) and the file and folder law in 2.2, which owns placement and naming.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.structure.distant-declaration | A variable declared far from its first use; every declaration hoisted to the top of a long function | M | The reader carries state across a screen | a declaration with no use within roughly ten lines | Declare at first use, `const` by default |
| style.structure.stepdown | The file reads bottom-up: helpers above the public entry point that uses them, entry points scattered between helpers | M | A file that cannot be read top to bottom | a private helper defined above the public function calling it | Public entry points first, helpers below in the order they are called |
| style.structure.wildcard-import | `import *`, `from x import *`, or a barrel that re-exports everything | I | Unreadable public surface; defeats tree-shaking (perf.build.*) and hides what is used | an `import *`; an `export *` | Named imports; a barrel that lists its exports (2.2, Barrels) |
| style.structure.circular-import | Two modules import each other, directly or through a chain | I | Undefined at import time in one order and fine in another; a design cycle (2.2) | a cycle in the import graph (madge, dpdm, knip) | Move the shared concept to a third module; never break a cycle with a lazy import |
| style.structure.unused-import | An import nothing in the file references | M | The reader believes a dependency is in play | the linter's unused-import rule | Delete |
| style.structure.inconsistent-return | A function returning a value on some paths and nothing on others | I | Callers get `undefined` by surprise on the path nobody tested | a bare `return;` and a `return x` in one body | One return shape per function; `null` for not-found (2.1, Null safety) |
| style.structure.global-mutable | A module-level `let`, a mutable exported object, or a module that reassigns its own exports at runtime | C | Hidden shared state; behaviour depends on import and call order; untestable | a top-level `let`; an `export let`; writes to an imported binding's fields | Pass state explicitly, or own it in one store module behind an API |
| style.structure.import-side-effect | A module that does work when imported: connects, reads the environment, starts timers, registers handlers | I | Import order becomes behaviour; tests cannot load the module without the effect | top-level statements with I/O; `new Client()` at module scope | Export a factory or an `init()`; the composition root calls it (2.2, `app.ts`) |
| style.structure.debug-artifact | A `debugger` statement, or a `console.*` call in domain code that bypasses the project's logger | I | Ships a breakpoint, or output with no level, no redaction and no transport | the tokens (`clean.debug-artifact` in 16.4, grepped by 9.5) | Delete `debugger`; route output through the logger module |
| style.structure.dense-line | Several statements on one line, or lines well past the formatter's width | M | The tooling baseline (2.1) owns formatting; a dense line hides a statement | two `;` outside a `for` header; lines over the formatter's width | Run the formatter; one statement per line |

### Objects & data

Grounded in the objects-and-data-structures chapter of *Clean Code*, the Law of Demeter, and the code-smells catalog in *Refactoring*.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.object.train-wreck | Reaching through a chain of foreign objects (`order.customer.address.city.name`, `a.getB().getC().doD()`), the Law of Demeter | I | Every link is a dependency; one shape change breaks every chain | three or more `.` hops through objects the caller does not own (a fluent builder and `?.` over the caller's own DTO are excluded) | Ask the nearest object for what you need; a method on the owner (tell, don't ask) |
| style.object.exposed-state | Public mutable fields, or a class that is a bag of getters and setters with no logic | I | No invariant can be enforced; every caller is a co-author of the object's state | `public` non-`readonly` fields on a class with behaviour; getter and setter pairs with no logic | Expose behaviour, hide data; `readonly` fields; a pure data shape is a type in the types file (2.2), not a class |
| style.object.hybrid | Half object, half data structure: behaviour AND public mutable data on one class | I | Hard to add behaviour AND hard to add data: the worst of both | a class with methods and public writable fields | Pick one: a data type (types file, no methods) or an object (private data, methods) |
| style.object.feature-envy | A method that uses another object's data more than its own | I | The behaviour lives in the wrong class; every change touches two files | most references in a method are `other.x` | Move the method to the class whose data it uses |
| style.object.data-clump | The same three or four values travelling together through many signatures (`street, city, zip`) | M | A type that was never named; `cap.fn-params` fires everywhere it goes | the same parameter group in two or more signatures | Name the group as a type in the types file (2.2) |
| style.object.primitive-obsession | A domain concept carried as a raw `string` or `number`: an email, an amount of money, an id, a status | I | Any string fits; validation is repeated or forgotten; `userId` and `orderId` swap silently | ids and statuses typed `string`; money as a float | A branded or opaque type, an enum or union, or a value type with its validation in one place |
| style.object.stringly-typed | A closed set of values compared by string literal across the code (`if (status === 'active')`) | I | Typos compile; the full set is unknowable | the same literal compared in three or more places | An enum or literal union in the `enums`/`types` file (2.2); an exhaustive `switch` |
| style.object.mutable-shared | A shared object or array mutated in place by more than one owner (a config object, a cached list, a module singleton) | C | Order and race bugs that appear only under production interleaving | `.push`/`.splice`/property writes on an imported, injected or cached object | Immutable by default: `readonly`, `as const`, `Object.freeze`, copy-on-write |
| style.object.deep-inheritance | Inheritance three or more levels deep, or inheritance used to share code rather than to model an is-a | I | Fragile base class: every subclass carries every ancestor's assumptions | `extends` chains past two; a base class that is a bag of protected helpers | Composition: inject the collaborator; a function or a mixin for shared code |
| style.object.god-module | A class or module that knows everything: many unrelated methods, many dependencies, edited by every feature | I | Every change converges on it; merge conflicts and regressions follow | roughly ten or more injected dependencies; a file every feature's diff touches; `cap.file-lines` | Split by responsibility along 2.2's roles; each piece owns one domain |
| style.object.anemic-domain | Every entity is a data bag and every rule lives in a service, so an invariant has no home | M | Rules scatter across services; two services enforce the same rule differently | entities with no methods beside services holding all the rules | Move a rule that belongs to an entity onto it; keep orchestration in the service |
| style.object.middle-man | A class or function that only delegates every call to another | M | Indirection without value | every method a one-line pass-through | Delete it and call the real thing, unless it is the documented public surface (2.2, Barrels) or a boundary adapter (style.boundary.unwrapped-dependency) |
| style.object.temporal-coupling | Methods that must be called in an undocumented order (`init()` before `run()`, `setX()` before `save()`) | I | Works in the one path the author tried | a method that throws or misbehaves when another was not called first | Make the order impossible to get wrong: the constructor takes what it needs, or each step returns the next object |
| style.object.working-constructor | I/O, network or heavy computation inside a constructor | I | Cannot be constructed in a test; failures surface as `new` throwing | file, network or database calls, or loops over data, in a constructor | The constructor assigns; a static `create()` or an `init()` does the work |
| style.object.static-bag | A `Utils`/`Helpers` class or module of unrelated static functions | M | A collection of nothing in particular; 2.2 refuses `utils/` by name | a class with only static members; a module with more than one concern and a generic name | Place each function with the concept it serves |

### Error handling

Grounded in the error-handling chapter of *Clean Code* and the Error handling and Null safety rules in 2.1. The deterministic rows (`ban.empty-catch`, `ban.bare-error`) are verdicts in 1.1; this domain is the judged remainder.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.error.log-and-continue | A catch that logs, or returns a default, and lets the caller proceed as if the operation succeeded | C | The failure moves downstream and surfaces as corrupted state with no stack pointing home | a `catch` whose body is only a `logger.*`/`console.*` call, or `return null`/`[]`/`{}`, on a path the caller cannot continue without | Rethrow as a domain error with `cause`, or return a typed failure the caller must handle |
| style.error.lost-cause | Rethrowing a new error inside a catch without attaching the original | I | The root cause is gone from every log | a `throw new` inside `catch` with no `{ cause }` and no `.cause =` | `new DomainError(message, { cause: e })` |
| style.error.contextless | An error with no context: `throw new NotFoundError()` with no id, `'Something went wrong'` | I | Unactionable in production | an error constructed with no arguments or a generic message | The message names the operation and the identifiers, never the secret |
| style.error.control-flow | Exceptions used for expected branching: throw to leave a loop, catch to detect not-found | I | Slow, hides the real error path, and a genuine failure is caught by the same handler | a `try` around a lookup whose miss is normal; a `catch` used as `else` | Return `null` or a result type for expected outcomes; throw only for the unexpected (2.1, Null safety) |
| style.error.wide-try | A `try` wrapping dozens of lines or a whole function body | M | The catch cannot know which line failed; unrelated failures share a handler | a `try {` over roughly fifteen or more lines or several distinct operations | Narrow the try to the one call that can throw; extract the body |
| style.error.catch-all | Every error treated as one case (`catch (e) { return 500 }`), nothing re-classified | I | A bug and a bad request look identical to the caller | one catch handling every error type the same way | Branch on the error class; let unknown errors propagate to the boundary handler |
| style.error.return-code | Failure signalled with `-1`, `false` or `null` from an operation that can fail for more than one reason, in a language with exceptions | I | Callers forget the check; the reason is lost | sentinel returns from operations with several failure modes | Throw a domain error (2.1) or return a typed result; `null` is for not-found only |
| style.error.null-argument | `null`/`undefined` passed into a function as a "skip this" signal | M | Every callee needs a null check; the contract is invisible | call sites passing `null`/`undefined` literals as arguments | An options object with an explicit field, an overload, or two functions |
| style.error.unwrapped-boundary | A transport or vendor error shape (`AxiosError`, a driver's `code`) handled inside domain code | I | Domain code depends on the vendor's error shape; a client swap rewrites the rules | an `instanceof <VendorError>` or `err.code === 'ECONN…'` outside the adapter in `lib/` | Translate at the adapter into a domain error the callers know |
| style.error.async-in-sync-catch | A `try/catch` around an un-awaited promise, believing it catches the rejection | C | The catch never fires; the rejection floats (style.async.floating-promise) | a `try { asyncFn() }` with no `await` and no `return` | `await` inside the try, or `.catch` on the promise |
| style.error.silent-default | `?? []`, `\|\| {}` or a default masking a failed lookup that should have been an error | I | A missing record reads as an empty one | a `??`/`\|\|` on the result of a fetch or lookup | Distinguish not-found from empty; throw or return a typed absence |

### Boundaries & dependencies

Grounded in the boundaries chapter of *Clean Code* and the layer tables in 2.1 and 2.2.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.boundary.unwrapped-dependency | A third-party SDK or client called directly from several places in domain code | I | The vendor's API shape becomes the codebase's; upgrades and swaps touch every file | a vendor package imported in three or more feature files | One adapter in `lib/` (2.2) exposes the few calls the domain needs |
| style.boundary.leaked-type | A framework or vendor type (`Request`, `Response`, an ORM entity, a client's payload type) in a domain signature | I | The domain cannot be tested or reused without the framework (2.1, Clean architecture) | a framework type in a service or repository signature | Map at the edge to a domain type (types file) or a DTO |
| style.boundary.env-everywhere | `process.env`/`os.environ` read outside the one configuration module | I | Untyped, unvalidated, scattered configuration (2.1, Environment-variable validation) | environment access outside `config/` (2.2) | The env module validates once and exports typed config |
| style.boundary.clock-random-inline | `Date.now()`, `new Date()`, `Math.random()` read directly inside domain logic | M | Untestable; every test touching time or randomness is flaky | direct clock or random calls in services | Inject a clock or a random source; the composition root wires the real one |
| style.boundary.transitive-reach | Importing a dependency's internals (`vendor/dist/internal/x`) or another package's `src/` | I | Breaks on every minor upgrade; 2.2's monorepo rule | an import path through `/dist/`, `/src/` or `/internal/` of another package | Import the public entry point; ask the vendor for the API |

### Classes & cohesion

Grounded in the classes chapter of *Clean Code* and the smells catalog in *Refactoring*. SRP itself is `style.srp` in 16.4; these are the shapes it takes.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.class.low-cohesion | The methods of a class fall into groups that share no fields | I | Two classes wearing one name | fields used by disjoint method groups | Split along the field groups |
| style.class.global-singleton | A hand-rolled singleton (`static instance`, `export const x = new X()`) holding mutable state | C | A hidden dependency; tests bleed into each other (2.1, no import-time singletons) | a `getInstance()`; a stateful `new X()` at module scope | Construct once in the composition root and inject |
| style.class.static-only | A class with only static members used as a namespace | M | A module in disguise that cannot be substituted | no instance state, every member static | Plain module functions placed by concern (2.2) |
| style.class.inappropriate-intimacy | Two classes reaching into each other's private or protected details | I | Neither can change alone | `protected` used as a sharing channel; a cast or a suppression to reach a private member | Move the shared behaviour into one of them, or into a third |
| style.class.shotgun-surgery | One conceptual change requires edits in many files (adding a status touches eight switches) | I | The concept has no home (`solid.ocp`) | a change that adds one variant and touches many files | Centralise the variation: one map, one polymorphic dispatch |
| style.class.divergent-change | One file changed for many unrelated reasons; every feature's diff touches it | I | Single responsibility at module level; style.object.god-module is its extreme | the history shows a file edited by unrelated features | Split by reason to change, along 2.2's roles |
| style.class.refused-bequest | A subclass overrides inherited methods to throw or do nothing | I | The hierarchy is wrong (`solid.lsp`) | a `throw new NotSupported` or an empty body in an override | Composition, or an interface the subclass actually satisfies |
| style.class.lazy-class | A class or module too small to justify its existence | M | Indirection with no weight | one trivial method and no state; a one-line module | Inline it into its only user (2.2, Orphan folder) |
| style.class.interface-per-class | An interface with exactly one implementation, created by reflex (`IUserService` + `UserService`) | M | Two names for one thing; the seam is never used | an interface with one implementer and no test double | Depend on the class; introduce the interface on the second implementation (1.1, extract on the second use) |

### Async & concurrency

Grounded in the concurrency chapter of *Clean Code*. Throughput rows (sequential awaits, unbounded fan-out) are the performance catalog's `perf.async.*`; races on security-relevant state are `sec.concurrency.*`. This domain is correctness of ownership and completion.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.async.floating-promise | A promise created and neither awaited, returned nor handed a `.catch` | C | Rejections are unhandled; ordering silently changes; the process may crash later with no stack | an async call as a bare expression statement; a `void asyncFn()` with no error path | `await` it, return it, or hand it to a handler that owns the failure |
| style.async.shared-state-across-await | State read before an `await` and written after it as if nothing changed in between | C | Interleaving corrupts state (check-then-act; sec.concurrency.* owns the security case) | a field read, an `await`, then a write based on the read | Re-read after the await, or make the step atomic: a database constraint, a lock, a single writer |
| style.async.sleep-for-sync | `setTimeout`/`sleep` used to wait for another operation to finish | C | Passes on the fast machine, fails everywhere else | a fixed delay followed by a read of another operation's result | Await the actual signal: the promise, the event, or a poll with a condition and a timeout |
| style.async.detached-background | Background work with no owner: no handle, no cancellation, no error path | I | Leaks on shutdown; failures vanish | a `setInterval` or a spawned task whose handle is never stored | Own it: store the handle, wire shutdown, surface errors |
| style.async.dual-completion | An API that both returns a promise and takes a callback, or mixes an event emitter with a promise for one operation | M | Two completion paths; double-fire and missed errors | a `callback` parameter beside a `return new Promise` | One completion mechanism; promisify at the boundary |

### Test hygiene

Grounded in the unit-tests chapter of *Clean Code*, the F.I.R.S.T. properties, and the red-green-refactor protocol in 9.2. What to test is the test-scenario catalog (3.3); this domain is how a test is shaped.

| ID | Violation | Sev | Why it hurts | Detect (hint) | Fix direction |
|---|---|---|---|---|---|
| style.test.focused | `describe.only`, `it.only`, `test.only`, `fit`, `fdescribe` committed | C | The rest of the suite silently stops running; CI stays green on broken code | the tokens in a test file (`test.focused` in 16.4, grepped by 9.5) | Remove the focus; use the runner's filter flag for a local run |
| style.test.skipped-no-reason | `.skip`, `xit`, `xdescribe`, `test.todo`, `@pytest.mark.skip`, `@Disabled` and their kin with no ticket or owner on the line | I | A disabled test is a debt marker nobody owns; it never comes back | the tokens without an `ABC-123`, `#123` or `@owner` after them (`test.skipped` in 16.4) | Fix or delete the test; if it must wait, name the ticket in the reason |
| style.test.no-assertion | A test that only calls the code | I | Passes whatever the code does | a test body with no `expect`/`assert` | Assert the behaviour; a "does not throw" test says so with an explicit assertion |
| style.test.many-concepts | One test exercising several behaviours ("creates, updates and deletes") | M | A failure names three things (9.2, one thing per test) | a test name needing "and"; unrelated assertion groups in one body | Split by behaviour |
| style.test.order-dependent | Tests that pass only in sequence, or share a mutable fixture across cases | C | A green suite that fails under shuffle or in isolation (F.I.R.S.T., Independent) | a module-level mutable fixture; a test reading what another wrote | A fresh fixture per test; `beforeEach`; no shared mutable module state |
| style.test.non-deterministic | Real clock, real randomness, real network or a real sleep inside a unit test | C | Flaky; the suite trains people to re-run (F.I.R.S.T., Repeatable) | `Date.now()`, `Math.random()`, `fetch(`, `setTimeout` without fake timers in a unit test | Inject the clock and the random source (style.boundary.clock-random-inline); fake timers; a recorded stub at the boundary |
| style.test.mocked-subject | The thing under test is mocked, or the mocks are so deep the test asserts its own mocks | I | Tests the mock, not the code (9.2, real code not mocks) | a mock of the module under test; assertions only on mock calls | Real code; mocks only at the network, paid or non-deterministic boundary |
| style.test.implementation-coupled | Assertions on private state, call counts or internal call order instead of observable behaviour | I | Every refactor breaks the test (9.2, the name describes behaviour) | `toHaveBeenCalledTimes` as the only assertion; a spy on a private method | Assert outputs and observable state |
| style.test.derived-expectation | The expected value was produced by running the code and pasting the result | I | Absorbs the bug it should catch (9.2, trap two) | large literal expected objects with no derivation; a snapshot over logic | Compute expected values from the plan; snapshots only for serialisation shape |
| style.test.slow-unit | A unit test that hits a database, filesystem or network | M | The suite stops being run (F.I.R.S.T., Fast) | I/O in a test beside pure logic | Move it to the integration tier, or inject the boundary |
| style.test.unnamed | Test names like `test1`, `works`, `should work`, or the function's name alone | M | A failure says nothing | the patterns | Name the behaviour and the condition (9.2) |
| style.test.conditional-logic | `if`, loops or `try/catch` inside a test body deciding what to assert | M | The test has its own bugs and its own untested paths | control flow in a test body | One straight-line path per test; parametrise instead |
| style.test.commented-out | Disabled assertions or tests left as comments | I | A lost check that looks like a note | a `// expect(`, `// it(`, `// assert` | Delete or restore |

### Deliberately not adopted

The community carries a few rules this law reads differently. They are listed so nobody re-proposes them as an oversight.

| Community rule | Why this law does not adopt it as written | What applies instead |
|---|---|---|
| The Boy Scout rule, "leave the code cleaner than you found it" | It licenses drive-by edits, which Surgical Changes (1.6) forbids: the diff stops tracing to the ask (14.1, examples 2 and 6) | Note pre-existing smells as follow-ups (13.2, class 10); clean them in their own task with their own review |
| "Never return null" | This law returns `null` for not-found and throws for should-not-happen (2.1, Null safety); a result type everywhere is a taxonomy nobody asked for (9.2, minimum code) | style.error.null-argument bans passing null as a signal; 1.1 bans the non-null assertion |
| "One assert per test" | Several assertions on one behaviour are one test | style.test.many-concepts: one concept per test |
| "No comments, ever" | Comments default to none, and the non-obvious WHY is required (1.1, Comments) | style.comment.redundant, .journal, .banner, .mandated |
| "Small classes" as a member count | The only numbers are the caps in 1.1; a class is judged by cohesion, not counted | style.class.low-cohesion, style.object.god-module |
| "Program to an interface", an interface for every class | Extract on the second use (1.1); a single-implementation interface is a second name for one thing | style.class.interface-per-class; `solid.dip` where the project already injects an abstraction |
| "Prefer exceptions to error codes", everywhere | In Go and Rust errors are values; the analog table in 16.7 rules there | style.error.return-code applies only where exceptions are the idiom |
| "Composition over inheritance" as an absolute | A genuine is-a two levels deep is fine | style.object.deep-inheritance bans depth and code-sharing hierarchies, not inheritance |
| "Don't repeat yourself" from the first use | Extracting on the first use is speculation (1.1, `solid.yagni`); the extraction floors in 16.5 stay inline | The three-lines-twice floor in 1.1; style.naming.magic-literal honors 16.5 |
