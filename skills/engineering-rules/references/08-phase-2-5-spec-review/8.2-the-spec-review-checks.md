# 8.2 [check] The spec-review checks

**Audit the plan against itself, against the order it implies, and against the project's
rules — before any of it is built.**

## Method

**Internal consistency**

1. Read the original ask sentence by sentence. Mark every sentence nothing in the plan
   addresses.
2. Compare the clarifying Q&A against the approach. Any answer the approach contradicts is
   a finding.
3. Compare the acceptance criteria against the backlog. Any criterion with no covering task
   is a finding; any task covering no criterion is scope.
4. Compare the whole plan against the goal anchor (5.2): the Primary Goal, the Success Signals,
   the Guardrails, and the out-of-scope list. Drift here is the most expensive kind.

**Execution order and contended resources**

5. List every file two or more tasks write.
6. List every generated sequence counted off what already exists — migration numbers,
   ordinals, version stamps.
7. List every exclusive external resource — a single test database, a shared fixture, a port.
8. **Re-test each one.** Genuinely exclusive, or only conventionally serial? Name the
   isolation that lifts the conventional ones.
9. **Extract every genuinely contended write into one foundation stage** that lands them all
   and writes no business logic.
10. Order the remaining stages by dependency, and say which could safely be worked together.
11. Flag oversized tasks, undersized tasks, and missing prerequisites.
11b. Write the resulting order as the `### Execution stages` block (7.2), one line per stage.

**Rules and architecture**

12. Check the plan against the project's own `CLAUDE.md` and the user-global rules.
13. Check it against 2.1 and 2.2: layering, placement and naming of every file the backlog
    creates, inline types, suppressions, non-null assertions, bare error throws, and the
    caps in 1.1.
13b. Check that every task's test mode (9.2) is stated and that every behaviour change has
    a test-authoring task covering it; a fix has its reproduction first.
14. Quote the rule sentence verbatim in every finding. A paraphrased rule is a rule the
    author can argue with.

## Output

Lead with the execution order and the contended resources. Then the findings, each with a
severity and the lens it came from.

## Verification

1. Did you read the original ask sentence by sentence? (yes / no)
2. Does every acceptance criterion have a covering task, or a finding saying it does not? (yes / no)
3. Did you name every shared file, generated sequence and exclusive resource in the backlog? (yes / no)
4. Did you re-test each one as genuinely exclusive rather than assuming? (yes / no)
5. Is there a foundation stage holding every contended write? (yes / no)
6. Did you check the plan against the goal anchor? (yes / no)
7. Is every rule-based finding quoting the rule verbatim? (yes / no)
8. Did you say what this audit did not reach? (yes / no)
