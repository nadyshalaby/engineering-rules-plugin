# 8.1 [phase] Phase 2.5, Spec review

*Full mode only.*

**Audit the plan before any of it is built.** Every defect caught here is a defect that never
reaches code. The checks are in 8.2; this is when and how they run. Read 5.2 (the anchor),
2.1 and 2.2 (the doctrine the plan is checked against) alongside it.

## What it covers

Three lenses over one read of the plan:

1. **Internal consistency** — contradictions between the Q&A, the approach, the acceptance
   criteria and the backlog; sentences of the original ask nothing addresses; acceptance
   criteria with no covering task; and drift against the goal anchor (5.2).
2. **Execution order and risk** — every shared or contended resource the backlog touches
   (files two or more tasks write, generated sequences counted off what already exists,
   exclusive external resources such as a single test database), which ones are genuinely
   exclusive, the ordering that lifts the rest, tasks that are too big or too small, and
   missing prerequisites.
3. **Rules and architecture** — the plan against the project's own `CLAUDE.md`, the
   user-global rules, the code-quality doctrine (2.1) and the file-organization law (2.2). Quote the
   rule sentence verbatim in any finding.

## The output

Lead with the execution order and the contended resources, then the findings, each tagged
with the lens it came from and a severity. Write the execution order into the work-doc's
`### Execution stages` block (7.2) as part of acting on the report.

## Acting on it

- **Critical or Important findings change the plan before Phase 3 starts.** Edit the
  work-doc, do not carry a known-broken plan into implementation.
- **A finding that changes scope goes back to the user.** The gate was on the plan they
  approved; a materially different plan needs their word.
- **Minor findings are recorded and may be deferred.** Say so in the doc.

Then tick the item, re-print the ledger, read 9.1, and begin.
