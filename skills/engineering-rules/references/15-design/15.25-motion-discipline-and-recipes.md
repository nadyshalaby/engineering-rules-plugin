# 15.25 [reference] Motion discipline and recipes

## Motion is a claim the page has to keep

The spec's Motion section (15.3) sets the durations, the curves, what animates and what
must not, and the one orchestrated moment per view (15.1). This file governs everything
past that: when an animation is allowed to exist, the patterns that are banned outright,
and the canonical skeletons for the three scroll patterns that generated pages get wrong
most often. Read it at Phase 3 whenever `MOTION_INTENSITY` (15.20) is above 3, and before
adding any scroll-driven or pointer-driven behaviour at any dial.

---

### Motion must be motivated

Before adding any animation, answer in one sentence: **what does this animation
communicate?** Four answers are valid:

| Reason | What it does |
|---|---|
| **Hierarchy** | Draws the eye to the right thing, once. |
| **Storytelling** | Reveals content in a sequence that matches a narrative. |
| **Feedback** | Acknowledges a user action: press, hover, submit. |
| **State transition** | Shows that something changed: a list re-ordered, a panel opened. |

"It looked cool" is not an answer. Scroll triggers everywhere because a library is
installed is amateur. Each pinned section, each marquee, each reveal needs its sentence,
written on the motion line of the composition plan (15.22). No sentence, no animation
(`tell.motion.unmotivated`, 15.24).

### Motion claimed, motion shown

A page that declares `MOTION_INTENSITY` above 4 moves: an entry transition on the hero,
scroll reveals on the key sections, hover physics on the CTAs, at minimum. A static page
claiming 7 is broken. The converse binds too: when working motion cannot ship in the
available scope, drop the dial to 3 and ship a clean static page. Never half-build motion
that breaks, with cut-off triggers, jumpy entries or missing cleanups
(`tell.motion.claimed-not-shown`).

### The tools, and when each is allowed

None of these fires automatically. Each is reached for when the read (15.20) and the dial
call for it.

- **Glass and frosted panels.** For premium consumer, Apple-adjacent, luxury and media
  overlays; wrong for dashboards, public sector and plain B2B. Done properly it is more than
  a blur: a 1px inner border at low white opacity and a subtle inset highlight so the edge
  reads as refraction, a solid-fill fallback under `prefers-reduced-transparency`, and only
  on fixed or sticky elements (15.26). The honest approximation of Apple's material is in
  15.21.
- **Magnetic micro-physics** (a button that pulls toward the cursor). Motion dial above 5
  and a premium, playful or agency read. Implemented exclusively with motion values and
  transforms computed outside the framework's render cycle. Never with render state; a
  state update per pointer move re-renders the tree and collapses on mobile.
- **Perpetual micro-interactions** (pulse, typewriter, float, shimmer, a ticking carousel).
  Motion dial above 5 **and** a section that gains from liveness: a status indicator, a
  live feed, a product demonstrating itself. An informational section stays still. Not
  every card needs an infinite loop (`tell.motion.loop-everywhere`). Spring physics on what
  does loop, never linear easing.
- **Marquees.** At most one per page. A logo strip, a manifesto strip and a kinetic word
  band on one page is three marquees and two of them are filler
  (`tell.motion.two-marquees`).
- **Scroll pinning and hijacks** (a sticky stack, a horizontal pan). Motion dial 8 and
  above, one or two per page, each a real pin built from the skeletons below, never a
  sequential reveal list dressed as a stack.
- **Hover physics on cards and images.** A gentle scale inside an `overflow: hidden` frame,
  a border that lights, a shadow that shortens on press. Only on interactive elements
  (`tell.motion.hover-on-static`).

### Springs and curves

- **Interactive elements use a spring or a decelerating curve**, never `linear` and never
  `ease-in-out` (`tell.motion.linear-easing`). A spring at roughly stiffness 100 and
  damping 20 reads as weighty; the spec's `motion.easing.enter` curve is the CSS default.
- **Entrances decelerate; exits accelerate.** The spec's `enter` and `exit` curves are the
  two curves a page needs; a third is a decision, written in the spec.
- **Staggers are short.** 40-120ms between siblings, eight to twelve elements at most in one
  orchestrated reveal (15.1); a longer cascade feels like waiting.

### Forbidden patterns, at every dial

| Pattern | Why it is banned | Use instead |
|---|---|---|
| `window.addEventListener('scroll', …)` | Runs every scroll frame, no batching, jank-prone, collapses on mobile | `IntersectionObserver`; CSS scroll-driven animation (`animation-timeline: view()`); a motion library's scroll primitives; a scroll-trigger plugin |
| Scroll position read into render state on every frame | Re-renders the tree per frame | A motion value or a transform updated outside render |
| A `requestAnimationFrame` loop that writes framework state | Same failure, self-inflicted | Motion values driving transforms directly |
| Layout animation props on static content "for safety" | Costs measurement work on every render | Layout animation only for visible re-ordering, resizing and shared-element moves |
| A stagger whose parent and children live in different client trees | The orchestration silently never runs | Parent variants and children in one client component; pass fetched data down as props |
| Animating `top`, `left`, `width`, `height` | Layout and paint every frame (`perf.frontend.layout-animation`, 3.1) | `transform` and `opacity` |
| Motion above dial 3 with no reduced-motion path | An accessibility failure (`tell.motion.no-reduced-motion`) | Collapse to static or opacity-only under `prefers-reduced-motion` |
| A scroll-driven engine and a UI motion library in one component tree | They fight over the same frames (`tell.motion.mixed-engines`) | One engine per tree; scroll engines in isolated leaves |
| An effect that registers a timeline or a listener and returns nothing | Leaks and double triggers on re-mount (`perf.memory.leaked-listeners`) | Return the cleanup; revert the animation context |

The design scout (15.29) greps for the first, the sixth and the seventh; the rest are judged.

### Library choice, stack notes

The rules above are stack-agnostic. Where the project is React-shaped, the conventions that
follow keep the rules cheap to honour:

- **A UI motion library** (Motion, imported from `motion/react`; the older `framer-motion`
  package name still works as an alias) for UI, bento and state-change motion, `whileInView`
  for simple reveals, motion values for pointer physics.
- **A scroll engine** (GSAP with its scroll-trigger plugin) only for full-page scrolltelling
  and hijacks, in dedicated leaf components with effect cleanup.
- **A 3D engine** (Three.js, WebGL) only for canvas backgrounds and scenes, under the same
  isolation.
- **Never mix the scroll or 3D engine with the UI motion library in one component tree.**
- **Every animated component is a client-side leaf**, marked as such at the top of the file,
  memoised, and rendered by a static server-side layout. A perpetual loop lives in its own
  microscopic component so it can never re-render its parent.
- **Reduced motion is read once**, from the library's hook or the media query, and every
  effect exits early on it.

### Recipe 1, the sticky stack

Cards that pin at the viewport top and stack as the next one arrives. The most common
failure is a trigger that fires halfway down the viewport instead of pinning at the top.

**Critical points, in any stack:** the pin starts when the card's top reaches the viewport
top (`start: "top top"`, never `top center` or `top 80%`); every card except the last is
pinned; the shrink-and-dim of a card is driven by the **next** card's scroll progress, so
the previous card recedes as the next one arrives; pin spacing is off so the cards overlap;
the effect cleans up; reduced motion renders the cards as a plain column.

```tsx
"use client";
import { useRef, useEffect } from "react";
import { gsap } from "gsap";
import { ScrollTrigger } from "gsap/ScrollTrigger";
import { useReducedMotion } from "motion/react";

gsap.registerPlugin(ScrollTrigger);

export function StickyStack({ cards }: StickyStackProps) {
  const ref = useRef<HTMLDivElement>(null);
  const reduce = useReducedMotion();

  useEffect(() => {
    if (reduce || !ref.current) return;
    const ctx = gsap.context(() => {
      const cardEls = gsap.utils.toArray<HTMLElement>(".stack-card");
      cardEls.forEach((card, i) => {
        if (i === cardEls.length - 1) return;
        ScrollTrigger.create({
          trigger: card,
          start: "top top",
          endTrigger: cardEls[cardEls.length - 1],
          end: "top top",
          pin: true,
          pinSpacing: false,
        });
        gsap.to(card, {
          scale: 0.92,
          opacity: 0.55,
          ease: "none",
          scrollTrigger: { trigger: cardEls[i + 1], start: "top bottom", end: "top top", scrub: true },
        });
      });
    }, ref);
    return () => ctx.revert();
  }, [reduce]);

  return (
    <div ref={ref} className="relative">
      {cards.map((card, i) => (
        <div key={i} className="stack-card sticky top-0 min-h-[100dvh] flex items-center justify-center">
          {card}
        </div>
      ))}
    </div>
  );
}
```

`StickyStackProps` lives in the component's `*.types` file (1.1); the `key` on a static,
never re-ordered list may be the index, and on a mutable one it is the card's id
(`perf.frontend.index-key`, 3.1).

### Recipe 2, the horizontal pan

Vertical scroll translated into a horizontal slide of a track. The most common failure is
the slide starting before the section is pinned, so the user sees half a slide.

**Critical points:** the wrapper is pinned at `top top`; the scroll distance equals the
track's overflow (`scrollWidth` minus the viewport width); the track moves by exactly that
distance with `scrub`; the trigger recomputes on refresh so a resize does not strand it;
cleanup and reduced motion as above, where reduced motion renders the track as a normal
horizontal scroll area.

```tsx
"use client";
import { useRef, useEffect } from "react";
import { gsap } from "gsap";
import { ScrollTrigger } from "gsap/ScrollTrigger";
import { useReducedMotion } from "motion/react";

gsap.registerPlugin(ScrollTrigger);

export function HorizontalPan({ children }: HorizontalPanProps) {
  const wrap = useRef<HTMLDivElement>(null);
  const track = useRef<HTMLDivElement>(null);
  const reduce = useReducedMotion();

  useEffect(() => {
    if (reduce || !wrap.current || !track.current) return;
    const trackEl = track.current;
    const ctx = gsap.context(() => {
      const distance = trackEl.scrollWidth - window.innerWidth;
      gsap.to(trackEl, {
        x: -distance,
        ease: "none",
        scrollTrigger: {
          trigger: wrap.current,
          start: "top top",
          end: () => `+=${distance}`,
          pin: true,
          scrub: 1,
          invalidateOnRefresh: true,
        },
      });
    }, wrap);
    return () => ctx.revert();
  }, [reduce]);

  return (
    <section ref={wrap} className="relative overflow-hidden">
      <div ref={track} className="flex h-[100dvh] items-center">{children}</div>
    </section>
  );
}
```

### Recipe 3, the scroll-reveal stagger, the lighter default

For "items appear as they enter the viewport" with no pinning, the UI motion library's
in-view primitive is enough and far cheaper than a scroll engine. Use this for feature
lists, testimonial grids, logo walls, anything that only needs to enter on scroll; save the
scroll engine for real pin and scrub work.

```tsx
"use client";
import { motion, useReducedMotion } from "motion/react";

export function RevealStagger({ items }: RevealStaggerProps) {
  const reduce = useReducedMotion();
  return (
    <ul className="grid gap-6">
      {items.map((item, i) => (
        <motion.li
          key={item.id}
          initial={reduce ? false : { opacity: 0, y: 24 }}
          whileInView={{ opacity: 1, y: 0 }}
          viewport={{ once: true, amount: 0.3 }}
          transition={{ duration: 0.6, delay: i * 0.06, ease: [0.16, 1, 0.3, 1] }}
        >
          {item.label}
        </motion.li>
      ))}
    </ul>
  );
}
```

### Recipe 3b, the same reveal with no JavaScript

Where the stack is not React, or the dial is 4-7 and the page can stay static under
reduced motion for free, CSS scroll-driven animation does the reveal with no listener:

```css
@media (prefers-reduced-motion: no-preference) {
  .reveal {
    animation: reveal-up both;
    animation-timeline: view();
    animation-range: entry 0% entry 30%;
  }
  @keyframes reveal-up {
    from { opacity: 0; transform: translateY(24px); }
    to   { opacity: 1; transform: none; }
  }
}
```

Browsers without `animation-timeline` render the elements in their final state, which is
the correct fallback. A cascade is `animation-delay: calc(var(--index) * 80ms)` with the
index set inline per item.

### Reduced motion, the contract

- **Everything above dial 3 honours `prefers-reduced-motion`.** In a library, the reduced
  hook gates every effect; in CSS, animations sit under `no-preference` or are switched off
  under `reduce`.
- **Loops, parallax, hijacks and magnetic physics collapse to static or instant.** A fade
  may remain; a transform may not.
- **The spec's `motion.reduced` line says what remains**, and the pre-flight (15.30) ticks
  it after a run with the preference switched on.
