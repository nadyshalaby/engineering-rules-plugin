# 15.31 [reference] Image-first work and brand direction

## Two workflows that start with a picture

Read this file in two situations. First, when an image-generation tool is available in the
environment and the task is visually led: a hero, a landing page, a redesign where the look
is the point, a mobile screen set. Then the picture comes first, the analysis second, the
code third, and the extract protocol's Mode C (15.5) reads the generated images as its
input. Second, when the deliverable is a brand kit, a logo direction or an identity board
rather than a screen. Neither replaces the spec (15.3); both feed it.

---

## Part 1, image-first frontend work

### When it applies

Image generation goes first whenever the tool exists and the request is mainly visual: "a
beautiful hero", "a premium landing page", "a more modern site", "a polished marketing page",
"a portfolio", "a multi-section concept", anything described in visual terms. Direct-to-code
is right when the task is technical, a bug fix, structural, or when the user already
supplied a precise spec or reference. Do not start with freeform coding when the visual
problem should be solved with a picture first, and do not describe a site in prose when the
tool could render it.

### The order, which is mandatory

1. Infer the site type, the conversion goal and the section count (the packs in 15.22 when
   the brief is silent: landing page six, full site eight, product page six).
2. Commit out loud: "Generating N images, one per section."
3. Generate one image per section, then extra detail images where the text, buttons,
   spacing or components are too small to read.
4. Regenerate any unclear section as a fresh standalone image. **Never crop, zoom or slice a
   region out of an earlier image**: a crop destroys spacing accuracy, type-scale
   relationships, margins and proportions, and the code built from it inherits the damage.
   A regeneration keeps the same language, palette, type mood, button style, radius logic
   and image treatment, and makes the section larger, cleaner and more analysable.
5. Analyse every image deeply, with the checklist below, and write the extraction report
   (15.5).
6. Build the frontend to match the images as closely as reasonably possible.
7. Invent a missing detail only when the images leave it ambiguous, and only after a detail
   image failed to settle it.

### How many images

Enough to make the design readable and extractable, and never fewer than the section count.
It is better to generate too many clear images than too few compressed ones; better one
clear image per section than one unreadable board for the whole site; better an extra
detail image than a guess. A single tall image containing the whole page, a multi-column
collage, one "best" image standing in for the set: all banned. Where the tool renders one
image per call, generate them in sequence in one response, labelled "Section X of N:
<name>", until the set is complete.

### Each image is a section comp, not mood art

Every generated frame communicates layout, hierarchy, spacing, type scale, visual rhythm, CTA
priority, component styling, image treatment and the overall system, so a developer could
build from it. Horizontal frames (16:9, 16:10, 21:9 by density). The composition axes in
15.27 (theme paradigm, background character, type character, hero scale, section system,
composition anchor per section, background mode per section, CTA variation, narrative spine,
one second-read moment) are chosen before generating and vary across the set as 15.27 says.
Section size varies too: some frames large and art-directed, some mini and mostly negative
space, some medium editorial blocks.

### One brand world across every frame

Across all per-section images: the same palette and accent logic, the same type family and
scale, the same CTA family (style may vary, identity may not), the same radius language,
the same image treatment (grade, materials, framing), the same tonal voice in any copy.
Variation is allowed in the composition anchor, the background mode, section size and
density, and which frame carries the second-read moment. A viewer flipping through the set
must recognise one site; anything that breaks brand recall is over-variation.

### The deep-analysis checklist

Treat the images as a design specification, never a vibe. For every section image, extract:

- **Text.** Every readable string: hero headline, subheadline, CTA labels, section titles,
  pricing labels, feature names, testimonial names and roles, nav and footer labels. Text
  too small to read reliably gets a closer extraction image; ignoring text extraction is
  not allowed.
- **Typography.** Size relationships, weight relationships, line count, line-height feel,
  tracking, serif against sans behaviour, display-to-body contrast, heading rhythm, CTA
  text scale, calm against aggressive.
- **Spacing.** Headline to subheadline, text to buttons, card to card, section top and
  bottom, side gutters, card padding, image to text, nav spacing, CTA block spacing, the
  cadence across sections. The goal is faithful spacing logic, not pixel OCR.
- **Buttons and components.** Size, shape, radius, fill against outline, icon use, implied
  hover mood, primary against secondary hierarchy, card structure, badges, dividers,
  shadows, borders, pills, inputs.
- **Colour.** Background, panels, accents, button fills, text hierarchy, border logic, shadow
  mood, image grade, gradient restraint. The implementation preserves the palette logic;
  it never swaps a designed palette for default web colours.
- **Structure.** Grid logic, section order and density, visual rhythm, repeated motifs that
  define the language, what is still unclear.

The analysis is calm, structured and specific. When something is unclear, generate another
image before writing code.

### Anti-drift implementation

The common failure is drift: strong images, generic code. During implementation, do not
simplify into a default template, replace a distinctive section with a generic row, compress
generous spacing, flatten strong type into a plain hierarchy, merge sections into repeated
patterns the images did not have, or reintroduce nested boxes the analysis removed. The goal
is "visually faithful to the image, translated into real frontend", never "inspired by". The
coded page must still feel like the same site as the references. The pre-flight (15.30)
ticks against the composition plan; on image-first work the plan is the image set.

Ambiguity resolves in this order: the visible language; the layout and spacing logic; the
component family; the mood and polish level; an extra detail image; a fresh regeneration;
and only then the most implementation-friendly faithful reading.

### Mobile screen sets

A screen set is images only; it never switches into code. On top of the native rules in
15.22:

- **Decide the platform mode first** (iOS, Android, cross-platform), then generate enough
  screens for the flow to feel real: an onboarding flow is several distinct screens, an auth
  flow separates sign in, sign up and recovery when useful, an app concept is a meaningful
  set, never one hero mockup. Regenerate rather than crop, as above.
- **Lock a design bible before the second screen**: platform mode, device frame style and
  scale, palette logic, type mood and scale, spacing, radius, icon style, imagery and
  texture treatment, navigation model, card and list behaviour, button styling, shadow
  language. Screen four belongs to the same product as screen one.
- **The screens form a believable flow**: onboarding to auth to home, home to browse to
  detail, cart to checkout to confirmation. Ask why screen two follows screen one.
- **Present inside a clean phone mockup by default**, one device style and scale across the
  set, centered, even margins on all sides, soft controlled shadows, the frame visible and
  quiet, the content the hero. Remove the frame only on request or for asset sheets.
- **Regenerate** when text is small, spacing unclear, navigation fake, the screen reads as a
  website in a phone, the set loses consistency, the onboarding repeats, or the framing is
  uneven. The first mediocre render is never the delivery.

## Part 2, brand direction

A brand kit is a visual argument for why the brand exists, not decoration. The deliverable is
usually one board image, and its logic feeds the spec's identity (name, palette, type) when
the product is built afterwards.

### Strategy before pixels

Infer the strategy first: category, audience, product function, emotional promise, cultural
position, trust level, visual world, symbolic metaphor, and what the brand must avoid. The
visual system is built on meaning; symbols are never picked at random.

| Category | Core ideas | Symbol logic |
|---|---|---|
| Developer tool | building, speed, precision, control | cursor, frame, bolt, scaffold, grid |
| AI assistant | delegation, intelligence, clarity | spark, orbit, signal, path, node |
| Security | protection, vigilance, boundary | shield, eye, seal, protected core |
| Gaming | chance, reward, tension, speed | dice, gem, card, signal, trophy |
| Voice | sound, rhythm, command, flow | waveform, mic, orb, speech path |
| Compliance | trust, order, rules | seal, badge, document, shield |
| Robotics | flight, control, vision, mission | wing, owl, crosshair, path, zone |
| Luxury, editorial | taste, material, ritual, restraint | monogram, seal, paper, emboss |
| Productivity | focus, momentum, clarity | path, check, block, calendar, light |

### The mark

Simple, memorable, symbolic, scalable, ownable, balanced, tied to the idea, usable as icon,
wordmark, badge, UI mark and pattern; it should look like the product of research and
reduction. Avoid generic bolts without a reason, random animals, fake crests, copied famous
marks, overcomplication, clip art, meaningless sparkles and inconsistent variants.

Concept methods, one or at most two combined: **monogram plus meaning** (an initial fused
with a metaphor through negative space, cuts, folds or geometry, never a plain letter in a
circle); **product action** (build becomes a frame or scaffold, protect a boundary, convert
a switch, speak a waveform, made abstract and premium rather than literal); **metaphor
fusion** (owl and drone vision, shield and mountain, moon and waveform, subtle and
readable); **negative space** (a hidden arrow, a protected centre, a cut-out initial, crisp);
**construction geometry** (circles, diagonal cuts, grids, frames, modular blocks, orbital
paths, measured linework, with one panel showing the construction).

### The board

Default one image, a 3 by 3 grid, 4:3 or 16:10, clean gutters, minimal text, every panel
connected. Panels: logo cover; logo construction; a digital application (browser chrome, app
header, terminal, app icon); the brand essence as one tagline in large type; the colour
system; typography; a physical application (card, badge, label, packaging); image direction
(a cinematic crop, a halftone poster, a material texture); a system detail (chips, an input
bar, an icon row, a pattern). A 2 by 3 mini-deck (wordmark; product surface; command or
functional panel; atmosphere image; symbol or badge; tagline) is the compact alternative.
The board has rhythm: quiet, functional, emotional, technical, atmospheric, detailed; not
every panel is loud.

### Visual modes

Dark developer or builder (near-black, mono accents, terminals, cyan, blue, coral or lime);
dark product or operator (black with dark red or amber, glowing chips, card systems); dark
nature or calm system (deep green, lime, misty landscapes, soft overlays); dark security
(black or navy, shield forms, radar lines, red and blue alert chips); light editorial or
compliance (warm ivory, paper texture, small serif labels, seals, deep blue, red and gold);
luxury, beauty and fashion (ivory, stone, espresso, a serif wordmark, embossing, soft
shadows); voice and communication (dark indigo, lilac glow, waveform, mic); cultural and
experimental (halftone, CRT, analog print, one punchy accent). Each maps to a direction in
15.4 when the product is built.

### Discipline

- **Colour.** One dominant palette: base, primary accent, secondary accent, neutrals. Accents
  repeat across panels; no rainbow; no generic purple-blue glow; one accent can carry the
  whole system.
- **Text.** Very little: the name, one tagline, one URL, one command, two to five section
  labels, short chips. No paragraphs, no tiny fake body copy, no lorem, no unreadable labels.
- **Taglines.** Short and specific ("Nothing random.", "Your network. Our watch.", "Build
  better."); never buzzword soup or inspirational fluff.
- **Imagery.** Art-directed: cinematic landscapes, dusk skies, halftone clouds, CRT scenes,
  dark product close-ups, textured paper, moody architecture. No stock people, no office
  photos, no robot clichés.
- **Mockups.** Minimal and believable identity applications (browser chrome, a URL bar, a
  terminal, an app icon, a phone corner, a card stack, a seal), never feature demos full of
  fake data.
- **Detail.** Page numbers, tiny footer labels, alignment marks, construction lines, thin
  rules, one highlighted word, one accent chip; used sparingly so looking closer is rewarded.
- **References.** From a user's references extract layout rhythm, grid, spacing, type scale,
  density, logo placement, amount of text, image treatment and accent logic; never the
  exact logo, name, composition, slogan or asset. References train the quality bar, never
  the template. The extract protocol's identity rule (15.5) binds here too.

### The brand feeds the spec

When the product gets built, the board's decisions become the spec's identity: the palette
logic into `colors` with computed contrast, the type into `fonts` with freely-licensed
substitutes, the mark into the logo treatment the Shapes section documents, the visual mode
into the `direction` slug. The board is the argument; `DESIGN.md` is the contract.
