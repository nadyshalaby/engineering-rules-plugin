# 15.29 [scout] The design scout

## Design-scout (deterministic AI-tell candidate finder)

A predictable, grep-based scan that surfaces **AI-tell candidates** in the UI files this
task touched, keyed to the stable ids in the AI-tell catalog (15.24). It is the third scout,
beside the perf scout (9.4) and the law scout (9.5): same run points, same path list, same
staging shape, and it runs only when the task is UI-bearing (`SKILL.md` Definitions). Its
output feeds the Phase 5 decision table (12.9), and the design-conformance check (12.5)
re-judges every staged row.

### WHAT

- **Deterministic candidate finder.** Same files in, same candidates out, plain `grep`,
  `awk` and `sed`, no parser, no new dependency. Every line the block prints starts with the
  `tell.<area>.<slug>` id that fired, so the staging table's first column is copied, never
  inferred.
- **Candidates, not verdicts.** A match means "look here". Half the rows here have a
  legitimate form (a marquee, a backdrop blur on a sticky nav, a brand that is purple on
  purpose), and the disposition names it. Judgment lives in TRIAGE and with 12.5.
- **Keyed to catalog ids.** Every pattern cites a row in 15.24. A pattern with no id is
  invalid; extend the catalog first.
- **Scoped to the diff, to UI files.** Markup, style and theme files in the touched scope.
  Everything else in the list is out of this scout's scope and is covered by the other two;
  the coverage line says so by name.
- **Bytes where characters would lie.** The em-dash, the middle dot, the degree sign and
  the emoji ranges are matched as UTF-8 bytes under the C locale, built with `printf`, so
  this file stays ASCII and the patterns survive every grep.

### WHEN

| Run point | Scope | What happens with findings |
|---|---|---|
| **Phase 3, the end of every stage that wrote a UI file** | The files that stage wrote | Trivial candidates inside the stage's allowlist are fixed and marked `fixed`; the rest are `staged`; every candidate gets one disposition. The table goes into the stage's Daily Updates entry beside the other two. |
| **Phase 4, inside the design pre-flight (15.30)** | The whole touched scope | The rows answer the pre-flight's mechanical boxes, with run-point id `pre-flight`; a candidate found here is fixed or staged like a stage-end one, and Phase 5 re-runs the scan regardless. |
| **Phase 5, start, on any change with a UI surface** | The whole touched scope, the same list 9.5 builds | The staging table goes into the Sprint Review beside the coverage ledger; every `staged` row joins the decision table (12.9) and 12.5 re-judges each one. |

A stage that wrote no UI file records `design scout: no UI file in scope` on its line and
does not run the block; a task with no UI surface never runs it at all. That record is the
difference between a scan that did not apply and a scan that was skipped.

echo "scope $cov_t | covered by a table $cov_c | no table:$cov_n | out of this scout's scope $cov_o | unreadable:$cov_x"

**Reconcile before you trust the result.** Paths handed in must equal paths readable, as in
9.5. Then the buckets: `covered` files had every applicable table run against them; `no
table` names a UI-shaped file this scout has no pattern list for, which is MISSING COVERAGE
and gets its own staging row (`no pattern table for <ext>, coverage lost`); `out of this
scout's scope` counts the shell, Python, SQL, Go and prose files the other two scouts own,
and is the honest common case, never a gap. `covered 0` on a stage that wrote only a
migration is the correct answer, written as `covered 0 of N, no UI file in scope`, never as
`no candidates`.

### The rows, and their false-positive guards

| Id | What the pattern catches | Guard, the reason a candidate may be dismissed |
|---|---|---|
| tell.punct.em-dash | An em-dash or en-dash byte sequence in a markup file | None in UI copy. A dash inside a code comment or a `src` URL in the same file costs one `false-positive` row. |
| tell.punct.middle-dot-chain | Two middle dots on one line | A metadata strip that genuinely needs two separators, rare. |
| tell.asset.emoji-as-icon | Emoji and dingbat code points | The user asked for a chat-style voice; a check mark inside a `kbd` demo. |
| tell.label.locale-strip | A clock time near a degree sign, or a Celsius or Fahrenheit reading | A weather product, a travel brand, a real venue. |
| tell.hero.scroll-cue | "Scroll to explore" and its siblings | None. |
| tell.hero.version-label | A version string, BETA, ALPHA, EARLY ACCESS, INVITE-ONLY, a build number in markup | The brief is a launch or a preview; a docs site's real version. Re-file as `tell.label.version-footer` when it sits in a footer. |
| tell.label.section-number | `01 / 4`, `02 Capabilities` shapes | A real ordered process the user asked to number. |
| tell.label.step-numbering | Step, Stage, Phase or Pass plus a number | A wizard's real "Step 2 of 3" progress indicator. |
| tell.label.pseudo-system | `orchestration layer`, `runtime marker`, a numbered `control plane` | The product genuinely is an orchestration product. |
| tell.hero.decoration-strip | Three or more period-terminated uppercase words in a row | A strip that is real navigation. |
| tell.label.eyebrow-everywhere | Uppercase-plus-tracking pairs counted against `section` elements, over ceil(n/3) | Product UI overlines labelling metrics or panels (15.22 scope); components counted twice because a layout wraps them. |
| tell.copy.lorem, .generic-name, .slop-brand, .filler-verb, .quietly-trusted, .oops-error, .fake-perfect-number | The literal lists in 15.23 | A real customer named Nexus; a code identifier that happens to spell `elevate`. |

| tell.visual.custom-cursor | `cursor: url(` | None. |

**Known false positives, so nobody re-argues them.** `tell.hero.version-label` fires on a
`v1.2` inside a URL path that a preceding character other than `/` fails to exclude;
`tell.copy.filler-verb` fires on identifiers such as `elevateRole(`; `tell.label.step-numbering`
fires on a form wizard's real progress text; `tell.motion.linear-easing` fires on the
utility class name even when it decorates a non-interactive fade. Each costs one
`false-positive` disposition with the reason. A regex that avoided them would need a parser.

### The judged tier (what greps cannot see)

Everything in 15.24 not listed above is judged, not grepped, by the pre-flight (15.30) and
the design-conformance check (12.5): the hero fitting the viewport, the four-element stack,
the layout-family count, the zigzag run, the split header, the empty bento cell, the theme
flip, the shape lock, the copy self-audit, the missing states, the contrast numbers. The
scout lists them so the check re-judges them explicitly, each citing its id.

### STAGING

entry (in chat, in quick mode) beside the perf and law tables; at Phase 5 start it goes into
the Sprint Review beside the coverage ledger. The two reconcile numbers and the bucket line
go above the rows on every run, including a run with no rows:

### TRIAGE

- **Every candidate gets exactly one disposition**, `staged`, `fixed` or `false-positive`. A
  candidate that vanishes without a row is a protocol violation.
- **Dismissing needs a one-line reason** tied to the row's guard above or the run context
  (a documented brand colour, a sticky element, a demo fixture).
- **Critical rows cannot be dismissed at a stage end.** `tell.layout.h-screen`,
  `tell.motion.scroll-listener`, `tell.state.white-on-white-button`,
  `tell.chrome.placeholder-comment`, `tell.chrome.missing-alt` and
  `tell.motion.no-reduced-motion` are `fixed` or `staged` until 12.5 has judged them with a
  counter-citation.
- **`tell.punct.em-dash` and `tell.chrome.placeholder-comment` are never `staged` past a
  stage end.** Both are fixed where they stand, whatever the allowlist, because a dash is a
  one-character edit and a placeholder is an unbuilt section.
- **`tell.asset.placeholder-shipped` has exactly one valid non-fix disposition**: `staged`
  with the update-log line quoted in Evidence.
- **Fix-in-stage is allowed** for trivial fixes inside the stage's allowlist; mark them
  `fixed` with the diff in the stage's entry and re-run the triad. At Phase 5 start nothing
  is fixed by the scout; every `staged` row goes to the decision table.
- **Pre-existing tells in touched files are in scope**, as in 9.5: surface them as a Phase 6
  Step D, class 10 item (13.2) and offer to fix, so touched files end clean.
