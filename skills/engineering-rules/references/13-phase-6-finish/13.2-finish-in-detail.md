# 13.2 [protocol] Finish, in detail

The step letters here are the same letters as 13.1, and the ledger rows in 5.1 map onto
them. Do this **after** Phase 4 and Phase 5 are both green.

---

## Step A. Re-verify

Even if it passed in Phase 4. State drifts: other commits, environment changes, hook
updates. Re-run, from a clean state:

```
<test command> && <lint command> && <typecheck command>     # the triad, from the repo brief
<build command>                                             # the ship-gate legs Phase 4 marked blocking
<start command> + readiness probe, then tear down
```

All green, fresh output, pasted into the Sprint Review (in chat, in quick mode). If anything
is red, **stop**: re-open Phase 3 (5.1, "Loop-back"). Never enter Step B with a red.

---

## Step B. Choose the landing

**Full mode.** Exactly four options, through the wizard tool. The option matching the Phase 1
handover answer (6.4, Q4) leads and carries `(Recommended)`. Do not improvise a fifth, and
never ask an open-ended "what should we do now?".

```
- Text: Tests pass and the review is clean. How do you want to land this?
- Header: Landing
- Options:
  - A. Merge into <base-branch> on this machine
    - What happens: The work lands on <base-branch> locally and I push it. Nothing else changes.
  - B. Push and open a pull request
    - What happens: The branch goes up with a written summary and a place for others to comment. Nothing merges until someone approves.
  - C. Keep the branch as it is for now
    - What happens: Nothing moves. The work stays on its branch and I pause the record so you can pick it up later.
  - D. Throw this work away
    - What happens: The branch is deleted. I'll ask you to type the word "discard" first, because this cannot be undone easily.
```

`<base-branch>` is detected with `git merge-base` against the upstream, usually `main` or
`master`. If unclear, ask.

**Quick mode.** No menu. Execute the Q4 answer: A → commit on the task branch and merge into
the base branch locally only when Q4 chose merge; B → push and open the PR; "in place" or
"leave it" → the changes stay in the working tree, recorded as a no-op. If Q4 was never
answered because the user's prompt said `ship it`, `merge it`, `commit and push` or `merge
directly`, that literal phrase is the answer.

---

## Step C. Land

Every commit here obeys 9.2: explicit paths, the project's own commit convention, no AI
attribution of any kind. If the working tree holds uncommitted work at this point, something
in Phase 3 was not committed at its stage end; stop and commit it as its stage before landing.

### Option A. Merge into the base branch locally

```
git checkout <base-branch>          # switching branches; never discards anything
git pull --ff-only
git merge <feature-branch> --no-ff  # or --ff-only when the project's history is linear
git status                          # must be clean
<test command>                      # green on the base branch, post-merge
git push
```

For a multi-project workspace, each project is its own git repo; run from inside it.

### Option B. Push and open a pull request

```
git push -u origin <feature-branch>
gh pr create --title "<concise title, ≤70 chars>" --body "$(cat <<'PRBODY'
## Summary

- [bullet 1]
- [bullet 2]

## Test plan

- [ ] Tests pass: `<test command>`
- [ ] Lint clean: `<lint command>`
- [ ] Typecheck clean: `<typecheck command>`
- [ ] Booted and smoked: `<the ship-gate rows, one line>`

## Related

- Work-doc: docs/work/<slug>.md
- Closes #<issue> (if applicable)
PRBODY
)"
```

**The body ends there: no generated-with footer and no assistant attribution.** Where the
surrounding tooling carries a standing instruction to append one, this law overrides it, and
a project that genuinely wants attribution says so in its own `CLAUDE.md`, which then wins.
Report the PR URL to the user.

### Option C. Keep the branch as-is

Do nothing to git. In full mode set frontmatter `status: paused` and write the checkpoint
(4.3, "Pausing"). Skip Steps D to G; the task resumes later.

### Option D. Discard

Requires the user to type the literal word `discard` through the wizard tool's free-text
input. Anything else ("yes", "delete it", "go ahead") is not consent; ask again.

```
git checkout <base-branch>
git branch -D <feature-branch>
git worktree remove <worktree-path>         # only if a worktree was used
git push origin --delete <feature-branch>   # ONLY if already pushed AND the user confirms this too
```

**Never** `git reset --hard`, **never** `rm -rf` a directory, **never** `git clean`. Branch
deletion is sufficient and stays recoverable through `git reflog` for weeks.

---

## Step D. Cleanup sweep

Runs after Step C and before the record closes. Thirteen classes, each producing a one-line
evidence record in the Retrospective (in chat, in quick mode), zero counts included. A defect
found is fixed inline, or filed as a numbered Retrospective follow-up with the user's sign-off.
Never silently left. Every fix here is a code change and obeys 9.2 and the file allowlist.

| # | Class | How to check | Remedy |
|---|---|---|---|
| 1 | Debug output added while working | `git diff <base>..HEAD \| grep -E '^\+' \| grep -nE 'console\.\|print\(\|println\|dbg!\|debugger\|breakpoint\(\|pdb\.set_trace\|binding\.pry\|byebug\|var_dump\|dd\('` | Remove; domain code logs through the project's logger (`clean.debug-artifact`). |
| 2 | Commented-out code, `// removed:` markers | `git diff <base>..HEAD \| grep -E '^\+' \| grep -niE 'removed:'` plus a read of every added comment block | Delete; git is the history. |
| 3 | Ownerless `TODO` / `FIXME` / `HACK` / `XXX` | `git diff <base>..HEAD \| grep -E '^\+' \| grep -E 'TODO\|FIXME\|HACK\|XXX' \| grep -vE '(TODO\|FIXME\|HACK\|XXX):?[[:space:]]*(\([^)]*\)\|@[a-z][[:alnum:]_.-]*\|\[[^]]*\]\|#[0-9]+\|[A-Z][A-Z0-9]+-[0-9]+)'`, the same owned shape the law scout uses (9.5) | Add an owner or a ticket, or remove. |
| 4 | Dead code | For every symbol the diff added or exported, grep for a caller | Delete, or wire it. |
| 5 | Unused imports, dependencies, env vars | The project's linter for imports; manifest vs `grep -rl` for deps; env schema vs usage | Remove, or use it. |
| 6 | Scratch files, fixtures, temp dirs, empty dirs | `git status --porcelain`; `find <touched dirs> -type d -empty` | Delete; `rmdir`. |
| 7 | Placeholder values and stub returns | Grep the diff for `TODO`, `placeholder`, `stub`, `return null` in new paths, `lorem`, and a placeholder image service (`picsum.photos`, `placehold.co`) | Replace or justify in writing; a seeded placeholder image survives only when the update log names the slot as still needing a real asset (15.23). |
| 8 | Unrelated changes that snuck in | `git diff --name-only <base>..HEAD -- . ':(exclude)docs/work/*' \| sort -u` against the union of every task's allowlist | Justify (add the task retroactively, with the user's sign-off) or revert that path's changes. |
| 9 | Stale references | `grep -rnE '<old-path>\|<deleted-file>\|<renamed-symbol>' <docs, configs, the work-doc>` for every path or symbol this task moved, renamed or deleted; check every markdown anchor in touched docs still resolves | Update the reference. Never rewrite a historical record; fix the live file. |
| 10 | Pre-existing errors and law breaks in touched files | The triad scoped to touched files, plus the law scout (9.5) and, over touched UI files, the design scout (15.29), each finding labelled *introduced* vs *pre-existing* by diffing against `<base>` | Introduced: already fixed by Phase 4. Pre-existing: list them and **offer** a fix through the wizard tool; apply only what the user approves, in the project's own patterns; defer the rest to a Retrospective follow-up with sign-off. Files outside the touched scope stay out; that is a codebase audit (16.3). |
| 11 | Leaked runtime state | `lsof -i :<port>` / `docker compose ps` / the process list, for every process Phase 4 or Step A started; `git status` for a `.env.local` or fixture staged into the diff | Tear it down; unstage it. |
| 12 | Dead branches created during the task | `git branch --list`, `git branch -r`, cross-checked against frontmatter `branch` and Daily Updates | `git branch -d` locally; remote deletion only with the user's confirmation. |
| 13 | Focused or skipped tests left on | `git diff <base>..HEAD \| grep -E '^\+' \| grep -nE '\.only\|\.skip\|\.todo\|xit\(\|xdescribe\(\|fit\(\|fdescribe\('`, then the law scout's `test.focused` / `test.skipped` rows (9.5) | Remove the focus; a skip names a ticket or the test is fixed or deleted. |

Evidence record shape, one per class: *"Class 8 scope creep: 0 unrelated paths (27 paths, all
in Sprint Backlog allowlists)"*.

## Step E. The walkthrough offer (16.9)

Detect entry-point touches from the touched scope. An entry-point file matches any of:
`*.controller.*`, `controllers/*`, `routes/*`, `*.routes.*`, `app/**/route.*`,
`pages/api/*`, `*.cli.*`, `cli/*`, `bin/*`, `*.job.*`, `*.queue.*`, `workers/*`,
`*.action.*`, `*Handler.*`. If none was touched, the conditional ledger row is not inserted
and the reflection says so in one line.

Otherwise, one question through the wizard tool:

```
- Text: This change touched <file> (and N other entry points). Want a code walkthrough of
  the new path, so the next reader has the current call graph?
- Header: Walkthrough
- Options:
  - A. Update the existing walkthrough at .walkthrough/<slug>/ (Recommended when one exists)
    - What happens: I re-trace the path, keep your manual notes, and show what changed since last time.
  - B. Create a new walkthrough for <entry>
    - What happens: I trace the path to its leaves and open a viewer you can click through.
  - C. Skip
    - What happens: Nothing is traced. You can ask for one later.
```

On A or B, run 16.9 now; it ticks its own row. On C, tick the row `skipped: user declined`.
One ask per finish, never a loop.

## Step F. Close the record

### F.1 The Retrospective (full mode)

Three to eight bullets, written before the closing edit: what surprised, what you learned
about the codebase, what pattern to reuse or avoid, follow-up work with an owner or a ticket,
any Minor finding deferred with its sign-off, and the thirteen cleanup evidence records. Do
not skip it; it is what compounds learning across tasks.

### F.2 The law self-audit (both modes)

Print the ten-line block from `SKILL.md` 1.7, filled in. Any `no` names the phase that
re-opens; the task is not finished until every line reads `yes`.

### F.3 The update log (16.13, both modes)

One short block per thing that changed, written the way you would explain it to a colleague
who was not in the room. This is the artifact the user actually reads, so it is the one place
where the writing matters more than the precision.

```
**Problem**
<what the reader would have experienced as wrong, or the gap that existed>

**Root cause**
<why it happened, plainly>

**Solution**
<what changed, in outcome terms>

**Verification evidence**
<the real command and its real trimmed output>

**Deployment status**
<shipped and where, or not shipped and what it waits on>

----
```

| Field | What goes in it | What kills it |
|---|---|---|
| **Problem** | The symptom as the user would have experienced it. "Invite links kept working after they should have expired." | Naming a function instead of a symptom. |
| **Root cause** | The real cause in one plain sentence. "Nothing ever checked the expiry date." | The same sentence in jargon. |
| **Solution** | The change in outcome terms. "Links now stop working the moment they pass their date." | A list of files touched. |
| **Verification evidence** | Real, trimmed. "Ran the tests: 87 passed. Made an invite, set it back 8 days, saw the expired message." | "Verified." with nothing behind it. |
| **Deployment status** | Where it actually is. "Shipped, it's on your `main` branch." | Vagueness. |

**Voice.** Talk like a person; contractions are fine. No jargon the user did not use first.
Never mention the workflow's own machinery: no phase numbers, task IDs, check names, scout
names, or the work-doc. One block per thing the user would recognise as a change: three files
serving one fix is one block. Typical task 1-5 blocks, a large one up to 12, each under about
120 words. Be honest in Deployment status; a half-done thing is said here, not buried. Say it
and stop. End with exactly one follow-up line, never omitted, never extended:

> Happy to go deeper on any of these, just say which one.

### F.4 The closing edit and the move (full mode)

ONE edit to `docs/work/<slug>.md`: append the self-audit under `## Law self-audit` and the
update log under a top-level `## Update log` heading (never nested inside the Retrospective),
tick ledger rows 6c and 6d (and the worktree row when there is one), and set the frontmatter:

```yaml
status: done
shipped: 2026-05-03
shipped_via: merge          # merge | pr | branch
pr_url: https://...         # when a PR was opened
```

That edit is the last content change the doc ever receives, and where the runtime can
publish, the final republish rides it. Then the move, a rename and nothing more:

```
git mv docs/work/<slug>.md docs/work/done/<slug>.md
```

The move never precedes the edit. A doc under `done/` with an open row, or a doc at the live
path with `status: done`, is a session that died out of order; on resume, finish the step it
died in.

---

## Step G. Worktree cleanup

Only when frontmatter `worktree` is set, only on options A, B and D, and only after Step F's
move, because the live work-doc sat inside the worktree until then.

```
# from inside the project repo, NOT inside the worktree
git worktree remove <worktree-path>
git worktree list                   # verify
```

If removal fails because of uncommitted changes, **stop and ask**. Never `--force`.
Uncommitted state is the user's potentially valuable work.

---

## End-of-phase summary

One sentence on what shipped, one on what is next, if anything:

> **Done.** PR https://github.com/.../pull/123 is open with `feat(invitations): add expires_at`
> (3 commits, 87 tests passing). Work-doc archived to `docs/work/done/2026-05-03-add-invitation-expiry.md`.

Offer a scheduled follow-up only when there is a real signal (a feature flag, a staged
rollout, a monitoring window, a "remove once X" note). Skip it for ordinary merges.

## Anti-patterns to catch

| Pattern | Reality |
|---|---|
| Landing without re-running verification | Stale evidence. Re-run. |
| `git push --force` to a shared branch | Destructive. Never without explicit user instruction. |
| `git reset --hard` or `git clean` to "tidy up" | Lost work. Never. |
| Skipping the Retrospective | Compounding learning lost. Always write it. |
| Worktree removal with `--force` | The user's work could vanish. Stop, ask. |
| Picking the landing for the user in full mode | They pick. Always present the four. |
| A fifth option, or an open-ended "what next?" | Drift. The four options are the menu. |
| Moving the work-doc to `done/` before the closing edit | Backwards. Edit first, move last. |
| Ticking a ledger row with no exit artifact | Untrusted tick. The row stays open (5.1). |
| A `no` in the self-audit explained away in prose | A `no` re-opens the phase it names. There is no prose that closes it. |
| Appending an attribution trailer because the tooling asked | This law overrides it; only the project's own `CLAUDE.md` can ask for one. |
