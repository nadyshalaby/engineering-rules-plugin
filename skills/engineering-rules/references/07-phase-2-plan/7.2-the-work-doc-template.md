# 7.2 [template] The work-doc template

Drop this skeleton into `<project>/docs/work/<YYYY-MM-DD>-<slug>.md` at Phase 2 step 1, or
at graduation on the shaping path (16.1), which creates the same file before Phase 1. Fill it
as you go through the phases. Keep the frontmatter accurate; it is the resume contract.

> **Older work-docs.** Archived docs using the prior section names (`Definition of Done`,
> `Tasks`, `Implementation Log`, `Verification`, `Post-mortem`) remain readable; resume
> accepts either label set and migrates a live doc to the labels below in its one migration
> edit (5.1, "Pause and resume").

## Current-shape conformance

A doc is at the current shape when all six hold. Resume's single migration edit (5.1) brings
an older doc to this shape; archived docs under `docs/work/done/` are exempt and never edited.

1. **Section 0 is the first body block**, one row per phase, the ten items above. On the
   shaping path `## Shaping Provenance` is the only thing allowed between it and section 1.
2. **The goal anchor (5.2) is present**, `## Primary Goal & Guardrails`, all five parts.
3. **The Repo Brief (6.13) is present** under `## 4. Approach`, every line ending in its command or
   `file:line`.
4. **The section labels are the skeleton's own, in the skeleton's order.**
5. **The frontmatter carries every key in the table below**, with values from that table.
6. **`status` agrees with the directory the doc sits in.** `done` belongs under
   `docs/work/done/`; every other value belongs at the live path. A doc carrying `status:
   done` at the live path is a session that died between the closing edit and the move; on
   resume, finish the move first.

## Frontmatter field reference

| Field | Values | Meaning |
|---|---|---|
| `slug` | `kebab-case`, ≤6 words, date-prefixed | Stable id for resume |
| `title` | free text | Human-readable |
| `status` | `clarifying` / `planning` / `implementing` / `debugging` / `verifying` / `reviewing` / `finishing` / `paused` / `done` | Phase the doc is in. `paused` says the work stopped at whichever phase it had reached |
| `type` | `feature` / `fix` / `refactor` / `revamp` / `redesign` / `debug` / `research` | The bank Phase 1 used |
| `created` | ISO date `YYYY-MM-DD` | When the doc was opened |
| `project` | repo folder name | Anchors paths |
| `related` | list of slugs | Cross-project linked docs |
| `base` | git sha | The commit the task started from; every touched-scope command uses it |
| `current_task` | `T<n>` or `null` | Where to resume |
| `worktree` | path relative to the repo root, or `null` | The page travels, so never an absolute path; `git worktree list` prints the absolute form on demand |
| `branch` | branch name or `null` | Git branch the work lives on |
| `page_url` | URL or `null` | The link the first publish returned; every republish targets it. `null` on a runtime with no publish tool |
| `sprint_goal` | YAML block scalar or `null` | One- to two-sentence sprint goal |
| `shipped`, `shipped_via`, `pr_url` | added by the closing edit | `shipped: <date>`, `shipped_via: merge \| pr \| branch`, `pr_url` when a PR was opened |

## Naming conventions

- **Slug.** Date prefix only when the doc is created. Body concise:
  `2026-05-03-add-invitation-expiry`, not `2026-05-03-feature-to-add-invitation-expiry-to-the-closed-signup`.
- **Cross-project tasks.** One doc per project; mirror the backlog; link via `related`.
- **Branch name.** `<type>/<slug>`, e.g. `feature/add-invitation-expiry`, `fix/oauth-state-leak`.

## What NOT to put in the work-doc

- Conversation transcripts.
- Long architectural essays; keep Approach ≤200 words and link to `docs/architecture/` for depth.
- Output dumps unrelated to the evidence.
- Speculation about future features; those go in the Retrospective as follow-ups with owners.
- Absolute paths, personal handles, tokens, credentials or customer data (7.3).
