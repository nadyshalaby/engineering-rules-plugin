# 7.1 [phase] Phase 2, Plan and gate

*Full mode only. Quick mode restates its approach in chat at the end of Phase 1 (6.1,
step 6) and goes straight to implementation.*

## Step 1. Create the work-doc

Create `docs/work/<YYYY-MM-DD>-<slug>.md` from the template (7.2), or, when shaping (16.1)
already created it, open it and confirm it is at the template's shape. Whoever creates the
file writes `## 0. Phase ledger` into it first, with the ten full-mode items, and this step
confirms the block is present and in sync. Save. Where the runtime can publish a page, the
first publish happens right after this first save, and the returned link is written into
frontmatter `page_url` and said once in chat (7.3).

## Step 2. Fill the plan

The sections in order, per 7.2:

0. **Phase ledger**, the ten items, item 2 in progress.
1. **Original ask**, the user's words, verbatim, not summarized.
2. **Primary Goal & Guardrails**, the anchor locked in Phase 1, all five parts.
3. **Clarifying Q&A**, every question asked and the answer given.
4. **Acceptance criteria**, observable, checkable statements. Each one gets a task.
5. **Approach**, the design, the layering, the files it will touch, the alternatives you
   rejected with the reason, the repo brief (6.13) from Phase 1, and the execution stages.
6. **Sprint backlog**, the tasks, each with the files it may write and its verify line.
7. **Daily updates**, empty until Phase 3.
8. **Sprint review**, empty until Phase 4.
9. **Retrospective**, empty until Phase 6.

## Rules the plan itself must obey

- **Every acceptance criterion has at least one covering task.** A criterion with no task
  is a criterion nobody will meet.
- **Every task names the files it may write.** Placement is decided here, against section
  2.2, not discovered while implementing. Every new file's path and name is written down.
- **Every task names how it will be proven**, as `→ verify: <one-line check>`.
- **Every task is one commit's worth of work**, five to thirty minutes, and lists production
  files only; test authoring is the testing stage's own task.
- **Order the tasks into stages** (9.1): foundation first for every file two later tasks
  both write, then modules in dependency order, then assembly, then testing.
- **The plan cites, it does not assert.** Any claim about how the code behaves today comes
  with a `file:line`.
- **A UI-bearing task names the design spec** it builds against, or names authoring one as
  its first deliverable (15.1), states the read and the dials (15.20), and carries the
  composition plan (15.22) in its Approach when the surface is a marketing page.

## Step 3. Worktree, when Phase 1 chose one

When the workspace question (6.4, Q2) chose a separate copy, create it now, before the gate,
so the user approves a plan whose workspace already exists. Quick mode runs this same
procedure at the close of Phase 1.

```
# Path priority: an existing .worktrees/ dir, then an existing worktrees/ dir, then a
# CLAUDE.md override, then ask. Default: .worktrees/<slug> at the repo root.
git check-ignore -q .worktrees || { echo '.worktrees/' >> .gitignore; git add .gitignore; git commit -m 'chore: ignore .worktrees'; }
WORKTREE_PATH="$(git rev-parse --show-toplevel)/.worktrees/<slug>"
git worktree add "$WORKTREE_PATH" -b "<type>/<slug>"
cd "$WORKTREE_PATH"
<package manager install command>      # from the repo brief, never guessed
<project test command>                 # once, for a clean baseline; paste the result line
```

On Claude Code, where the repository has no worktree convention of its own, the `EnterWorktree`
tool (or `claude --worktree <slug>` at launch) does the same job: it creates the worktree under
`.claude/worktrees/<slug>`, copies in the files a `.worktreeinclude` names, and `ExitWorktree`
leaves it. Record its path and branch the same way. The block above stays the procedure for
every other runtime and for a repository that already keeps its worktrees elsewhere.

Write the path, relative to the repo root, into frontmatter `worktree`, and the branch into
`branch`. Every later command in the task runs inside the worktree. Never create a worktree
without the ignore check; an un-ignored `.worktrees/` pollutes the user's status forever.

## Step 4. The gate

**Stop and ask for approval, through the wizard tool. This is full mode's mandatory user
gate.** Present: what you are going to build, the acceptance criteria, the approach in a few
lines, what you are deliberately not doing, and any decision you want the user to make.
Recommend an option; do not present a neutral survey.

```
- Text: The plan is written at docs/work/<slug>.md. In short: <three plain sentences>.
  Shall I go ahead?
- Header: Plan
- Options:
  - A. Approved, go ahead (Recommended)
  - B. Change something first
  - C. Not this, let's rethink
```

Do not write implementation code before the user approves. Write the answer into the
work-doc's Clarifying Q&A. After approval, the remaining phases run without further gates
unless a phase says otherwise (a scope-changing spec-review finding, a Critical adjudication,
the landing menu).

## Step 5. Close

Tick item 2 with the approval quoted, open item 3, save, re-print, and read 8.1.
