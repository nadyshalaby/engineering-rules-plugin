# 4.3 [route] Full mode, when it is named

**Full mode runs only when the user names it.** It is quick mode plus a written plan, a
user gate, a spec review, and a durable record.

## What full mode adds

| Addition | What it buys |
|---|---|
| **Phase 2, plan and gate** | A written work-doc: the original ask, the clarifying Q&A, the goal anchor (5.2), the repo brief (6.13), acceptance criteria, the approach, and a task backlog with a file allowlist and a verify line per task. Then a stop, through the wizard tool, for the user to approve before any code is written. |
| **Phase 2.5, spec review** | An audit of that plan against itself, against the order it implies, and against the project's rules, before implementation starts. |
| **A durable work-doc** | `docs/work/<YYYY-MM-DD>-<slug>.md`, edited at every phase tick, moved under `docs/work/done/` when it ships. This is what makes a full-mode task resumable across sessions. |
| **Phase 6's four options** | Merge locally, push and open a pull request, keep the branch as-is, or discard, offered through the wizard tool as a choice rather than assumed. |

## The ship bar

A change is done when all of these are true, and not before:

- Every acceptance criterion has a covering task, and every task is ticked with evidence.
- The build passes, the application boots, and the primary path was exercised (11.3).
- Both scouts have run at every stage end and at Phase 5 start, and every row is dispositioned.
- The five review checks and the finding challenge (12.8) have run, and every surviving finding is
  fixed or has explicit user sign-off to defer.
- The law self-audit (1.7) has no `no`.
- The work-doc is current with the code, not with the plan.

## The phase ledger in full mode (5.1)

Ten items, written into `## 0. Phase ledger` of the work-doc **and** printed in chat. The
list is in section 5.1 and nowhere else. The checkbox and the written entry land together;
a tick with nothing written beside it is not a tick.

## Resuming, adopting and stale docs

- **Resuming.** Read the work-doc back. The ledger says where you stopped; the last written
  entry says what was true when you did. Re-print the ledger, restore it into the todo
  tracker if the runtime has one, set the first open phase to in progress, and read that
  phase's reference file before doing anything.
- **Adopting.** A work-doc from an earlier session, or from someone else, is adopted by
  reading it in full and re-deriving every fact in it from the code before acting. A
  pre-derived fact has a shelf life shorter than a session. The repo brief's commands are
  re-run, not trusted.
- **A stale doc is a defect in the process, not just in the file.** If the doc disagrees
  with the code, the code wins, the doc is corrected in the same edit that resumes, and the
  reason it drifted is written into the Retrospective.

## Pausing

When the user signals a pause (*"let's stop here"*, *"pick this up tomorrow"*, *"come back
to this"*), write a checkpoint before you stop: the ledger as it stands, frontmatter
`status: paused`, what is in the working tree, what is proven and what is not, and the
single next action. A pause with no checkpoint is an abandoned task. Never commit, discard
or archive on a pause; the working tree is left exactly as it is.
