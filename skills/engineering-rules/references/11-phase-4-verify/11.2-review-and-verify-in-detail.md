# 11.2 [protocol] Verify, in detail

Phase 4 proves the **original ask** is met. Phase 5 (12.1) proves the **code is good**. Both
run after the last Sprint Backlog checkbox is ticked, and this file is Phase 4's detail; the
five checks, the challenge and the decision table (12.9) live in group 12 and are not restated here.

**Rule.** Evidence before claims. Every "passes", "done", "works" is backed by output you ran
in THIS session, pasted, not remembered. Read the claim-integrity procedures (1.5 reference)
before you write a single row.

Phase 4 has four parts, in every mode: the **Evidence Ledger**, the **three-layer
re-verify**, the **ship gate** (11.3), and the **list of what was not reached**. Cross-package
verification (11.4) joins when the change spans more than one package.

---

## Part 1. The Evidence Ledger, per-item proof

One row per Sprint Backlog task AND per acceptance bullet. No item ships on a bare checkmark.

| Column | Meaning |
|---|---|
| Item | Task ID (`T3`), acceptance bullet (`AC2`), scout row (`scout.perf`, `scout.law`) or ship-gate row (`ship.build`, `ship.boot`, `ship.smoke`). |
| Type | `task`, `acceptance`, `protocol` or `runtime`. |
| Claim | One line: what this item asserts is true now. |
| What I ran | The exact command, test, grep or manual step that proves it, as run. |
| Proof sample | A REAL, trimmed slice of the output, the few lines that show the pass. Never a summary, never invented. |
| Result | ✅ pass / ❌ fail / `⏭ skipped` with a reason (ship-gate rows only). |

Worked rows:

| Item | Type | Claim | What I ran | Proof sample | Result |
|---|---|---|---|---|---|
| T3 | task | Expired tokens are rejected with 403 | `bun test invitations` | `✓ rejects expired token → 403 (4 pass)` | ✅ |
| AC2 | acceptance | Lint clean | `biome check src/` | `Checked 142 files. No fixes needed.` | ✅ |

**Ledger rules.**

- Cover EVERY task and EVERY acceptance bullet. A missing row is an unproven item; treat it
  as ❌.
- The proof sample is trimmed but real: copy the true lines that show the result, then cut
  the noise. Do not paraphrase output into prose.
- A row with no command is not a row. Write "not verified" and why, rather than implying
  proof that does not exist.
- A ❌ row blocks Phase 5. Re-open Phase 3 (5.1, "Loop-back"), or 3b when stuck.
- Each scout's Phase 5-start staging table (or its `covered N of M, no candidates` line) is
  itself a row, `scout.perf` and `scout.law`, type `protocol`.
- The three ship-gate rows are mandatory in every mode (11.3).
- In full mode the ledger lives in the work-doc's Sprint Review and nowhere else; in quick
  mode it is printed in chat.

The top-level triad and the hygiene checks appear as acceptance rows too:

```
- [ ] All tests pass: fresh test output, exit 0, 0 failures, 0 errors, N > 0 tests ran
- [ ] Linter clean: fresh lint output, 0 errors, warnings only if pre-existing
- [ ] Typecheck clean: fresh typecheck output, 0 errors
- [ ] All Sprint Backlog checkboxes ticked
- [ ] No placeholders, no orphan TODOs, no debug logging left behind
- [ ] No new lint suppressions, no new `!` assertions, no empty catches, no bare Error throws
- [ ] Every new file placed and named per 2.2
- [ ] Manual smoke (if the user opted in for cosmetic parts): steps + outcome logged
```

## Part 2. Three-layer re-verify, prove it without drifting

Run the layers in order, in every mode. The point is that the proof survives a second,
independent look, and never wanders off the goal.

**Layer 1. Fresh triad.** Re-run test, lint and typecheck from a CLEAN state: no warm cache,
all packages. This is the ledger's mechanical backbone.

**Layer 2. Goal-drift re-check.** Trace every ledger proof back to the goal anchor (5.2).
For the North-Star Goal and each Success Signal, name the ledger row that proves it. A
Success Signal with no proving row → the goal is NOT met yet. A proof that serves no
In-Scope bullet → possible drift: justify it against the anchor or cut it.

**Layer 3. Independent re-prove.** Re-earn the proof WITHOUT trusting Layer 1's output:
re-run the ledger's commands from scratch, from a clean checkout or fresh state where the
project allows one, and record what you actually saw. If Layer 3 disagrees with Layer 1,
Layer 1 was stale; investigate before advancing. Re-run any layer whenever the user says
"prove it again"; that is why the layers are named.

## Part 3. The ship gate (11.3), prove it runs

A green triad proves the code is well-formed. It does not prove the app builds, boots or
serves a request. Run the three legs in order and record one ledger row each; the full
protocol, the detection table per ecosystem, the readiness-probe rules and the secrets
guards are in 11.3.

| Leg | Row | Proves |
|---|---|---|
| 1 Build | `ship.build` | Builds clean from a cold cache, and the artifact exists on disk |
| 2 Boot | `ship.boot` | Starts, reaches a real ready signal, tears down clean |
| 3 Smoke | `ship.smoke` | The critical path this task touched works end to end against the running app |

**The contract: a leg is blocking whenever the diff touched something that leg's target
consumes; a recorded skip otherwise; never silently skipped.** A blank row, an `n/a`, or a
missing row counts as ❌. This gate runs in every mode and takes no user opt-in.

## How evidence looks

Bad: *"Tests should pass now. ✓"* Good:

```
$ cd <project> && <test-runner-command>
✓ 87 pass
0 fail
Ran 87 tests across 12 files. [3.42s]
```

Bad: *"Lint is fine."* Good:

```
$ <lint-command> src/
Checked 142 files in 89ms. No fixes needed.
```

If you cannot show the output, you do not know it is true. Re-run.

## Common verification failures, catch yourself

| Failure | What to do |
|---|---|
| Output references caches or "warm" runs | Re-run from a clean state |
| One package green, another not run | Run all packages (11.4) |
| Test command exits 0 but skips suites | Check the count; "0 tests ran" is a fail |
| Linter exits 0 with warnings | Confirm warnings are pre-existing; if new, fix |
| Typecheck "skipped" or "incremental" | Force fresh; delete the incremental cache if needed |
| A check whose failure would have looked like success | Re-do it; see the tells in the 1.5 reference |

## Regression-test red-green cycle, a Layer 3 proof

For bug fixes, prove the regression test actually catches the bug:

```
1. Apply your fix.        ← test passes
2. Revert the fix only, by editing the lines back (never git checkout/restore/stash).  ← test fails; paste it
3. Re-apply the fix.      ← test passes again; paste it
```

This proves the test is sensitive to the bug it claims to catch.

## Part 4. Close the phase by saying what you did not reach

List, plainly: what was not tested, what was tested only by proxy, and what you are taking
on trust. That list is the honest half of a green ledger, and it is an exit artifact (5.1).
Then tick Phase 4, re-print the ledger, and read 12.1.

## After review, back to Phase 4 if anything changed

If Phase 5 fixed anything, Phase 5 closes with the triad on the touched scope, and Phase 6
Step A re-runs verification on the pre-land state. New code means new evidence; nothing
from this pass carries over as proof of code that changed after it.
