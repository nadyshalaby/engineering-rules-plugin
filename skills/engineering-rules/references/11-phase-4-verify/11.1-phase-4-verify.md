# 11.1 [phase] Phase 4, Verify

**Prove every claim with fresh output, or do not make the claim.** Runs in full in every
mode. This is the phase in outline; 11.2 is the detail, 11.3 the ship gate, 11.4 the
cross-package check when the change spans packages. Read the 1.5 reference before writing
a row.

## The Evidence Ledger

One row per acceptance criterion and per task. Four columns:

| Claim | Command run | Real output (trimmed) | Verdict |
|---|---|---|---|

Rules that make the ledger worth having:

- **The command is the one you actually ran**, pasted, not described.
- **The output is real and fresh**, from this run, not remembered from earlier and not
  summarized. A number you did not just count is already wrong.
- **A row with no command is not a row.** Write "not verified" and say why, rather than
  implying proof that does not exist.
- **A skipped leg is a recorded skip**, with the reason, never silence.

## The three layers

1. **Layer 1, the claim itself.** Re-run the check for every acceptance criterion. Not the
   whole suite as a proxy — the specific thing being claimed.
2. **Layer 2, the goal.** Read the goal anchor (5.2) again. Does what you built meet the Primary
   Goal and the Success Signals, and did any Guardrail move? Drift found here is a finding,
   not a footnote.
3. **Layer 3, the neighbours.** Run the project's full gate. A change that fixed its own
   target and broke something adjacent has not passed.

## The ship gate

Three legs, each either proven or explicitly skipped with a reason:

| Leg | Passes when |
|---|---|
| **Build** | The project's real build command completes clean. |
| **Boot** | The application starts and reaches a ready state. |
| **Smoke** | The primary changed path was exercised end to end and produced the right result. |

Whether a leg is blocking depends on what the diff touched. A library with no entry point
has no boot leg — that is a recorded skip, not a pass. **A skip that is not recorded reads
as a pass, and that is the failure this gate exists to stop.**

## Verifications that can fail silently

Any of these means the check proved nothing, and it is re-done:

- output redirected to `/dev/null`
- an `|| echo clean` or similar swallowing the failure
- an exit code lost through a pipe
- a loop that lost the tool partway and kept going
- an unquoted variable that made the scope empty
- a scan whose input list was shorter than the thing being scanned

**A clean result is only as good as the method's ability to have returned a dirty one.** If
you cannot show the check failing on a planted defect, you have not shown it passing. A red
anywhere in this phase re-opens Phase 3 (5.1, "Loop-back"); never patch inside Phase 4.

## Close the phase by saying what you did not reach

List, plainly: what was not tested, what was tested only by proxy, and what you are taking
on trust. That list is the honest half of a green ledger.
