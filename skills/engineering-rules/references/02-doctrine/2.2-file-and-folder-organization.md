# 2.2 [law] File and folder organization

Where a file lives and what it is called are not taste. They are a contract, and this
section is that contract. It binds every file you create and every file you move. Read it
at Phase 1 step 2 (to detect the repo's convention) and again before any file is created.

## Precedence, before anything else

**Read the repository's existing layout first, and obey it.** A structure already in the
code outranks the structure written here, because consistency inside one codebase is worth
more than agreement with any external standard.

1. **Detect.** Before writing a file, look at where its siblings live. Read any
   `CLAUDE.md`, `AGENTS.md`, `README`, `ARCHITECTURE.md` or `CONTRIBUTING.md` that
   documents a layout. Look at the two or three most recently added files of the same kind.
2. **State it.** Write the detected convention down in one or two lines before you create
   anything: *"services live at `src/<domain>/<domain>.service.ts`, types flat beside them
   in `<domain>.types.ts`, tests beside the file they test."* An undetected convention is
   one you are about to break.
3. **Obey it exactly.** Every new file matches it. Not approximately, not "close enough",
   not "the newer style I prefer". If the repo keeps its types flat beside the service,
   yours goes flat beside the service, even though this section would have put it in
   `types/`.
4. **Fall back only into a genuine gap.** Where the repo has made no decision — a kind of
   file it has never had — the structure below is the decision. Say that you are making it.
5. **Never migrate as a side effect.** Moving existing files to match anything is its own
   task with its own approval. A feature that also relocates twelve files is a feature whose
   diff nobody can review. Note the drift, finish the feature, offer the migration.

**Two layouts in one repository is the failure this ordering exists to prevent.** A new
convention introduced beside an old one does not replace it; it doubles the number of places
a reader has to look, permanently.

## The three rules everything below is derived from

1. **A file's path says where it belongs. A file's name says what it is.** Path answers
   *which part of the system* and, through its role folder, *which role*; name answers
   *which concern and which role*. The role is written in both places on purpose: the
   folder groups it, the suffix keeps it visible where only the file name shows, in an editor
   tab, a stack trace or a grep result. Nothing else repeats:
   `users/services/users.service.ts`, never `users/services/users-module-service-file.ts`.
2. **One concern per file, and the name states it.** This is the one-construct rule with an
   address attached. A file holding a service holds one service and nothing else — not its
   types, not its constants, not a second helper class.
3. **A name is written once and never varied.** The same concept is spelled the same way in
   every file name, folder name, symbol and import across the whole repository. `user`, or
   `users`, or `account` — pick one and it is the only one.

## Naming, exactly

### Folders

| Rule | Value |
|---|---|
| Case | `kebab-case`, always, with one exception: a component folder is named for the component it holds, `PascalCase`, so the folder and the file inside it are the same token. Never `camelCase` or `snake_case`. |
| Words | Lowercase ASCII letters, digits and single hyphens. No spaces, no underscores, no dots, no capitals. |
| Number | **Singular for a thing, plural only for a collection of peers.** `user-profile/` holds one feature; `services/` holds that feature's services; `components/` holds many components. A folder named `utils/` fails this rule twice: it is a collection of nothing in particular. |
| Depth | Four levels below the source root is the ceiling. Past that, the hierarchy is doing work a name should do. |
| Nesting | A feature folder, `shared/` and every role folder (the Folder column below) exist from their first file, one or many. A component folder exists to hold **two or more** files that belong together, the parent and its sub-components; one holding a single file is deleted and the file moves up into `components/`. |
| Never | `misc/`, `common/`, `shared/` at feature level, `helpers/`, `utils/`, `stuff/`, `new/`, `old/`, `v2/`, `temp/`, or anything dated. A folder whose name does not say what is inside it is a folder nobody can find anything in. |

`shared/` and `common/` are permitted **once**, at the top level of a package, for code with
at least two consumers in different features. Anywhere else they are a naming failure.

### Files, by kind

Every file name is `<subject>.<role>.<ext>`, in `kebab-case`, with the two exceptions marked
below. The subject is the concept; the role is what the file does with it, and the role also
names the folder the file sits in.

| Kind | Name | Folder | Example |
|---|---|---|---|
| Service / domain logic | `<subject>.service.<ext>` | `services/` | `user-profile.service.ts` |
| HTTP controller | `<subject>.controller.<ext>` | `controllers/` | `user-profile.controller.ts` |
| HTTP route module | `<subject>.routes.<ext>` | `routes/` | `user-profile.routes.ts` |
| Data access | `<subject>.repository.<ext>` | `repositories/` | `user-profile.repository.ts` |
| Middleware | `<subject>.middleware.<ext>` | `middleware/` | `require-auth.middleware.ts` |
| Guard / policy | `<subject>.guard.<ext>` | `guards/` | `owns-profile.guard.ts` |
| Types and interfaces | `<subject>.types.<ext>` | `types/` | `user-profile.types.ts` |
| Enums | `<subject>.enums.<ext>` | `enums/` | `user-profile.enums.ts` |
| Constants | `<subject>.constants.<ext>` | `constants/` | `user-profile.constants.ts` |
| Config | `<subject>.config.<ext>` | `config/` | `database.config.ts` |
| Validation schema | `<subject>.schema.<ext>` | `schemas/` | `user-profile.schema.ts` |
| Database schema / model | `<subject>.model.<ext>` or the ORM's own convention | `models/`, or where the ORM insists | `user-profile.model.ts` |
| Mapper / serializer | `<subject>.mapper.<ext>` | `mappers/` | `user-profile.mapper.ts` |
| Error types | `<subject>.errors.<ext>` | `errors/` | `user-profile.errors.ts` |
| Event / message | `<subject>.events.<ext>` | `events/` | `user-profile.events.ts` |
| Job / worker | `<subject>.job.<ext>` | `jobs/` | `send-welcome-email.job.ts` |
| Test | `<the file it tests>.test.<ext>` | `tests/` | `user-profile.service.test.ts` |
| Fixture | `<subject>.fixture.<ext>` | `fixtures/` | `user-profile.fixture.ts` |
| Migration | the tool's required format, unchanged | `db/migrations/`, or where the tool insists | `0007_add_profile_avatar.sql` |
| API client (frontend) | `<subject>.api.<ext>` | `api/` | `user-profile.api.ts` |
| **UI component** | `PascalCase.<ext>`, no role suffix | `components/` | `UserProfileCard.tsx` |
| Page / screen | `PascalCase.<ext>`, like a component | `pages/`, or `screens/` where the framework says screen | `UserProfilePage.tsx` |
| **Hook** | `use-<subject>.<ext>` | `hooks/` | `use-user-profile.ts` |
| Component styles | `<Component>.module.<ext>` | `styles/` | `UserProfileCard.module.css` |
| Style tokens / class-name maps | `<subject>.styles.<ext>` | `styles/` | `button.styles.ts` |
| Store / state slice | `<subject>.store.<ext>` | `stores/` | `session.store.ts` |
| Barrel / public surface | `index.<ext>`, and only where this section allows one | the folder it fronts | `index.ts` |

**The folder is the role's plural.** A role whose word has no plural keeps its name
(`middleware/`, `config/`, `api/`). A file whose role is in this table has exactly one folder
it may sit in, inside whichever scope owns it: a feature, or `shared/` when no feature owns
it; the source root keeps only the closed list below. A file of a role this table does not
name gets a row here first, never a folder invented on the spot.

**The two exceptions are deliberate.** A UI component file is `PascalCase` because the file
name and the exported component must be the same token, and a hook carries `use-` because
its framework enforces the prefix on the symbol. Everything else is `kebab-case` with a role.

#### How this table meets the inline-type ban

The code doctrine (`SKILL.md` 1.1, 2.1) bans a type of two or more properties from being declared inside an
implementation file. That ban has two tiers, and this table sits across both.

- **The mechanical tier** is keyed to five role names, `service`, `controller`, `routes`,
  `middleware` and `guard`. A grep can decide those, and it does.
- **The semantic tier** is one construct per file, and it is the wider of the two. It covers
  every other role in the table above, `repository`, `model`, `mapper`, `job`, `events`,
  `errors`, plus components, pages and route modules.

So a `user.repository.ts` carrying a four-property inline type is a defect under the semantic
tier even though no grep fires on it. **The table is the placement contract; it does not narrow
the ban.** Where a role appears here and not in the five, the type still moves to the `.types`
file in the feature's `types/` folder, it is just a reviewer rather than a regex that catches it.

### Symbols inside the file

| Symbol | Case | Note |
|---|---|---|
| Class, interface, type alias, enum type | `PascalCase` | Never prefix an interface with `I`. |
| Enum member | `SCREAMING_SNAKE_CASE` | |
| Function, method, variable, parameter | `camelCase` | |
| Module-level constant | `SCREAMING_SNAKE_CASE` | Only for a true constant; a computed default is `camelCase`. |
| React / UI component | `PascalCase` | Matches its file name exactly. |
| Hook | `useCamelCase` | Matches its file name's subject exactly. |
| Boolean | `is` / `has` / `can` / `should` prefix | `isActive`, `hasAccess`, never `active` for a boolean. |
| Function name | verb first | `getUserProfile`, `buildQuery`, `assertOwner`. A noun-named function is a value with a call site. |
| Private field | the language's own private marker | Never a leading underscore where the language has real privacy. |

**The file name and its primary export agree.** `user-profile.service.ts` exports
`UserProfileService`. `use-user-profile.ts` exports `useUserProfile`. `UserProfileCard.tsx`
exports `UserProfileCard`. A file whose name and export disagree is a file nobody greps
successfully.

### Names that are refused on sight

`data`, `info`, `item`, `obj`, `temp`, `val`, `res`, `result`, `handle`, `process`,
`manager`, `helper`, `util`, `utils`, `base`, `core` used as a whole name, `MyThing`,
`ThingImpl`, `AbstractThing` where there is one implementation, and any name whose meaning
requires reading the body. A name that needs a comment is the wrong name.
## Hierarchy, exactly

### The rule that decides every placement

**Group by feature first, then by role inside the feature.** A feature folder is a piece of
the product. Inside it, every file sits in the folder named for its role: the service in
`services/`, its types in `types/`, its tests in `tests/`. Both other arrangements are
refused. A `services/` folder at the source root holding every service in the system puts
one change across five directories and makes deleting a feature an archaeology exercise. A
feature folder with its role files lying flat beside each other hides what the feature is
made of behind a wall of suffixes; a repository already built that way keeps it under
Precedence, and a repository that has not decided never starts one.

```
GOOD, feature first, role folders inside
src/
  user-profile/
    services/
      user-profile.service.ts
    controllers/
      user-profile.controller.ts
    types/
      user-profile.types.ts
    tests/
      user-profile.service.test.ts
  billing/
    services/
      billing.service.ts
    ...

REFUSED, role first at the source root
src/
  services/
    user-profile.service.ts
    billing.service.ts
  types/
    user-profile.types.ts
    billing.types.ts

REFUSED, feature first but flat
src/
  user-profile/
    user-profile.service.ts
    user-profile.controller.ts
    user-profile.types.ts
    user-profile.service.test.ts
```

The source root keeps a few folders of its own for what no feature owns, and they are a
closed list rather than a judgement call. Beside the feature folders and the process entry
files, a folder at the source root is allowed only for these:

| Folder | Holds | The test it has to pass |
|---|---|---|
| `components/` | the generic UI kit | no component in it knows any feature's name |
| `hooks/` | hooks used by two or more features | a hook used by one feature lives in that feature |
| `stores/` | state shared across the tree | state one feature owns lives in that feature |
| `lib/` | framework glue, formatters, error mappers | nothing here imports a feature |
| `config/` | configuration the whole app reads | not a feature's own settings |
| `db/` | the database schema and, under it, the ordered `migrations/` | ordering is global, so ownership cannot be local |
| `routes/` | route definitions the app mounts, delegating immediately | no logic: a route file names a controller and nothing else |
| `styles/` | tokens, resets, global sheets, the generic kit's stylesheets | a feature's styling stays with the feature |
| `types/` | types genuinely global to the app | a type one feature owns lives in that feature |
| `tests/` | tests of the source-root folders that have no `tests/` of their own, and of root files such as `app.ts` | a test of a feature's file lives in that feature's `tests/` |
| `shared/` | see the barrel rules below | earns its place on the second consumer, never the first |

Anything not on that list groups by feature. A folder on the list still has to pass the test in
its own row: **a file lands there because it has no feature that owns it, never because a second
feature happened to import it once.** The moment you can name the feature a file belongs to, it
moves there, whatever the list says. `shared/` is a feature-shaped scope: the same role folders
inside it, `shared/services/`, `shared/types/`, `shared/tests/` and the rest.

### A feature folder, from the outside in

```
<feature>/
  services/
    <feature>.service.ts        the one entry point other features may import
  controllers/
    <feature>.controller.ts     transport binding, if this feature is exposed
  repositories/
    <feature>.repository.ts     data access
  types/
    <feature>.types.ts          every type ≥ 2 properties
  schemas/
    <feature>.schema.ts         input validation
  constants/
    <feature>.constants.ts      named literals
  errors/
    <feature>.errors.ts         this feature's error types
  tests/
    <feature>.service.test.ts   every test the feature owns
  fixtures/
    <feature>.fixture.ts        test data, from the first test that needs it
```

A frontend feature adds `pages/`, `components/`, `hooks/`, `api/` and `styles/`; the concrete
layouts below show it.

**A role folder appears with its first file and holds one file or many.** Its existence is
decided by the skeleton, never by a count, so a feature with one service still has a
`services/` folder. **A component folder appears only when a component has parent-only
sub-components**: `components/UserProfileCard/UserProfileCard.tsx` beside
`components/UserProfileCard/UserProfileAvatar.tsx`. A component with no sub-components is a
file directly in `components/`. No other folder kind exists inside a feature; a grouping that
is neither a role folder nor a component folder is a second layout.

### Import direction, and it is one-way

| From | May import | May never import |
|---|---|---|
| A feature | `shared/`, `lib/`, its own role folders, another feature's **public surface only** (its service file, see Barrels below) | any other file of another feature, its `types/`, `repositories/`, `constants/` and the rest; a route file |
| `shared/` / `lib/` | other `shared/` / `lib/` modules | any feature |
| `components/` (generic UI) | `lib/`, other generic components | any feature, any store, any API client |
| A route file | features | another route file |
| A test | anything it is testing | nothing that changes global state |

**A cycle between two features is a design error, not an import problem.** The shared concept
moves to `shared/` and both depend on it. Do not break a cycle with a lazy import.

### Where each kind of thing lives

| Thing | Location |
|---|---|
| Business logic | the feature's `services/` |
| Anything reachable over the network | the feature's `controllers/` or `routes/`, one service call deep |
| Every type of 2+ properties | the feature's `types/`, never inline in an implementation file |
| Every named literal | the feature's `constants/` |
| Environment access | exactly one module for the whole application; nothing else reads the environment directly |
| Database schema | `db/`, one place, the tool's own convention, never split across features |
| Migrations | `db/migrations/`, one folder for the whole app, filenames in the tool's required format, never edited after they run |
| Generic UI | the source root's `components/` |
| Feature UI | the feature's `components/`, its screens in `pages/` |
| Cross-feature state | the source root's `stores/` |
| A helper used by exactly one feature | inside that feature, in the folder its role names |
| A helper used by two or more features | `shared/`, in the folder its role names, on its second consumer and not before |
| Tests | the `tests/` folder of the scope that owns the file under test: the feature's, `shared/`'s, or the source root's |
| End-to-end tests | one `tests/` folder at the repository root, since they belong to no scope |
| Fixtures and factories | the `fixtures/` folder beside the `tests/` that use them, or `shared/fixtures/` on the second consumer |
| Scripts | one top-level scripts folder |
| Documentation | one top-level docs folder |
| Generated output | its own folder, git-ignored, never hand-edited |

### Barrels and public surface

A folder's public surface is what other folders may import from it.

- **A feature exposes one entry point.** Prefer the named service file in `services/`. Add
  an `index` file only where the language or bundler requires one for a package boundary.
- **`index` files re-export and nothing else.** No logic, no side effects, no instantiation.
- **A barrel that re-exports everything is refused**, and there are two reasons: it makes
  the public surface unreadable, and it defeats tree-shaking, so it is both a design and a
  performance defect.
- **Never re-export a symbol from a non-canonical source.** There is exactly one path a
  symbol is imported from, and it is where the symbol is declared.

## Conventions

| Convention | Rule |
|---|---|
| Extensions | One per language per repository. Pick `.ts` or `.js`, `.tsx` or `.jsx`, and never mix. |
| Line endings, encoding | LF, UTF-8, no BOM, everywhere. |
| Trailing newline | Every file ends with exactly one. |
| Path aliases | If the project has them, use them for anything crossing a feature boundary. Relative imports stay inside one feature. `../../../` is a placement error, not an import style. |
| Import order | External packages, then aliased internal, then relative, then styles. One blank line between groups. |
| Config files | Repository root, at the tool's expected name. Never nested to hide them. |
| Env files | `.env.example` is committed and complete; no other env file ever is. |
| Dot-folders | Only where a tool requires the name. |
| Case sensitivity | Treat the filesystem as case-sensitive whatever your machine does. Two files differing only in case is a broken build on someone else's laptop. |
| Ordinals in names | Never. `service-2.ts`, `user-new.ts`, `handler-old.ts` are all the same defect: a second thing that needed a real name. |
| Dead paths | A file nothing imports is deleted, not kept "for reference". Git is the reference. |

## Concrete layouts

These apply where the repository has not already decided. They are the fallback from the
precedence rules, not an override of them.

### A backend service

```
src/
  <feature>/                    one folder per feature, kebab-case
    controllers/
      <feature>.controller.ts
    services/
      <feature>.service.ts
    repositories/
      <feature>.repository.ts
    types/
      <feature>.types.ts
    schemas/
      <feature>.schema.ts
    constants/
      <feature>.constants.ts
    errors/
      <feature>.errors.ts
    tests/
      <feature>.service.test.ts
  shared/                       ≥ 2 consumers in different features, same role folders
    services/
    types/
    tests/
  lib/                          third-party glue, clients, transports
  config/                       one module per config domain
  db/
    schema.ts
    migrations/
  tests/                        tests of lib/, config/, app.ts and server.ts
  app.ts                        composition root: wiring only, no logic
  server.ts                     process entry: start and stop only
tests/                          end-to-end only
scripts/
docs/
```

### A frontend application

```
src/
  routes/                       route definitions only, delegating immediately
  features/
    <feature>/
      pages/
        <Feature>Page.tsx       the screen; `screens/` where the framework says screen
      components/
        <Component>.tsx
        <Parent>/               only when a component has parent-only sub-components
          <Parent>.tsx
          <ParentPart>.tsx
      hooks/
        use-<feature>.ts
      api/
        <feature>.api.ts
      types/
        <feature>.types.ts
      constants/
        <feature>.constants.ts
      styles/
        <Component>.module.css
      tests/
        <Component>.test.tsx
        use-<feature>.test.ts
  components/                   generic UI kit, no feature knowledge, same shape
    <Component>.tsx
    <Parent>/
      <Parent>.tsx
      <ParentPart>.tsx
  hooks/                        cross-feature hooks
  lib/                          framework glue, formatters, error mappers
  stores/                       cross-tree UI state
  styles/                       tokens, resets, and the generic kit's stylesheets
  types/                        only truly global types
  tests/                        tests of components/, hooks/, lib/ and stores/
tests/                          end-to-end only
docs/design/DESIGN.md           the design spec, when the project has UI
```

### A monorepo

```
apps/
  <app>/                        a deployable; the layouts above apply inside it
packages/
  <package>/                    a publishable or importable library
    src/
    index.ts                    the package's only public surface
```

- **An app may import a package. A package may never import an app.**
- **A package never reaches into another package's `src/`.** It imports the entry point.
- Every package name is `kebab-case` and matches its folder exactly.

### A library

```
src/
  index.ts                      the entire public API, and the only export site
  <subject>/                    internal structure, free to change, role folders inside
tests/
```

**A library's public surface is a decision, not a by-product.** Everything not named in
`index` is internal, and may be renamed or removed without ceremony.

## Enforcement

**Placement is checked before the file is written, not after.** The question *where does this
go and what is it called* is answered in the plan, not discovered during implementation.

At review time, every one of these is a finding, with the correct path named in the finding:

| Finding | What it means |
|---|---|
| Wrong location | The file is not where its kind belongs, or not where the repo already puts that kind. |
| Outside its role folder | A file whose suffix names a role sits anywhere but that role's folder in its scope: a `.types` file beside the service, a test beside the file it tests. |
| Wrong name | The case, the role suffix, or the subject spelling breaks a rule above. |
| Name and export disagree | The file's primary export is not the file's name. |
| Type or constant inline | A type of 2+ properties, or a named literal, in an implementation file. |
| Layer leak | An import that crosses a boundary the direction table forbids. |
| Reach-in | An import of another feature's internals rather than its entry point. |
| Orphan folder | A component folder holding one file, or any folder holding nothing after a deletion. |
| Second layout | A new file following a different convention from its siblings. |
| Dead path | A file nothing imports, or a re-export from a non-canonical source. |

**A placement finding is fixed by moving the file, in that same change.** It is the one class
of finding where deferring is worse than fixing, because every import written against the
wrong path makes the move more expensive.
