# 6.14 [check] Investigating unfamiliar code

**One question at a time, answered from the code, with a citation on every claim.**

Use this whenever you need a fact about unfamiliar code — at Phase 1 to learn the ground, and
at Phase 3b to test a hypothesis. The two modes share a method and differ in what they are
looking for.

## Method

1. **State the one question.** Not three. A question that needs "and" is two investigations.
2. **Build the keyword set from the question**, not from the filenames you expect. Include
   the domain word, the likely symbol name, the likely error string, and the framework's own
   term for the thing.
3. **Search widely, then narrow.** Grep the whole scope first; a search restricted to where
   you think the answer lives cannot tell you that you were wrong.
4. **Discard what has already been ruled out**, and say that you did.
5. **Read around every surviving hit.** A filename is not evidence. Open the file, read the
   function, and follow what it calls.
6. **Report the smallest set of citations that actually answers the question.** Every claim
   carries a `file:line` and a quoted snippet.
7. **Name the conventions the change must mirror**, with one canonical example file for each.
8. **List everything you are only partly sure about under `NOT SURE`**, as its own list. Do
   not fold a partial fact into confident prose — that is how a guess becomes a citation
   somebody else trusts.

## In debug mode, two extra obligations

- **Enumerate at least two ways the hypothesis could be FALSE before looking for support.**
  Going looking for confirmation finds it.
- **Trace every assignment site, every read site, and every gating conditional on the
  failure path**, and walk the symptom backwards to the earliest citation in scope that
  could have caused it.

Return a verdict on the hypothesis: supported, refuted, or undetermined — and for
undetermined, the specific evidence that would settle it.

## Verification

1. Does every claim carry a `file:line` and a quoted snippet? (yes / no)
2. Did you open every file you cite, rather than inferring from its name? (yes / no)
3. Is there a `NOT SURE` list, or an explicit statement that nothing was partial? (yes / no)
4. In debug mode, did you enumerate the ways the hypothesis could be false first? (yes / no)
5. Does the report answer the one question asked, and no other? (yes / no)

**Never edit anything during an investigation.** Reading and changing in the same pass is how
you stop being able to tell what the code did before you touched it.
