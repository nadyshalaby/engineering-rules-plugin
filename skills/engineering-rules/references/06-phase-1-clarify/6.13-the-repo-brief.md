# 6.13 [reference] The repo brief

**Build it once, at the end of Phase 1, in every mode, and hand it to everything that
follows.** Every later phase, every helper you brief and every reviewer pass starts from it
instead of re-deriving the stack, the commands, the layout and the layering rule.

## When to build it

At Phase 1, step 5 (6.1), after the question round and before the approach is restated. In
full mode it is written into the work-doc's `### Repo Brief` block under `## 4. Approach`
(7.2) and survives pause and resume with the rest of the doc. In quick mode it is printed in
chat and kept current. Refresh it only when the task itself changes one of its facts (a new
package, a changed test command), and say so when you do.

## What goes in it

Cap it at **~350 words**. It is a briefing, not documentation.

**Every line carries the command or the `file:line` that produced it.** A brief is a pile of
claims about a repo, and a claim the reader cannot check is one they have to take on faith.
Naming the command turns each line from something to believe into something anyone can
settle in one run.

| Line | Content | Shape: the fact, then what proved it |
|---|---|---|
| Stack | language, runtime, framework, package manager | `TypeScript / Node 22 / NestJS / bun` ← `jq -r .packageManager package.json` |
| Commands | the triad, verbatim: test, lint, typecheck, plus build and start where they exist | `bun test` ← ran this session, 41 pass / 0 fail |
| Layout | where each layer lives, one line | `routes in *.controller.ts, logic in *.service.ts` ← `git ls-files 'src/**/*.controller.ts' \| head -3` |
| Layering rule | the one boundary that matters here | `controllers delegate only, services own their data access` ← `CLAUDE.md:24` |
| Rules source | which rule files govern, and who wins on conflict | `project CLAUDE.md at root; stricter wins per SKILL.md Precedence` ← `ls CLAUDE.md ~/.claude/CLAUDE.md` |
| Test convention | where tests live and what they are named | `*.spec.ts beside the source file` ← `git ls-files '*.spec.ts' \| head -3` |
| Design spec | whether `docs/design/DESIGN.md` exists, and its direction | `present, direction: nordic-calm` ← `head -5 docs/design/DESIGN.md` |
| Base commit | the commit the task started from | `a1b2c3d` ← `git rev-parse HEAD` |
| Landmines | facts a newcomer would get wrong on their own | `the ORM lazy-loads relations by default` ← `src/db/orm.config.ts:18` |

A `file:line` citation counts as a command: it is a fact settled by opening one file at one
line.

**A line with nothing to the right of the arrow is not a fact, it is a guess.** Verify it or
drop it. If you did not run the test command this session, do not name it.

## What stays out

- **Anything a task's own file allowlist already says.** The brief is repo-wide, not
  task-specific.
- **Anything visible in the diff.** The brief explains the ground, not the change.
- **Opinions, history, rationale.** No "we used to do X". A brief is facts.
- **Anything you have not verified this session.** A wrong brief is worse than no brief,
  because everything downstream inherits the error at once.

## The contract on the receiving end

Whatever receives the brief, a later phase, a helper, a reviewer pass, treats it as given
and does **not** re-derive it: no rediscovering the stack, no hunting for the test command,
no re-mapping the layout. That is the cost the brief exists to delete.

**"Do not re-derive" bans exploration, not verification.** Re-running one named command to
settle one line before writing code that depends on it is correct behaviour, and it is what
the arrow column is for. And the brief ships with standing permission to refute it, in
words: *if one of these facts is wrong, say so plainly and show the command that proves it.*
Neither half works alone (1.5 reference, "The pairing").
