# 6.15 [check] The end-to-end coverage map

**Every aspect of the task is accounted for before the first question is sent, and the map
is what proves it.** Phase 1 is where truth is collected; a hole in the map is a hole in the
truth, and Phase 3 fills holes with guesses. The map is composed with the question batch
(6.1, step 4), printed with the restatement (6.1, step 6), and kept beside the anchor (5.2)
so every later drift-check can see what was settled, by whom, and on what evidence.

## The aspects, sixteen, always these sixteen

| # | Aspect | The question it answers |
|---|---|---|
| 1 | Value | Who this is for, what changes for them, and how anyone would know it worked. |
| 2 | Actors and permissions | Who can trigger it, who must not, and what each one may see. |
| 3 | Entry points | Where it starts: a screen, an endpoint, a command, a job, an event, a webhook. |
| 4 | Inputs and validation | Every input, its shape, its limits, and what happens to a bad one. |
| 5 | The happy path | The one flow that must work end to end, named step by step. |
| 6 | States and lifecycle | The states the thing can be in, the transitions, and the ones that must be refused. |
| 7 | Data | What is stored and where; migration, backfill, retention, deletion. |
| 8 | Failure paths | Errors, retries, timeouts, partial failure, concurrency, idempotency. |
| 9 | Integrations | Every external call: its contract, its failure, its cost. |
| 10 | Security and privacy | Auth, tenancy, secrets, injection, personal data, audit. |
| 11 | Volume and performance | Real counts from the user's own data, the hot path, the ceiling. |
| 12 | Observability | What is logged, measured and alerted on, and who reads it. |
| 13 | Rollout and compatibility | Flags, the migration order, old clients still out there, the way back. |
| 14 | Surfaces | UI, API, CLI, docs, copy, translations, accessibility: each one the change touches. |
| 15 | Tests and acceptance | The proof per deliverable and per failure path, in the test mode chosen (9.2). |
| 16 | Operations | Config, environment, secrets, scheduling, cost, and who owns it after it ships. |

## Method

1. **Build the deliverables list first** (5.2). Each entry names a thing that will exist
   when the task is done, an endpoint, a screen, a migration, a job, a document, a test, a
   config change, and what it must do. An entry that names an activity ("improve",
   "handle", "clean up") instead of an artifact is not a deliverable yet; rewrite it until
   it is one.
2. **Walk the sixteen aspects for every deliverable.** Each aspect gets exactly one mark:
   - `pinned: <source>`, settled by evidence produced in this session: `code:<file:line>`,
     `run:<command>`, `user:"<their words>"`, `rules:<file:line>` (`CLAUDE.md`, a documented
     convention), or `docs:<url fetched this session>`;
   - `asked: Q<n>`, a question in the batch forks it, and the question's `traces-to` line
     (6.2) names this deliverable;
   - `n/a: <reason>`, the aspect does not apply to this deliverable, and the reason is one
     that would convince the reviewer, not just you. "Not mentioned" is not a reason; the
     user never mentions rollout, which is why the row exists.
   A blank is a hole. A `pinned` mark with no source is a blank. A `pinned` mark whose
   source is what you remember about a library, a framework or a platform is a blank, until
   it points at the lockfile, the installed source, or documentation fetched this session
   (1.5, "Memory is a hypothesis").
3. **Fold, never pad.** One question may cover one aspect for several deliverables, and one
   `n/a` reason may cover a whole row. The map counts holes, not questions; the batch stays
   at the size the ask needs (6.5).
4. **Print the map with the restatement**, in the short form below, and close Phase 1 only
   on an empty holes line. A hole is an unpinned part of the anchor: one more question,
   through the wizard tool, then close (6.1, step 6).

## The report shape

```
Coverage map: <deliverable>
 1 Value             pinned: user:"so support stops answering the same ticket twice"
 2 Actors            asked: Q3
 3 Entry points      pinned: code:src/routes/invites.ts:41
 ...
15 Tests             asked: Q9
16 Operations        n/a: no config, no schedule, runs inside the request
holes: none
```

`holes:` lists the aspect numbers with no mark, or the word `none`. It is the last line of
every map, and the line the ledger reads.

## Verification

1. Does every deliverable have a map, and every map sixteen marks? (yes / no)
2. Does every `pinned` mark name a source produced in this session, none from memory? (yes / no)
3. Does every `asked` mark point at a question that is actually in the batch, whose `traces-to` names this deliverable? (yes / no)
4. Would every `n/a` reason convince the reviewer? (yes / no)
5. Is the holes line printed, and does it read `none`? (yes / no)

## Anti-rationalizations

| Thought | Reality |
|---|---|
| "It's a small fix, the map is overkill." | Fourteen marks will be one `n/a` line each. The two that are not are the ones the fix would have missed. |
| "I know how this library behaves." | You remember how it behaved. Pin it to the lockfile and its source or docs, or it is `asked`. |
| "The user didn't mention rollout." | The user never mentions rollout. That is why the row exists. |
| "I'll cover the rest in the plan." | The plan is written from this map. What is not here is guessed there. |
| "Sixteen rows will scare the user." | The user sees the short form, one line per row, most of them `n/a`. What scares a user is the hole found in production. |
