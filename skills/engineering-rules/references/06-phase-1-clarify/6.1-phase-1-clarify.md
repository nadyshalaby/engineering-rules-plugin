# 6.1 [phase] Phase 1, Clarify

**Open the ledger, learn the ground, lock the anchor, ask everything at once, write the repo
brief, then restate the approach and close.** Runs in full in every mode.

## Step 1. Open the ledger

Every substantive task opens the phase ledger (5.1) before anything else. The only tasks
that do not are the three trivial shapes in `SKILL.md` Definitions; there is no fourth
shape, and "the user told me to just do it" is not one. Print the block, name the substrate
once, set item one in progress, record the base commit, and keep it visible.

## Step 2. Learn the ground before you ask

You cannot ask a good question about code you have not read. Before the question round, use
the investigation method in 6.14:

- Read the files the ask names, and the files those import.
- Find the two or three closest existing examples of the thing being asked for, and note
  the conventions they establish. Those conventions bind your change.
- Detect the layout the repository already uses and state it in one or two lines, per the
  precedence rules in section 2.2. An undetected convention is one you are about to break.
- Where the answer to a load-bearing question is in the code, **find it rather than asking
  it.** A question whose answer is one grep away wastes the user's turn.
- If the task is UI-bearing (Definitions), read the frontend design law (15.1) now, and
  check whether `docs/design/DESIGN.md` exists.
- If the task type is `debug`, the evidence-gathering steps of 10.1 (D1) run here, inside
  Phase 1.

Anchor every fact you take from this to a `file:line` with a quoted snippet, and keep a
separate `NOT SURE` list for anything you are only partly sure about. Do not smooth partial
evidence into confident prose.

## Step 3. Write the goal anchor

Draft the five parts of the anchor (5.2): North-Star Goal, In-Scope, Out-of-Scope /
Non-Goals, Guardrails / Invariants, Success Signals. Beside it, a short list of open risks.
The question round below is what confirms and completes it; do not present it as settled
before the user has answered.

## Step 4. Ask, in one batched round

Every question goes through the wizard tool, batched, with the recommended option first.
The question contract (6.2) governs the format; the banks supply the questions.

- Classify the ask: `feature`, `fix`, `refactor`, `revamp` / `redesign`, `debug` or
  `research`. Combine banks where the ask genuinely spans two (6.5).
- Compose from the universal preamble (6.4) plus the matched bank (6.6 to 6.11), using the
  bank's COMPOSITION rules mechanically. Draw every recommendation from the domain
  mechanisms (6.12), never from "best practice". The contract (6.2), the preamble (6.4),
  the combining rules (6.5), the matched bank and the mechanisms (6.12) together run to
  several hundred lines: send a fork to read them and return the composed batch (5.5). The asking stays here, through the wizard tool, and so does every answer.
- Drop any question the code, the prompt or `CLAUDE.md` already answered, and say so in the
  preamble paragraph. Never ask more than the ask needs.
- Lead the message carrying the first wizard call with a one-paragraph *"What I heard you
  ask for"* preamble.
- Around sixteen questions is the soft target, not a ceiling and not a quota. When the batch
  comes back and a part of the anchor is still unpinned, or an answer opened a new fork, ask
  a second, smaller batch for exactly that. Then stop.

**A clarify round with no bank questions is legitimate** when the ask is unambiguous and the
code answered everything. Say that is what happened; do not pretend to have asked. The
restatement in step 6 still prints.

## Step 5. Write the repo brief

Build the repo brief (6.13) now, in every mode: stack, the triad commands run once in this
session, layout, the one layering rule that matters, the rules source, the test convention,
landmines. Every line ends with the command or `file:line` that proved it. In full mode it
goes into the work-doc at Phase 2; in quick mode it is printed and kept current in chat.

## Step 6. Restate and close

Restate what you heard in a few lines: the goal, the shape of the solution, the boundaries,
the test mode, the landing, and anything you are treating as an assumption. Print it under an
`## Approach` heading so the user sees exactly what is about to be built and can stop you.

**Full mode.** Print the restatement, tick item one, and open Phase 2. The plan is the gate.

**Quick mode.** Print the restatement and go straight to Phase 3. Quick mode has no gate
between clarify and code: the user's answers in the question round are the confirmation.
Two things still hold you here. An anchor part that is still unpinned gets one more question
through the wizard tool before you close. And a user who asks for a written plan by name, at
this point or any later one, promotes the task to full mode under the routing rules in 4.1:
the ledger is re-opened with the ten-item list and Phase 2 begins.

**Worktree.** When the workspace question (6.4, Q2) chose a separate copy, create the
worktree now in quick mode, following the procedure in 7.1, before any code. In full mode it
is created at Phase 2.

Then tick item one, print the reflection, re-print the ledger, and read the next phase's
reference file.
