# 6.4 [reference] The universal preamble

## Universal preamble

Runs before any task-type bank on every Phase 1, in every mode. Settles the intent, in the user's own confirmation, the guardrails, and the four cross-cutting logistics answers that every downstream bank assumes are already decided. See the question contract (6.2) for the canonical 4-section spec.

**SCENARIO**

Runs before any task-type bank, on every Phase 1. Sets the four cross-cutting logistics answers that every downstream bank assumes are already settled: scope shape, isolation strategy, test discipline, and done-state. Skip questions whose answers are already implied by the user's prompt or pinned in `CLAUDE.md`.

**COMPOSITION**

- If the user's prompt explicitly names a scope ("just this one file", "all over the codebase"), skip Q1 (Scope check).
- If the user is already on a branch named for the task, skip Q2 (Worktree) and confirm in the preamble. Also skip if the user prompt contains the literal substring `this branch`, `in place`, or `just push`.
- If `CLAUDE.md` pins a test discipline, skip Q3 (Tests) and confirm it in the preamble. Q3 never offers "no tests" for a behaviour change; the law (9.2) owes every behaviour change a proven test.
- Always ask Q4 (Done state) unless the user has explicitly stated PR vs merge intent in the prompt.
- Always ask Q0 (What I heard, and why) FIRST, in every bank, and never skip it: it is the user's confirmation that the intent was understood, and everything after it is built on that answer. A bank whose own first question restates the goal (6.6 Q1, 6.9 Q1) skips that question; Q0 carries it. Q5 (Must not break) follows Q0 in the first batch; skip Q5 only when the guardrails are already unambiguous from the prompt, and then restate them in the preamble for a one-line confirmation instead of asking.
- **"Prepend this bank" means Q0 and Q5 lead, not the whole file.** Q0 opens the first batch, Q5 sits beside it. Q1 through Q4 are logistics (scope, workspace, tests, done state) and go in the LAST batch, after the matched bank's domain questions. This is the canonical batch order and the other files point here for it: intent first, then what the thing actually is, then where it goes and how it ships. Asking where to put the work before settling what the work is means asking about the wrong feature, and the user answers it seriously because the question looks reasonable.
- The "What I heard you ask for" paragraph that leads the first batch carries an `Assuming:` list under it: every assumption you are making, each with the source tag that gave it to you (`code:`, `user:`, `rules:`, `docs:`), and one line inviting the user to strike any of them. An assumption with no source is not listed as an assumption; it becomes a question.

**QUESTIONS**

Every question below is a TEMPLATE. Substitute the real names, files and current behavior you found before sending it, so the user can answer without opening anything. Angle-bracket slots are yours to fill. `What happens:` lines are mandatory and are what the user reads.

Q0. What I heard, and why
- Text: Here is what I understood, tell me if any part is off. You want `<the outcome, in their own words>`, for `<who it is for>`, because `<why now, or what hurts today>`. Done means `<what will exist and what the user will be able to do>`, and I would leave `<what you understood to be excluded>` alone. `<When the ask was ambiguous: "I read it as X rather than Y because <what in the code or the message settled it>.">`
- Header: The intent
- Options:
  - A. Yes, that's exactly it (Recommended)
    - What happens: I build toward that and check the details with you in the next questions.
  - B. Close, but let me correct a part
    - What happens: Tell me which part is off and I re-check everything that rested on it before asking anything else.
  - C. Not sure yet, show me two or three ways this could go
    - What happens: I sketch the options with what each one costs and you pick, before I plan anything.
- Why-this-matters: Locks the North-Star Goal and its value line in the anchor (5.2): for whom, what changes, how anyone would know. Every later question traces to a deliverable this answer defines; a wrong restatement here poisons every downstream phase. Option B re-opens the ground read (6.1, step 2) for the corrected part; option C branches to a framing sub-question before any domain question is sent. Never skipped, in any bank, in any mode.
- Traces-to: the North-Star Goal and the deliverables list, every one of them.
- Cost-of-guessing: the whole task, built against the wrong intent.

Q1. Is this on its own or part of something bigger
- Text: Is `<the thing they asked for>` a standalone piece of work, or one step in something larger you already have in flight?
- Header: Scope
- Options:
  - A. Just this, on its own (Recommended)
    - What happens: I focus only on this and don't try to fit it into a bigger plan.
  - B. It's part of something bigger already underway
    - What happens: I'll look at the related work first and match how it was done, so the two fit together.
  - C. It's the first step of something bigger
    - What happens: I'll build it so the next pieces slot in easily, rather than as a one-off.
- Why-this-matters: Determines whether the work-doc is standalone or links to a parent plan via the `related` frontmatter field (full mode), and whether Phase 1 step 2 surveys neighbouring work before the plan is stated.

Q2. Where the work should happen
- Text: Should I do this on a separate copy of your project so your current branch stays untouched, or work directly where you are now (you're on `<current branch name>`)?
- Header: Workspace
- Options:
  - A. Separate copy, keep my current branch clean (Recommended)
    - What happens: Your current work is untouched. When it's done you review it and decide whether to bring it in.
  - B. Work right here on this branch
    - What happens: Changes appear in your working folder straight away. Faster, but mixed in with whatever else you have going.
- Why-this-matters: Triggers (or skips) the worktree creation, which happens at the close of Phase 1 in quick mode and at Phase 2 in full mode (7.1), and adds the worktree-cleanup row to the ledger for Phase 6.

Q3. How much testing
- Text: How do you want this proven? For everything that changes behaviour I write automated tests and break the code on purpose once to prove each test really catches a failure. For a bug, the failing test comes before the fix.
- Header: Testing
- Options:
  - A. Automated tests, proven to catch failures (Recommended)
    - What happens: Every behaviour change gets a test, and I show you each test failing on purpose before it passes for real.
  - B. Automated tests for behaviour, and I'll check the visual parts by hand
    - What happens: Behaviour still gets proven tests. For purely visual changes I list the exact steps and walk them myself, then you can too.
  - C. There's already a test suite for this, extend it
    - What happens: I add to the existing tests in the same style, and still prove each new test can fail.
- Why-this-matters: Sets each task's test mode per 9.2: `test-authoring` after the code lands (bug fixes: the reproduction first), `manual smoke` only for cosmetic changes the user chose in B, `none` only with a written reason. Recommend A unconditionally; there is no option that skips tests on a behaviour change, because the law does not allow one.

Q4. What you want at the end
- Text: When the work is finished, what should be waiting for you?
- Header: Handover
- Options:
  - A. The changes ready on a branch for you to look at (Recommended)
    - What happens: Nothing goes live. You read it over and merge when you're happy.
  - B. A pull request opened for you or your team to review
    - What happens: Same code, but with a written summary and a place for others to comment.
  - C. Merged straight into the main branch
    - What happens: It lands directly. Choose this only if you're comfortable with it going in unreviewed.
- Why-this-matters: Sets Phase 6's landing in both modes: full mode presents the four options (13.2, Step B) with this answer recommended first; quick mode executes this answer with no second menu (4.2). Recommend A when the diff is ≤3 files OR ≤200 added lines; B for larger or cross-team diffs; C ONLY when the user prompt contains the literal substring `ship it`, `merge it`, `commit and push`, or `merge directly`.

Q5. Anything I must not break
- Text: Is there anything that must keep working exactly as it does now, no matter what? For example `<name 1-2 real things you spotted, e.g. "existing users staying logged in" or "the nightly export">`.
- Header: Must not break
- Options:
  - A. Nothing specific, use your judgment (Recommended)
    - What happens: I'll protect anything that looks important and tell you before touching something risky.
  - B. Yes, let me name them
    - What happens: Whatever you name becomes a hard line I won't cross, and I check against it before finishing.
  - C. I'm not sure, tell me what you think is at risk
    - What happens: I'll list what this change could affect and you confirm before I start.
- Why-this-matters: Fills the Guardrails/Invariants part of the goal anchor (5.2), enforced by the Phase 2.5, Phase 4 and Phase 5 drift-checks. A violated guardrail is a Critical finding.

**EXIT CRITERIA**

Q0 answered A, or B and C resolved into a corrected restatement the user confirmed; Q1 to Q5 each answered or explicitly skipped per COMPOSITION rules; the `Assuming:` list printed with a source per line; scope sentence, worktree decision, test mode, and done-state recorded (work-doc in full mode, the in-chat anchor block in quick mode); the goal anchor's Guardrails seeded from Q5; no answer left as free-text without being reduced to one of A/B/C/D semantics.
