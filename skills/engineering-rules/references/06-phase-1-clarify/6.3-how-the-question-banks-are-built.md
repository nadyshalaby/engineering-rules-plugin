# 6.3 [reference] How the question banks are built

Phase 1 builds **one batched questionnaire** drawn from the universal preamble (6.4) plus the bank
for the matched task type. The question contract (6.2) is the canonical 4-section
specification every bank conforms to; a bank that drifts from it is a defect.

Every bank asks about the same four things beyond the logistics, in its own words: the
**proven shape** working systems use for the domain the request touches, whether the
**expensive half** of the request needs to exist (the necessity challenge), the **business
rule** that has to be exactly right, and what the **real numbers** are. The mechanisms behind
the first of those are shared data and live once, in 6.12.

| Section | When Phase 1 reads it |
|---|---|
| 6.2 The question contract | Always. Delivery format, the clarity law, the honesty rule, how `(Recommended)` is chosen, the 4-section bank specification. |
| 6.4 The universal preamble | Always. Runs before any task-type bank to settle goal, scope, workspace, tests and done-state. |
| 6.5 Picking and combining the banks | Always. Closing rules for picking and combining questions across banks, and the drop order when the batch is too long. |
| 6.6 Question bank, feature | When the user is adding new behaviour the system does not currently have. |
| 6.7 Question bank, fix | When the user is reporting broken behaviour with a clear reproduction. |
| 6.8 Question bank, refactor | When behaviour should NOT change but structure should. |
| 6.9 Question bank, revamp and redesign | When old behaviour is being replaced: UI redesign, API redesign, subsystem replacement. |
| 6.10 Question bank, debug | When the user has a mystery with no reliable reproduction. |
| 6.11 Question bank, research | When the user wants to explore an idea before committing to build it. |
| 6.12 Domain mechanisms | Whenever the request touches a domain it names. Reference data, not a bank: the mechanism behind each recommendation and the failure it prevents. |

The `type` the bank was chosen for is written into the work-doc frontmatter in full mode
(7.2) and stated in the Phase 1 restatement in quick mode.
